# AI高画質化の高速化 — 計測結果

対象: `AI_Video_up/vup/vup.py`
素材: `サンプル.mp4`（720x480 h264 VFR / 16分34秒 / 24,279 frame）と、
その300秒地点から60秒を切り出した `テスト60秒.mp4`
機体: RTX 4070 Ti 12GB / Ryzen 5 5600X (6C12T) / Windows 11 /
torch 2.10+cu126 / TensorRT 11.2 / ffmpeg full build

---

## 0. 結論

### 全長16分34秒（720x480 → 1440x960）

| 版 | 総時間 | 出力 |
|---|---|---|
| 旧実装（ncnn-vulkan 4並列 + 中間JPEG + libsvtav1） | 18分45秒 | 映像だけ4倍速になる |
| 検証開始時点の vup（torch / bgr24 / `sd` / p7） | **3分11秒** | 映像が徐々に遅れ末尾3分が欠ける |
| **本改修後**（TensorRT bs2 / `sd-fast` / p4 / nv12） | **1分13秒** | **原本と一致（ずれ 0.00〜0.10秒）** |

**検証開始時点から 2.6倍、旧実装から 15.4倍**です。

出力例（サンプル.mp4 の780秒地点）は `doc/result_sample.png` にあります（絵は git 管理外）。

ただし速度より重いこととして、**この検証で出力が壊れていることが判り、直しています**（第2章）。

### 効いた順（60秒clip、処理時間）

| 積み上げ | 処理 | 総時間 | 起点比 |
|---|---|---|---|
| 1 起点（torch / bgr24 / 非fuse / `sd` / p7） | 13.2s | 21.2s | — |
| 2 ＋ nv12出力 ＋ 前後処理のfuse | 12.8s | 21.0s | 1.03倍 |
| 3 ＋ encoder `-preset p7` → `p4` | 12.0s | 20.0s | 1.10倍 |
| 4 ＋ model `sd` → `sd-fast` | 7.4s | 15.0s | 1.78倍 |
| 5 ＋ TensorRT bs2（modelは `sd` に戻した参考値） | 6.8s | 10.7s | — |
| **6 ＋ TensorRT bs2 ＋ `sd-fast`** | **4.8s** | **8.3s** | **2.75倍** |
| 7 6 で dedup を `strict` にした参考値 | 5.4s | 8.9s | — |

**model の変更（1.62倍）と TensorRT（1.54倍）が二本柱**で、
encoder preset が1.07倍、dedup が1.13倍です。
nv12化と fuse は速度にはほとんど効きませんでした（理由は第4章）。

### x4出力（2880x1920）

| 条件 | 処理 |
|---|---|
| `-preset p7`（従来の既定） | 27.4s |
| `-preset p4` | **15.5s** |
| `-preset p4` ＋ TensorRT bs2 | **11.2s** |

**preset を変えるだけで1.77倍**です。理由は第5章。

## 1. 計測の前提

### 1.1 GPUの排他

この検証は5つのprocess（lead + 調査Agent 4体）が同一GPUを共有して進めたため、
**途中までの実測値は最大3倍歪んでいました。** 背景sm が92〜98%で埋まった状態では、
本来104 fps 出るSRが25〜40 fps しか出ません。

対策として `scratchpad/gpulock.py` による排他lock（`O_EXCL` のatomic create、
25分でstale奪取）を全員に課し、さらに測定harnessに
**「背景smが12%以下になるまで待つ」関門**を入れ、各測定の背景smを記録しました。

**本Docの速度の数値はすべて背景sm 0〜4%の静穏環境で、条件ごとに2回走らせて
速い方を採ったものです。**

この過程で途中経過として出した「nv12化で33秒→23秒」という値は競合による誤りでした。
静穏環境では差がありません。

### 1.2 「総時間」と「処理時間」を分ける

60秒の素材では起動が総時間の3〜4割を占めます。長い素材では無視できる分なので、
**起動**と**処理**を分けて記載しています。

## 2. 検証の途中で見つかった不具合（速度以前の問題）

高速化のための計測中に、**出力そのものが壊れている**不具合が4件見つかりました。
いずれも今回修正しています。

### 2.1 映像が徐々に遅れ、末尾が丸ごと欠ける（致命的）

`ffmpeg -i src -f rawvideo -pix_fmt bgr24 -` は、rawvideo muxer が timestamp を
持たないため、既定の `-fps_mode cfr` で **VFR入力をCFRへ複製展開**します。

| decode指定 | サンプル.mp4 が出すframe数 |
|---|---|
| packet数（＝真の source frame） | 24,279 |
| **既定（修正前の vup.py）** | **29,819** |
| `-fps_mode passthrough` | 24,279 |

vup.py は pipe から出てくるのが source frame だと仮定して `for i in range(n_src)` で
24,279枚だけ読み、さらに自前の schedule で複製を掛けていました。つまり
**複製が二重に掛かり、先頭81%の映像を全長へ引き伸ばして出力**していました。

60秒clipで、出力の絵が原本のどの時刻と一致するかを0.05秒刻みで総当たりした実測:

| 出力時刻 | 修正前 → 原本 | 修正後 → 原本 |
|---|---|---|
| 10.0s | 11.45s（+1.45s） | **10.00s（±0.00s）** |
| 30.0s | 27.50s（−2.50s） | **30.00s（±0.00s）** |
| 58.0s | 56.45s（−1.55s、別の絵） | **58.00s（±0.00s）** |

全長16分34秒では**末尾約3分が出力されません**。
README が「旧実装は映像だけ4倍速になる」と直したつもりの問題が、
逆向きの同種のずれとして残っていました。

**修正**: decoder に `-fps_mode passthrough` を付けました。
修正後の全長出力は 994.96秒（原本 994.97秒）で、
t=60/300/600/900/980秒のいずれでもずれは 0.00〜0.10秒に収まります。

### 2.2 `-ss ... -c copy` で切った素材で時刻軸が105 frameずれる

`read_pts` は packet の PTS を使いますが、`ffmpeg -ss ... -c copy` で切った file は
先頭GOPの前置きが**負のPTS**で残っており、decoder はこれを捨てます。
実測でテスト用clipは packet 1,567 に対し decoder が出す frame は 1,462 で、
**差の105枚がすべて負のPTS**でした。捨てないと i 番目のframeに別の時刻を割り当てます。

**修正**: stream の開始時刻より前のPTSを捨てるようにしました。

### 2.3 画素の縦横比（SAR）が失われ、映像が横に潰れる

サンプル.mp4 は anamorphic（SAR 853:720 / DAR 853:480 ≈ 16:9）ですが、
rawvideo で渡すと SAR が失われ、出力は SAR 1:1 の 1440x960 = **表示 3:2** に
なっていました。

**修正**: 入力のSARからDARを計算して `-aspect` で引き継ぎます。
出力DARは 247:139 = 1.7770 で、原本の 853:480 = 1.7771 と 0.004% 以内で一致します。

### 2.4 `--tile-diff` が起動直後に落ちていた

`TileDiffBackend` に `run_into` が無く、reader thread 化以降ずっと例外で落ちていました
（README の tile差分の数値はそれ以前に測られたものです）。
`run_into` を足して動くようにしました。結論はREADMEと同じで、
81 frame 中79 frame が全画面SRへ落ち、実効計算量比 0.975 と得になりません。

### 2.5 波及: 「frame使い回しで1.50倍削減」は誤りでした

この数値は、ffmpeg が挿入した完全複製frameを含む水増しされた列で測ったものです。
真の source frame だけで測り直すと、全長（出力に使う23,103枚）で:

| 判定基準 | SR回数 | 削減 |
|---|---|---|
| 厳密一致 | 22,818 | 1.01倍 |
| 旧 balanced | 19,134 | **1.21倍** |
| 新 balanced（4x4 box平均、閾値16） | 18,559 | **1.24倍** |
| 新 aggressive（同、閾値20） | 18,070 | **1.28倍** |

**真の source frame の完全一致率は3.1%です。**
VFRの段階で既に2コマ打ちが畳まれた後の列なので、時間方向の余地は元々小さいものでした。

## 3. 天井はどこか

改修前の状態で成分ごとの上限を測りました（1440x960、乱数入力なのでencoderには最悪値）。

| 経路 | 実測 |
|---|---|
| decode CPU h264 → bgr24 pipe | 957 fps |
| decode CPU h264 → yuv420p pipe | 2000 fps |
| decode `-hwaccel cuda` → bgr24 pipe | 597 fps |
| nvenc hevc p7 ← bgr24 pipe | 167 fps |
| nvenc hevc p5 ← bgr24 pipe | 188 fps |
| nvenc hevc p5 ← **nv12** pipe | **237 fps** |
| nvenc hevc p1 ← nv12 pipe | 283 fps |

`-hwaccel cuda` が遅いのは NVDEC で decode してから結果を CPU へ戻すためです。

GPU側を1 frameあたりで分解すると次の通りです（`sd`）。

| 段階 | 実測 |
|---|---|
| H2D (720x480 bgr24 1.04MB, pinned) | 0.096ms |
| H2D + 前処理 (permute/half/div/channels_last) | 0.873ms |
| **model forward (torch.compile)** | **9.98ms** |
| model forward (eager) | 14.05ms |
| nv12変換 (GPU) | 0.454ms → `torch.compile` で 0.161ms |
| bgr24変換 (GPU) | 0.063ms |
| D2H nv12 (2.07MB, pinned) | 0.204ms |
| D2H bgr24 (4.15MB, pinned) | 0.361ms |

**転送は合計0.3msで、model forward の3%しかありません。**
完全GPU常駐 pipeline で消せるのはこの3%です。

## 4. 何が遊んでいるか — 律速は動く

| 段階 | GPU SM | NVENC | CPU | 律速 |
|---|---|---|---|---|
| 起点（`sd` / p7 / bgr24） | 90〜97% | 8〜22% | 2〜4 core / 12 | **SR** |
| 最終構成（全長） | 99%（SR stream占有） | 25〜29% | — | **SR と encode が共律速** |

全長の最終構成では、writer thread が処理69.9秒のうち **67.6秒を pipe への書込**に
使っており（入力待ちは1.67秒）、**出力側が詰まる側に回りました。**

- **起点では「SRを速くする」以外に道がありませんでした。** decode 957 fps、
  nvenc 167〜283 fps に対し SR は100 fps 前後で、encoder も CPU も遊んでいました
- **SRを2.7倍にした結果、今度は encoder が同格になりました。** 次の高速化は
  encoder 側（または出力frame数の削減）に向かいます

### batch化は torch では効かない

720x480 の Compact は1枚でSMを埋めるため、torch では batch を積むと逆に遅くなります。

| batch | torch.compile（`sd`） | TensorRT（`sd-fast`） |
|---|---|---|
| 1 | 103.2 fps | 159.2 fps |
| 2 | 77.6 fps | **333.0 fps** |
| 4 | 57.7 fps | 357.3 fps |
| 8 | 65.3 fps | — |

**TensorRT だけが batch で伸びます。** これが TensorRT の効果の6割を占めます。

## 5. encoder preset が SR を待たせていた

x4 出力で encoder の preset だけを振りました。**SR側は一切変えていません。**

| encoder設定 | 処理時間 | SRのGPU stream占有/回 |
|---|---|---|
| `-preset p7 -cq 24`（従来の既定） | **27.4s** | 19.7ms |
| `-preset p4 -cq 24` | **15.5s** | 12.0ms |
| `-preset p4` ＋ TensorRT bs2 | 11.2s | 16.2ms（bs2なので2枚ぶん） |

**preset を p7 から p4 にするだけで1.77倍**です。
注目すべきは右列で、**SRの計算は何も変えていないのに、SRのGPU stream占有が
19.7ms → 12.0ms へ落ちています。**

つまり nvenc は「別engineだから干渉しない」のではなく、
**別processのCUDA contextとして我々のSR kernelと時分割され、SRを待たせていました。**
「sm使用率が41%しか無いのに GPU stream 占有は82%」という食い違いは、これで説明が付きます。

x2 出力（1440x960）でも同じことは起きますが、encoder の仕事が1/4なので影響は小さくなります。

| 条件 | p7 | p5 | p4 |
|---|---|---|---|
| x2 `--model sd` | 11.2s | 10.4s | **10.2s** |
| x2 `--model sd-fast` | 8.4s | — | **6.9s** |

`sd-fast` の方が preset の影響が大きい（1.22倍 対 1.10倍）のは、
SR が軽くなるほど encoder の占める割合が上がるためです。

**画質側**: 同じ `-cq 24` での出力file sizeは p7 18.5MB / p5 19.0MB / p4 19.2MB でした。
`cq` は品質目標型の rate control なので、**速いpresetは同じ品質をやや大きいfileで
達成します**（p4 は p7 に対して3.5%大きいだけ）。

`-split_encode_mode 3`（NVENCの2基を両方使う）も試しましたが、
全長で 69.6秒 → 68.9秒（1%）で、採用していません。

## 6. 実施した改修

### 6.1 TensorRT fp16 + batch 2（`trt_backend.py`、既定ON）

前処理（uint8 BGR → fp16 NCHW）から後処理（nv12化）まで engine に入れています。
model だけ差し替えると、`FusedSR` が畳んでいた前後処理が別kernelに戻るためです。

engine は (重みfile, 入力解像度, 倍率, batch, 画素形式, TensorRT版, GPU名) ごとに
1つ作られ、初回だけ20〜45秒掛かります（以降は0.75秒で読み込み、1つ400〜650MB）。

`sd-max`（DAT2）だけは build に2GBを超える workspace が要り、
「insufficient memory」で tactic を全部捨てて失敗していました。
空きVRAMの半分（上限6GB）を割り当てるようにして、**全11 modelが通ります。**

品質は **TensorRT fp16 が PSNR最悪 59.22dB・画素差最大 2/255** で、
既に許容済みの torch fp16（60.96dB・2/255）と同水準です。

batch 2 のために `sr_worker` を batch 対応にしました。frame の順序が狂わないことを
**bs=1 の出力と突き合わせて確認**しています（PSNR 61.10dB・最大画素差5、
順序が狂えば桁違いの差になります）。

### 6.2 model を `sd` → `sd-fast`（0.60M → 0.30M）

end-to-end で 12.0秒 → 7.4秒（1.62倍）、SR単体で 118.2 → 213.4 fps（1.81倍）。

openmodeldb の全671件を調べ、20個以上の重みを実際に落として試しましたが、
既存の `sd` / `sd-fast` を超える物はありませんでした。

品質は、60秒の素材1798 frameで**差が30/255を超えた画素は最悪frameでも0.006%**、
2倍拡大で並べても判別できません。差は線画の輪郭にだけ乗り、平坦部には出ません。

sd と sd-fast の最悪frame を並べた絵は `doc/model_worst.png` にあります（絵は git 管理外）。

### 6.3 encoder の既定を `-preset p7` → `-preset p4`

第5章の通り。

### 6.4 dedup の判定を 4x4 box平均 + 最大へ

`|diff|` を 4x4 の box平均へ畳んでから最大を取ります。h264 の encode noise は
面に薄く広がるので平均で潰れ、瞬きや口のような局所的で濃い変化だけが残ります。

| 判定基準 | SR回数 | 削減 | 欠落合計 | 欠落最大 | >100画素のframe |
|---|---|---|---|---|---|
| 旧 balanced | 19,134 | 1.21倍 | 43,884 | 494 | 138 |
| 旧 aggressive | 15,336 | 1.51倍 | 4,555,428 | 9,371 | 2,638 |
| **新 balanced（box4<16）** | 18,559 | **1.24倍** | 146 | **13** | **0** |
| **新 aggressive（box4<20）** | 18,070 | **1.28倍** | 3,353 | **70** | **0** |

欠落画素 = 使い回したframeと本来のframeで `|d|>48` の画素数（判定基準と独立な指標）。
実際に動いているframeの `|d|>48` 画素数は p5=268・p10=680・中央9,206なので、
新 aggressive の最悪70画素でも本物の動きの最小規模の1/4以下です。
**旧 aggressive は瞬きや口の動きを取りこぼしていました。**

閾値は素材のh264 noise水準に対して選んだ値なので、`--dedup-thresh` で較正できます。

### 6.5 出力pipeを bgr24 → nv12

pipe の帯域が半分（4.15MB → 2.07MB/frame、全長で 123.7GB → 61.8GB）になり、
nvenc の native 形式なので ffmpeg 側の色変換も消えます。

**速度への効果は x2 で0%、x4 で3%**でした。採用の理由は速度ではなく、
CPU負荷の半減と、**色が swscale より正確になる**ことです。

float64 で丸める前の真値からのズレ:

| 変換 | Y 符号付き / 絶対 | UV 符号付き / 絶対 |
|---|---|---|
| ffmpeg swscale | **−0.5113** / 0.5113 | **−0.3937** / 0.3938 |
| 本実装（float + round） | **−0.0015** / 0.2381 | −0.1371 / 0.1896 |

**swscale は切り捨てのため Y が系統的に0.51暗く出ます。**
改修後の出力は改修前より B が+1.55 / R が+1.31 明るく出ますが、
これは改修前が swscale の切り捨て分だけ暗く沈んでいたためで、改修後の方が正しい色です。

### 6.6 前後処理を `torch.compile` の graph へ畳む（`FusedSR`）

前処理 0.873ms と nv12変換 0.454ms は合わせて model forward の13%でした。
入力uint8から出力画素形式までを1つの関数にして `torch.compile` に渡しています。
SR単体で 106.2 → 114.3 fps（1.08倍）。非fuse版との出力差は PSNR 62.5dB。
（TensorRT を使う場合はこの経路を通りません）

### 6.7 起動時間

| 段階 | 実測 |
|---|---|
| `import torch` | 4.20s |
| **`import spandrel`** | **3.71s** |
| `load_from_file` | 0.04s |
| `torch.compile` | 約4.5s |

`import spandrel` は52 arch すべてを読み込むため単体で3.7秒掛かります。
SRVGGNetCompact 系は重みの形から自前実装で組む経路を用意し、spandrel を通しません。
**Compact系5 model すべてで spandrel版との出力差 0.000000 を確認済み**です。

この過程で、`params` と `params_ema` の両方を持つ重み（`2x_AnimeJaNai_SD_V1beta34_Compact.pth`
ほか12件）で**採るべきは EMA 側**であることが判りました。順序を間違えると重みが最大0.022、
出力が0.18ズレます。spandrel の `canonicalize_state_dict` と同じ順序に合わせています。

`torch.compile` は約4.5秒掛かり、1 SR回あたり3.2ms速くなります（損益分岐は約1400 SR回）。
`--compile auto` が素材の長さから判断します。TensorRT を使う場合は不要になるため、
最終構成の起動は **3.5秒**です。

## 7. Agent team の調査結果

観点を4つに分け、それぞれ専任のAgentが調査しました。
以下は各Agentの報告のうち、lead側で妥当性を確認した内容です。

### A. GPU推論の高速化

| 手段 | 実測 | 判定 |
|---|---|---|
| **TensorRT fp16 + batch 2** | **SR単体 1.80倍** | **採用** |
| TensorRT fp16 batch 1 | 1.12倍 | batch 2 の下位互換 |
| batch化（torchのまま） | bs2 0.92倍 / bs4 0.88倍 | 不採用 |
| CUDA Graph / `reduce-overhead` | 1.00倍 | 不採用。model単体では+11%だが前後処理を入れると消える |
| `max-autotune` | 0.98倍 | 不採用。4070 Tiは60 SMで inductor の閾値68 SM未満のため Triton conv template が無効 |
| TensorRT int8 | 0.86倍／PSNR最悪 34.14dB・画素差最大134 | 不採用。**遅いうえに明確に劣化** |
| TensorRT fp8 (Ada) | 0.85倍／PSNR最悪 50.90dB・画素差最大21 | 不採用。同上 |
| ONNX Runtime CUDA EP | 0.45倍 | 不採用 |
| ONNX Runtime TensorRT EP | IOBinding で失敗 | — |
| cudnn/cublas の精度設定 | — | TF32系は fp32 にしか効かない。fp16 accumulate は torch から選べない |

**なぜ TensorRT 以外に手が無いのか**が profile で示されました。
`torch.compile` の 8.54ms の内訳は conv 5.61ms (65.7%) と、bias+PReLU を畳んだ
triton kernel 2.68ms (31.4%) です。

- conv は **72.7 TFLOPS** で、観測clock 2805MHz での fp16(fp32累積) 理論値 86.2 TFLOPS の **84%**
- epilogue は **561 GB/s** で帯域限界。消すには conv の epilogue へ融合するしかなく、
  cuDNN の融合は ReLU 止まりで PReLU は対象外

TensorRT bs=2 は 91.8 TFLOPS で fp32累積の理論値を超えます。
**epilogue融合 + fp16累積**を使っており、これは torch/cuDNN からは選べません。

### B. I/O経路

| 手段 | 実測 | 判定 |
|---|---|---|
| encoder の画質knob（multipass / lookahead / b-frame / AQ） | ΔVMAF +0.02 / +0.01 / −0.04 / +0.04（AQはsize 1.48倍） | 不採用。**NVENCの余力は画質に変換できない**（cq modeで画質を買う通貨は時間ではなくbitrate） |
| 全部盛り | ΔVMAF −0.04、size 1.44倍 | 不採用。盛るとむしろ下がる |
| `-cq` を下げる | cq22 +0.44 / cq20 +0.71 / cq18 +0.97 VMAF | 不採用。現行cq24が既に基準比 PSNR 50.7dB / VMAF 95.5 でほぼ透過 |
| GPU常駐 pipeline（PyNvVideoCodec） | **Windowsで動かない** | 不採用。decodeは通るがencodeが torch tensor を受け付けない。効果も2.6% |
| NVDEC hardware decode | 325 fps（CPU decode 695 fpsより遅い） | 不採用 |

なお、この担当は当初「NVENCは別engineなので総時間に影響しない」と結論していましたが、
**測定がすべて `-f null -` の encode 単体か SR を止めた状態**で、
SR と nvenc が同時にGPUを取り合う状況を測っていませんでした（第5章）。

### C. 時間方向のalgorithm

| 手段 | 実測 | 判定 |
|---|---|---|
| **dedup判定を 4x4 box平均 + 最大へ** | 削減 1.21 → 1.28倍、取りこぼし最大 494 → 70画素 | **採用** |
| 過去16枚のcacheと照合 | 削減 1.45倍 | 見送り。writer/buffer poolの作り直しと判定の別thread化が要る |
| h264 の skip macroblock 活用 | 変化macroblock率が中央 **80.6%** | 不採用。**noiseを完全に排しても切り出せる形が無い**（矩形1個97.2%／横帯97.9%／tile128 98.6%の面積） |
| tile差分（noise-freeな判定でも） | 1.01〜1.03倍 | 不採用。README の「h264 noiseが真因」は誤りで、真因は**変化が画面全体に散っている**こと |
| 低解像度SR + 差分補正 | 高周波量が通常の29%（bicubicは21%） | 不採用。SRにGPUを使う意味が消える |
| optical flow で中間frame生成 | PSNR 32.8（そのまま保持は40.3） | 不採用。**何もしないより悪い** |
| 整数画素 pan の再利用 | 該当 **0 frame**、探索自体が9.01ms/frame | 不採用 |
| 最終convへ縮小を畳み込む | 1.00倍 | 不採用。数学的には正しいが最終convはFLOPの4.5% |
| recurrent/propagation系VSR | — | 不採用。per-frameの計算量が**増える**手法群 |

### D. model の選定

| model | arch | param | SR単体(torch) | 判定 |
|---|---|---|---|---|
| `sd`（従来の既定） | SRVGGNetCompact | 0.60M | 118.2 fps | — |
| **`sd-fast`** | SRVGGNetCompact | **0.30M** | **213.4 fps** | **既定に採用** |
| 蒸留したUltraCompact（自作） | SRVGGNetCompact | 0.30M | `sd-fast`と同一 | 不採用（下記） |

蒸留modelは**評価が汚染されている**とAgent自身から申告がありました。
サンプル.mp4 の全長から等間隔に200 frame取って学習し、**同じ動画のframeで採点**しています。
加えて品質も一長一短（輪郭PSNRと平坦部noiseは上、全体PSNRとLPIPSは下）で、
既定を置き換える段階にありません。

## 8. 検討したが採用しなかった手（全体）

| 手段 | 判定 | 根拠 |
|---|---|---|
| **入力pipeも yuv420p / nv12 にする** | 不採用 | 律速がGPUのSMなので**逆効果**。H2D は 0.096ms しかなく半分にしても 0.048ms しか浮かないのに、GPU側の YUV→RGB は約0.3ms掛かる。decode も 957 fps で余っている |
| **NVDEC hardware decode** | 不採用 | `-hwaccel cuda` は結果をCPUへ戻すため 597 fps と CPU decode より遅い |
| **完全GPU常駐 pipeline** | 不採用 | 効果は H2D+D2H の 2.6%。かつ Windows では encode が torch tensor を受け付けない |
| **batch化（torch）** | 不採用 | bs2 で0.92倍、bs4 で0.88倍 |
| **TensorRT int8 / fp8** | 不採用 | 0.86倍 / 0.85倍と遅いうえ、int8 は PSNR最悪 34.1dB と明確に劣化 |
| **CUDA Graph / max-autotune** | 不採用 | 1.00倍 / 0.98倍 |
| **ONNX Runtime** | 不採用 | CUDA EP は0.45倍、TensorRT EP は IOBinding で失敗 |
| **encoder の画質knob** | 不採用 | ΔVMAF ±0.04以内で size は最大1.48倍 |
| **`-split_encode_mode 3`** | 不採用 | 全長で1% |
| **letterbox を crop して SR面積を減らす** | 不適用 | `cropdetect` で479 frameすべて `crop=720:480:0:0`。黒帯が無い |
| **出力frame数の削減（VFR出力）** | 見送り | rawvideo にも Y4M にも per-frame の timestamp が無く、CFRが強制される。PyAVでencoderへ明示PTSを渡すか中間fileの復活が要る。**出力側が律速に回った今は再検討の価値がある** |
| **`torch.compile` を背景threadで進める** | 不採用 | 長い素材では compile の4.5秒は全体の2%未満。短い素材は `--compile auto` が既に省く |
| **nv12変換をCPUへ降ろす** | 見送り | GPUは0.29ms空くが D2H が倍になる。差引 model forward の約2.5% |
| **tile差分 / motion vector / 低解像度SR / flow補間 / pan再利用 / 最終conv畳み込み / recurrent VSR** | 不採用 | 第7章C |

## 9. 今後の課題

出力側が律速に回ったため、**次に効くのは encoder 側と出力frame数**です。

1. **出力frame数の削減**。現在 source 24,279枚から出力29,819枚を作っています
   （29.97 CFRへ引き伸ばし）。`--fps-mode dominant`（23.976）にすると出力が
   23,852枚（−20%）になり、しかも落とす source frame はむしろ減る（1,176→903）
   という測定があります。出力fpsを変える判断なので既定にはしていません
2. **dedup の cache16**（削減 1.28 → 1.45倍）。writer と buffer pool の作り直しと、
   判定を専用threadへ出す改修が要ります。判定costは指紋(45x30)の前段選別が必須で、
   総当たりだと 6.64ms/frame と SR より高くつきます
3. **蒸留による専用model**。1本の動画・4分半・無調整で `sd-fast` と同等まで来ています。
   本番用には複数話数での学習と、学習に使っていない動画での評価が必要です
4. **別素材での較正**。dedup の閾値20はサンプル.mp4 の h264 noise 水準に対して
   選んだ値です。`--dedup-thresh` で調整できるようにしてありますが、自動較正は
   試していません

## 12. 10秒clipでのmodel別実測

`品質比較/` の8条件について、end-to-end の時間を model 別に測った物です。
素材は `テスト10秒.mp4`（`サンプル.mp4` の300秒地点から `-c copy` で10秒。
packet 346 に対し decoder が出す frame は 241 で、差の105枚が負のPTS＝2.2 と同じ形）。
encoder は本番既定の `-preset p4 -cq 24`、背景sm 12%以下を待って各条件2回走らせ
処理時間の速い方です（実測時の背景smは4〜6%）。出力は300 frame / 10.016秒。

| 条件 | 総時間 | 起動 | 処理 | 出力fps | SR fps |
|---|---|---|---|---|---|
| AI無し（lanczos, ffmpegのみ） | 0.8s | — | — | — | — |
| **`sd-fast` ＋ TensorRT bs2（既定）** | **7.2s** | 3.2s | **1.0s** | **293.7** | 185.8 |
| `sd-fast`（torch.compile） | 9.9s | 4.8s | 2.1s | 144.8 | 91.6 |
| `anime`（旧実装と同じ重みを vup で） | 11.1s | 5.1s | 2.9s | 104.2 | 65.9 |
| `sd` | 11.2s | 5.1s | 3.0s | 100.3 | 63.4 |
| `sd-janai` | 11.4s | 5.3s | 3.0s | 101.5 | 64.2 |
| `sd-span` | 12.9s | 6.3s | 3.5s | 85.2 | 53.9 |
| `toon` | 22.2s | 7.5s | 11.6s | 26.1 | 16.5 |
| `sd-hq` | 40.8s | 8.6s | 28.9s | 10.4 | 6.6 |

「SR fps」は **SR呼び出し回数 ÷ 処理秒** です。dedup が効くので出力fpsより小さくなります
（10秒clipでは source 241枚に対し SR実行 191回）。第3章の「SR単体」とは別の量です。

### 旧実装そのものと突き合わせる

上の表の `anime` は**旧実装の重みを vup に載せた物**で、旧実装そのものではありません。
旧実装（`realesrgan-ncnn-vulkan-v0.2.0-windows/movie_upscale.py`＝全frameをJPEG
qscale 4 へ展開 → 4分割して `realesrgan-ncnn-vulkan.exe` を4並列 → libsvtav1 で再encode）
を同じ素材に掛けた実測が次です。各2回走らせて速い方。

| 素材 | 旧実装 | vup既定（`sd-fast`＋TensorRT） | 倍率 |
|---|---|---|---|
| `テスト10秒.mp4` | 11.0s | 7.2s | **1.5倍** |
| `テスト60秒.mp4` | 76.2s | 11.0s | **6.9倍** |
| `サンプル.mp4`（全長16分34秒） | 18分45秒 | 1分13秒 | **15.4倍** |

60秒での旧実装の内訳は、抽出2秒 ＋ 音声1秒 ＋ アップスケール41秒 ＋ 再構成28秒です。
**旧実装は尺に対してほぼ線形（23.6〜27.4 fps）**なのに対し、vup は起動3.2秒が固定でかかるため、
**短いclipほど旧実装が有利に見えます。** 10秒での1.5倍という数字は vup の起動費用であって、
処理能力の差ではありません。

なお旧実装の出力は、この素材でも**映像だけ4倍速**でした（2.1 と同じ症状。出力fpsに
`r_frame_rate`＝119.88 を使うため）。ffprobe の format の尺は音声に引きずられて正常に
見えるので、stream 別に見る必要があります。

| 素材 | 旧実装の出力（映像stream） | 同（音声stream） |
|---|---|---|
| `テスト10秒.mp4` | 2.510秒 | 10.026秒 |
| `テスト60秒.mp4` | 15.015秒 | 60.010秒 |

### 10秒は短すぎる

同じ条件（`sd-fast` ＋ TensorRT bs2）を尺だけ変えて測ると、
**10秒clipは処理速度を22%低く見せます。**

| 素材 | 起動 | 処理 | 出力fps |
|---|---|---|---|
| `テスト10秒.mp4` | 3.2s | 1.10s | 277.2 |
| `テスト60秒.mp4` | 3.1s | 5.10s | **356.1** |

起動は尺によらず一定（3.1〜3.2秒）なので、10秒では**総時間の76%が起動**になります。
処理時間そのものも1秒しかなく、thread と encoder の立ち上がりが相対的に大きく出ます。

**10秒clipは条件どうしの相対比較には使えますが、絶対速度の根拠には使えません。**
速度を数字で言う時は60秒以上で測ってください。

## 13. 実写modelでも同じ手が効くか

素材 `実写.mp4`（1280x720 / 14.86秒 / 445 frame）。encoder は本番既定
`-preset p4 -cq 24`、背景sm 12%以下を待って測定（実測時 1〜8%）。

| 条件 | 出力 | torch.compile | TensorRT bs2 | 伸び |
|---|---|---|---|---|
| `photo` x2 | 2560x1440 | 17.9 fps | **35.0 fps** | **1.96倍** |
| `photo` x4 | 5120x2880 | 16.0 fps | **30.3 fps** | **1.89倍** |
| `photo-hq` x2 | 2560x1440 | 1.1 fps | 1.5 fps | 1.36倍 |

（`photo-hq` は遅すぎるので先頭3秒だけ。fpsは出力frame/処理秒）

### 効く物と効かない物

**model に依らず既に効いている物**: 中間JPEGの廃止とpipe直結、PTSからの出力fps決定、
encoder `-preset p4`、nv12出力。これらは実写でもそのまま効いています。

**TensorRT は効きます**が、伸びは model の重さで変わります。`photo`（Compact 1.20M）で
1.9倍なのに対し、`photo-hq`（RRDB 23block 16.7M）は1.36倍止まりです。

**dedup はほぼ効きません。** SR実行は 445枚中 435回（1.02倍削減）で、anime素材の
1.45倍削減とは別物です。カメラのnoiseとgrainで完全に同じframeが存在しないためで、
実写ではこの手は当てになりません。

**model の差し替えという手が使えません。** anime では `sd`(0.60M) → `sd-fast`(0.30M) で
品質を保ったまま1.6倍稼げましたが、実写側で登録しているのは `photo`(1.20M) と
`photo-hq`(16.7M) の2つだけで、`photo` が既に軽い方です。

### TensorRT engine の初回costと容量

engine は (重み, 入力解像度, 倍率, batch, 画素形式) ごとに1つ作られ、初回だけ build が入ります。

| engine | build | 容量 |
|---|---|---|
| `photo` x2 (1280x720) | 66.8s | 2.6GB |
| `photo` x4 (1280x720) | 81.0s | 3.6GB |
| `photo-hq` x2 (1280x720) | 138.5s | 402MB |

2回目以降の起動は4.2秒です（cache hit）。今回の測定で `trt_engines/` は 9.0GB に
なりました。**解像度が変わるたびに作り直しになる**ので、素材の解像度が揃わない用途では
容量に注意してください。

### 旧実装との比較（実写）

旧実装の実写は `realesrgan-x4plus`（＝`photo-hq`）の x4 でした。同じ素材で突き合わせます。

| 実装 | model | 出力 | 総時間 | 旧実装比 |
|---|---|---|---|---|
| 旧実装（ncnn 4並列 + 中間JPEG + libsvtav1） | `realesrgan-x4plus` 16.7M | 5120x2880 | **14分14秒** | 1.0 |
| vup（同じ重み） | `photo-hq` x4 | 5120x2880 | 約5分18秒※ | 2.7倍 |
| vup | `photo` x4 | 5120x2880 | **21.7秒** | 39倍 |
| vup（`4_実写_x2.bat`） | `photo` x2 | 2560x1440 | **20.2秒** | 42倍 |

※ engine cache後の推定（実測は初回buildを含む450.1秒、処理305.8秒）。他はcache後の実測。
旧実装の内訳は 抽出1秒 ＋ 音声0秒 ＋ **アップスケール13分9秒** ＋ 再構成1分2秒 です。

**同じ重みどうしでは2.7倍**しか変わりません。anime（テスト60秒で6.9倍、全長で15.4倍）と
差が付くのは、実写では dedup が効かず、SR自体が重くて中間JPEGの無駄が相対的に小さいためです。
39〜42倍はmodelを軽い方へ替えた効果であって、pipelineの差ではありません。

### `photo` は x4 model なので x2 指定でも計算量が落ちない

`photo` は realesr-general-x4v3（x4）です。vup は model 倍率で推論してから縮小するため、
`--scale 2` にしても **SR の計算量は x4 のまま**です。上の表で
x2 が 35.0 fps、x4 が 30.3 fps とほとんど変わらないのがその証拠で、差は encoder だけです。

実写を x2 で使うなら、**native x2 の実写向け model** に替えるのが最も効きます
（`--model <path.pth>` で重みを直接渡せます）。

### 試した native x2: `2xParimgCompact`（不採用）

OpenModelDB の `2xParimgCompact`（Compact 0.60M、native x2、実写向け）を測りました。

| | 出力fps torch | TensorRT | engine容量 | 鮮鋭度(frame12/292) | lanczos差 |
|---|---|---|---|---|---|
| `photo` x2 | 17.9 | 35.0 | 2.6GB | 206 / 126 | 4.02 / 4.13 |
| `2xParimgCompact` x2 | **34.8** | **68.2** | 1.49GB | **35 / 22** | 5.41 / 4.66 |

**速度は狙いどおり2倍**になりました（x4で計算して縮小する無駄が消えるため）。
しかし**品質が使い物になりません**。鮮鋭度は lanczos（24/21）とほぼ同じで解像感が上がらず、
それでいて lanczos差は `photo` より大きい＝**絵を変えているのに良くなっていない**状態です。
実際の絵は色が抜けて灰色寄りになります。

channel順（BGR/RGB）の取り違えを疑って両方で試しましたが、色差は4.86と4.88でほぼ同じ
（`photo` は2.50/2.14）だったので、入れ替えの問題ではありません。この重みは
Microsoft ImagePairs（実カメラの対）で学習されており、その組の色味まで学んでいると見られます。

**native x2 という方向は正しく、この重みが外れ**です。次の候補は
`2xNomosUni_compact_multijpg`（Compact x2、jpg劣化向け）や
`2xBHI_small_realplksr`（RealPLKSR small x2）です。

## 14. PTSの丸めで source frame を取りこぼしていた（修正済み）

実写の品質比較で絵を突き合わせている最中に、`build_schedule` が
**同じ時刻の判定で1つ前の source frame を選ぶ**不具合が見つかりました。

### 原因

`read_pts` は ffprobe の `pts_time` を読んでいましたが、これは**小数6桁に丸めた値**です。
30fpsなら真値 1/30 = 0.0333333… に対し `0.033333` が返り、出力時刻 `k * den/num` との差が
**±3.3e-7** 出ます。`build_schedule` は

```python
idx = np.searchsorted(pts, t, side="right") - 1
```

と等号ぎりぎりで引くため、`pts[k]` が `t[k]` より 3.3e-7 でも大きいと1つ前を選びます。

### 影響

出力に一度も現れない source frame が出ます。**`サンプル.mp4`（全長）では 1,175枚（4.8%）**が
捨てられ、代わりに別の frame が2回出ていました。24,279枚から29,819枚を作る（増やす）
処理なので、本来1枚も落ちてはいけません。

| 素材 | 修正前の未使用source frame | 修正後 |
|---|---|---|
| `サンプル.mp4`（全長） | **1,175枚** | **0枚** |
| `テスト60秒.mp4` | 0枚 | 0枚 |
| `実写.mp4` | 9枚 | 1枚（末尾のみ） |

### 修正

`pts_time`（6桁丸め）ではなく **time_base単位の整数 `pts`** を読み、秒はこちらで計算します。
その上で、出力時刻と source PTS が別々の有理数から作られる以上 最下位桁は食い違うため、
`PTS_EPS = 1e-6` の許容を持たせて比較します（240fps の frame間隔 4.2e-3 より桁違いに小さい）。

```python
idx = np.searchsorted(pts, t + PTS_EPS, side="right") - 1
```

### 「1 frame 遅れている」は誤りだった

当初この件を「vupの出力が原本より1 frame 遅れ、33msの音ズレが出る」と報告しましたが、
**これは誤りです。** 比較の基準に旧実装とlanczosの frame番号を使ったのが原因で、
frame番号での突き合わせは source が完全なCFRでない限り成立しません
（`実写.mp4` は50 frameごとに1回 0.035秒の間隔があり、平均29.97fpsです）。

保持則（その時刻に原本が表示しているのは pts <= T の最後の frame）で照合し直すと:

| 時刻 | 原本が表示中のframe | 修正後のvup | 旧実装 |
|---|---|---|---|
| 1.0s | 29 | **29** | 30（+1） |
| 5.0s | 149 | **149** | 150（+1） |
| 11.0s | 329 | **329** | 330（+1） |
| 14.0s | 419 | **419** | 420（+1） |

**vupは修正前も修正後も時刻が正しく**、1 frame 先走っているのは旧実装の方でした。
旧実装は source の PTS を見ずに frame を 1:1 で詰め直すため、VFR寄りの素材で
表示時刻がずれます。音ズレの記述も取り消します。

## 15. dynamic shape engine（`--trt-dynamic`）

engine が解像度ごとに増える問題への対策として、入力の高さ・幅を可変にした engine を
1本だけ作る経路を足しました。範囲は `trt_backend.py` の
`DYN_MIN`(256x144) / `DYN_OPT`(1280x720) / `DYN_MAX`(1920x1088) です。

### 結果

| | 固定形状（従来） | 可変形状（`--trt-dynamic`） |
|---|---|---|
| engine容量 `photo` x2 @1280x720 | 2,608MB | **3.1MB** |
| engine容量 `sd-fast` x2 @720x480 | 534MB | **1.2MB** |
| build | **解像度ごとに** 54〜74秒 | **1回だけ** 53〜72秒 |
| 速度 `photo` x2 @1280x720（opt） | 35.0 fps | **36.1 fps**（同等） |
| 速度 `photo` x2 @960x540（optの外） | 65.1 fps | 62.0 fps（−4.8%） |
| 速度 `sd-fast` x2 @720x480（optの外） | 381.5 fps | 376.5 fps（−1.3%） |

**容量が3桁減り、速度はほぼ変わりません。** opt から外れた解像度で数%落ちますが、
torch（`--no-trt`、960x540で33.4 fps）に対しては可変形状でも1.86倍あります。

### 出力の一致

`photo` x2 は固定形状と**出力fileがbyte単位で完全一致**しました。
`sd-fast` x2 は tactic の選び方が変わるぶん fp16 の丸めが動き、
平均0.37〜0.93階調・中央値0〜1・8階調を超える画素は0.001〜0.13%の差が出ます。
目で見て判る差ではありませんが、bit一致ではありません。

### 副産物: engine が異常に大きかった理由

「1.2Mの `photo` が2.6GB、16.7Mの `photo-hq` が402MB」という逆転は、**固定形状の build が
解像度に比例した定数を engine へ焼き込んでいた**ためと判りました。同じ model・同じ解像度で
可変形状にすると3.1MBまで落ちます。paramではなく、固定形状であることが容量の主因です。

### 既定にするか

上限やLRUを作り込むより、可変形状を既定にする方が筋が良いと考えます。
代償は opt から外れた解像度での1〜5%で、`trt_engines/` は14GBから数MBになります。
**未決**です。
