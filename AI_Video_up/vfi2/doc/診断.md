## 0. 結論

**素直な x2 は、手を出せている区間で何も変えていません。** 会話場面
(B_talk)の位置ずれ `lag_px` は **2.90px → 2.74px(-5.5%)**。同じ区間を
絵の列へ張り直すと **1.22px(-58%)** になります。x2 が効かないのは model が
弱いからではなく、**中間 frame の置き場所が間違っている**からです。

**中間 frame の 81.8%(B_talk)・67.7%(C_act)が「同じ絵と同じ絵の間」**で、
model を呼ぶまでもない複製です。cut 判定の巻き添えまで足すと、複製で
埋まる中間 frame は B_talk 82.6%・C_act 71.0%・A_op 37.0% になります。

**増えた絵は 20.9ms しか映りません。** x2 後の保持長は
**1 frame(20.9ms)が 134枚、5 frame(104.3ms)が 85枚の二極**で、中間の長さが
空洞です。1/4 速に伸ばして並べ、目でも確かめました(6章)。

**指標の選び方だけで結論が逆になります。** 同じ B_talk の同じ2本を測って、
`絵/秒` は 4.4 → 8.6(+95%)、`step_p95_px` は 7.77 → 4.25px(-45%)と
「効いた」と言い、`new_pct` 18.4% → 17.9%、`lag_px`、`step_cv` は
「変わらない」と言います。しかも **`step_p95_px` は model を使わない
単純な frame 複製で 7.77 → 0.34px と更に「良く」なります**(情報は 1bit も
増えていないのに)。判定に使えるのは `lag_px` だけです。

**その `lag_px` も、全区間の平均では動きません。** B_talk は尺の **53.5%**、
C_act は **33.9%** が「意図的に止めてある絵」で、そこは触らないのが正解です。
区間を分けずに平均すると 6.47 → 5.92px(-8.5%)にしか見えません。
**指標は必ず「手を出した区間」と「封じた区間」に分けて出します。**

**出力 fps は素材 fps の整数倍にすべきです。** 23.976fps を 60fps へ
載せると、絵の切り替わりが出力 frame の内側に落ち、**A_op では尺の 17.4% で
「もう切り替わっているはずの前の絵」が画面に出ます**(judder)。また
47.952fps では絵1枚につき1枚、素材の絵そのものを出力できるのに、60fps では
それが 0.2% になります。**整数倍(71.928 / 119.88)にすると古い絵を出す時間が
0% になり、`lag_px` は A_op で 60絵 18.10 → 72絵 12.95(-28%)、
120絵 15.42 → 120整絵 12.48(-19%)まで下がります。119.88fps が3本とも
最良でした**(3.10)。cut が1 frame 遅れる件(6.5)も同じ原因です。

**`lag_free` が 48絵 < 60絵 なのは 48 が良いからではありません。** 48絵 だけが
持つ「無料の正解 frame」が作った見かけで、**両方が model の絵を出している
時刻だけで比べると 3本とも 60絵 が勝ちます**(A_op 19.74→17.31、
C_act 4.20→3.76、B_talk 1.31→1.22)。120絵 が 60絵 より良いのも本物です(3.9)。

**「動きが大きい所にこそ掛けたい」が効かない理由は、model の性能ではなく
「等速の仮定」でした。** model は tau=0.5 で D0 と D2 のちょうど中間を作りますが、
**A_op では絵の 72% が D0 か D2 のどちらかに張り付いています**(B_talk は 31%)。
非等速そのものは A_op の全帯で起きており、**大変位の帯だけが壊れて見えるのは
誤差が「ずれ × 変位」だから**です(64-128px で 42px、指標の雑音の下限の 3倍)。
**新しい model を待っても直りません。**ただし tau を直して効くのは
**素材が素直な所(B_talk 型)だけ**で、A_op の大変位は tau を直しても
直りません(変位を固定した偏相関が B_talk +0.632 対 A_op +0.132)。
非等速が決めるのは **「model を使う価値があるか」**で、位置誤差
(ずれ × 変位)が **11.5px** を超えると model は blend に負けます(7章)。

**その調査で実装の bug を1つ見つけ、主担当が修正しました。** `lib.scdet` が
自分で生成した scd file では **cut の位置が 1 frame 遅れて**いました。
C_act の絵は 263 → 257 枚になり、試験集合の 128px超は 7組 → 3組
(4組は本当は cut)、5章の `mad>18` の見逃しは 11 → 0 になりました(7.6)。
**本書の C_act の数値はすべて修正後に測り直した物です。**

## 2. 素直な x2 が何を変えて、何を変えなかったか

現行実装と同じ規則で組みました(`d2_x2.py`)。出力 frame 2i は素材 frame i、
2i+1 は box4 < 16 なら複製、mad > 18 なら複製、それ以外は model の tau=0.5。

### 2.1 中間 frame のうち、複製にしかならない割合

| clip | 中間 frame | model 呼び出し | 静止で複製 | cut 判定で複製 | 静止だけの複製率 | 複製の合計 |
|---|---|---|---|---|---|---|
| A_op | 719 | 453 | 71 | 195 | 9.9% | **37.0%** |
| C_act | 718 | 208 | 486 | 24 | 67.7% | **71.0%** |
| B_talk | 718 | 125 | 587 | 6 | 81.8% | **82.6%** |

B_talk では 718枚の中間 frame のうち **593枚がただの複製**です。
「x2 にした」と言いながら、実際に絵が増えたのは 125枚だけです。

A_op は静止が 9.9% しか無いのに複製が 37.0% あります。差の 195枚は
cut 判定(mad > 18)の巻き添えで、**そのうち 158枚は cut ではありません**
(5章)。

### 2.2 同じ2本を測って、指標ごとに結論が逆になる

B_talk の `out/B_talk_元.mp4` と `out/B_talk_x2素直.mp4` を測った値です。

| 指標 | 元 24fps | x2素直 48fps | 変化 | この指標が言う事 |
|---|---|---|---|---|
| 絵/秒 | 4.4 | 8.6 | **+95%** | 倍になった |
| `step_p95_px`(跳び幅) | 7.77px | 4.25px | **-45%** | 跳びが半分になった |
| 保持 p50 | 125.1ms | 20.9ms | **-83%** | 6倍こまかくなった |
| `new_pct`(新規絵率) | 18.4% | 17.9% | -0.5pt | **増えていない** |
| `step_cv`(跳びのばらつき) | 4.03 | 4.01 | -0.5% | **変わらない** |
| `lag_px` 全区間 | 6.47px | 6.43px | -0.6% | **変わらない** |
| `lag_px` 手を出した区間 | 2.90px | 2.74px | -5.5% | **ほぼ変わらない** |

`絵/秒` が倍になるのに `new_pct` が増えないのは矛盾ではありません。
`new_pct` = 絵の枚数 / 出力 frame 数で、**分母も一緒に倍になった**だけです。
つまり `絵/秒` が言っているのは「frame rate を上げた」であって、
「絵が増えた」ではありません。

### 2.3 保持時間の二極化

`out/*.mp4` を box4 >= 16 で数え直した保持長です。

| 出力 | 絵 | 最多 | 次点 | 3位 | 保持 p50 | 保持 p90 |
|---|---|---|---|---|---|---|
| 元 24fps | 132 | **3 frame ×86**(125ms) | 2 frame ×22 | 1 frame ×10 | 125.1ms | 162.7ms |
| x2素直 48fps | 257 | **1 frame ×134**(20.9ms) | **5 frame ×85**(104.3ms) | 3 frame ×21 | 20.9ms | 104.3ms |
| 60絵 60fps | 758 | **1 frame ×696**(16.7ms) | 2 frame ×37 | 3 frame ×11 | 16.7ms | 16.7ms |

x2素直 では **2 frame 保持が 1枚、4 frame 保持が 1枚**しかありません。
分布の真ん中が空洞です。元の 3コマ打ちが 5 frame(104.3ms)へ引き伸ばされ、
その隙間に 1 frame(20.9ms)の中間が1枚だけ挟まる形になっています。
**52.1% の絵が 20.9ms しか映りません。**

60絵(絵の列へ張り直した 60fps)では 91.8% が 1 frame 保持で、p50 も p90 も
16.7ms です。**保持長が一様になっています。**

なお主担当が 480x270 の粗い判定で測った `lead_holdlen` の記録
(元 3 frame ×86、x2 1 frame ×134 / 5 frame ×85)と、上の原寸 box4 の
数え直しは完全に一致しました。判定の解像度には依存しない現象です。

## 3. 滑らかさ metric の設計

### 3.1 前提 — 何を「滑らかさ」とみなすか

anime の絵は等間隔に並んでいません。1枚が k frame 保持され、次へ飛びます。
人が「カクつく」と言うのは **絵が動くべき時刻に動いていない**状態で、
これは frame 数ではなく「時間あたりの位置のずれ」で測るのが正しい。

作画された絵 D_a(時刻 t_a)と D_b(時刻 t_b)の間では被写体が連続に動いた、
と読みます。すると時刻 t に画面へ出ているべき絵は tau=(t-t_a)/(t_b-t_a) の
中間絵であり、実際に出ている絵との差が **そのまま位置の誤差(px)** です。

tau は frame の**表示区間の中央**(PHASE=0.5)で採ります。先頭で採ると
標本の少ない低 fps ほど誤差が過小に出て、**24fps 1コマ打ちの素材が
lag=0 になってしまいました**(初版で実際に起きました)。

### 3.2 主指標 `lag_px`

出力 frame ごとに `|| flow(D_a → 出力frame) - tau * flow(D_a → D_b) ||` の
画素 p95 を取り、全出力 frame で平均した値。単位は原寸 px。0 が完璧です。

**採った理由。** frame rate にも出力 frame 数にも直接は依存せず、
「絵が正しい位置に居るか」だけを見るためです。frame を複製しても
絵の位置は変わらないので、複製では下がりません(3.6 で実測)。

画素方向は p95 で集約します。動いているのは画面の一部なので、平均だと
静止した背景に薄められます。

**同時に出す `lag_rel`** は `lag_px / 区間の変位` です。素材そのものを
測ると 3本とも **0.500 / 0.500 / 0.497** になりました。区間の中央で測れば
保持中の平均遅れは変位のちょうど半分になるはずで、**式が意図通り動いている
事の検算**になっています。

### 3.3 副指標 `step_px`

隣接する出力 frame 間の変位 p95(中央値と p95 の両方を出します)。
1枚あたりの跳び幅で、24fps 特有のストロボ感に対応します。

**`lag_px` と分けなければならない理由がここです。**

- `lag_px` は**保持の長さ**で決まります。frame rate を上げても、同じ絵を
  複製して埋めるだけなら減りません。
- `step_px` は **frame rate に反比例**します。frame を増やせば、
  1枚あたりの跳びは機械的に小さくなります。

この非対称が「素直な x2 が効かない」ことの説明そのものです。x2 は
frame rate を倍にする操作なので `step_px` は必ず下がりますが、
絵の位置は動かないので `lag_px` は下がりません。**1つの数字に混ぜると
この2つが打ち消し合って、何も判らなくなります。**

### 3.4 検算(`d8_selftest.py`)

図形では検算になりません。texture が無いと Farneback は輪郭でしか flow を
立てられず、実測が理論の 0.4〜2倍に振れました(初版で確認)。
**実際の絵(C_act)を既知の画素数だけ平行移動**させて測り直しました。

| ずらし量 | p90 | p95 | p99 | p99.9 |
|---|---|---|---|---|
| 4px | 4.0 | **4.0** | 4.0 | 4.0 |
| 8px | 8.0 | **8.0** | 8.0 | 8.1 |
| 16px | 15.9 | **16.0** | 16.0 | 16.2 |
| 32px | 31.8 | **32.0** | 32.0 | 34.1 |
| 64px | 63.5 | **63.9** | 64.0 | 64.1 |

p95 は 4px から 64px までずらし量ちょうどを返します。集約に p95 を選んだ
根拠です(p99.9 は 32px で 34.1 と外れ始めます)。

位置ずれの式そのものの検算(区間の変位 32.0px)。

| tau | 保持したまま(実測) | 同(理論 = tau×span) | 正しい位置に置く(実測) | 同(理論) |
|---|---|---|---|---|
| 0.25 | 8.0px | 8.0px | 4.08px | 0 |
| 0.50 | 16.0px | 16.0px | 4.96px | 0 |
| 0.75 | 24.0px | 24.0px | 3.00px | 0 |

保持の lag は理論値に厳密一致します。ただし **正しい位置に置いても
lag は区間の変位の 15.5% までしか下がりません。** これが Farneback の
局所誤差による**この指標の下限**で、これ以下の差は読めません。

### 3.5 3本で意図通り区別できたか

素材そのものを測った値です。

| clip | `lag_px` | `step_px` p50 | `step_p95_px` | この2つが言っている事 |
|---|---|---|---|---|
| A_op | 21.81 | 30.24 | 114.63 | 毎 frame 大きく跳ぶ。lag も step も大 = 1コマ打ちの大変位 |
| C_act | 6.78 | 0.19 | 53.03 | 中央は止まっているのに p95 は大 = 止まっては跳ぶ |
| B_talk | 6.38 | 0.02 | 7.71 | どちらも小 = ほとんど動いていない |

特に **C_act の「p50 は 0.19px なのに p95 は 53.03px」** は「止まっては跳ぶ」を
1つの clip の中で捉えた形で、平均だけを出す指標では出てこない値です。

**`lag_px` だけでは C_act と B_talk を区別できません**(6.78 対 6.38)。
C_act は絵と絵の変位が中央 5.0px と小さく、たまに大きく跳ぶ形なので、
時間平均の `lag_px` は小さく出ます。**区別しているのは `step_p95_px`**
(53.03 対 7.71)です。**主指標だけを見るなという事の実例**なので残します。
(cut 位置の修正(7.6)の前は C_act の `lag_px` が 20.86 と出ていました。
cut を跨ぐ絵の組が区間に混ざり、変位 275px のような値が参照に入っていた
ためで、**修正前の C_act の `lag_px` はすべて過大でした。**)

### 3.6 採らなかった指標と、その理由

#### `step_cv`(跳び幅の変動係数 = std/mean)— 採りません

「保持→跳躍の型ほど大きくなるはず」という狙いで入れましたが、
**3条件を通してほとんど動かず、判断に使えませんでした。**

| clip | 元 24fps | x2素直 48fps | 60絵 60fps |
|---|---|---|---|
| B_talk | 4.03 | 4.01 | 3.49 |
| C_act | 2.61 | 2.80 | 3.57 |
| A_op | 0.99 | 1.10 | 1.51 |

分解すると理由がはっきりします(B_talk)。

| | 元 24fps | x2素直 48fps | 60絵 60fps |
|---|---|---|---|
| step 平均 | 1.079px | 0.666px | 0.553px |
| step 標準偏差 | 4.349px | 2.672px | 1.931px |
| `step_cv` = 標準偏差/平均 | 4.03 | 4.01 | 3.49 |
| step < 0.5px の frame | 90.3% | 86.4% | 79.9% |

**平均と標準偏差が同じ割合で下がるので、比を取ると消えます。**
cv は無次元なので、**跳び幅が px で小さくなったという肝心の事実を
原理的に見られません**。加えて分母の平均は「step がほぼ 0 の frame」が
8〜9割を占めることで決まっており、静止区間の多い素材ほど分母が小さく、
比が不安定になります。C_act と A_op では **frame rate を上げるほど
cv が大きくなり、良し悪しの向きすら逆**になりました。

決定的なのは次です。**model を一切使わず frame を単純複製しただけ**の
48fps では何が起きるか。複製の組の変位は厳密に 0 なので、素材で実測した
step の列に同数の 0 を挟むだけで、正確な値が出せます。

| clip | `step_p95_px` 元 → 単純複製 | `step_cv` 元 → 単純複製 |
|---|---|---|
| B_talk | 7.77 → **0.34** | 4.03 → **5.79** |
| C_act | 53.37 → **29.99** | 2.61 → **3.82** |
| A_op | 114.60 → **90.99** | 0.99 → **1.72** |

情報は 1bit も増えていないのに `step_p95_px` は 96% も「改善」し、
`step_cv` は「悪化」します。**`step_px` は単独では判定に使えず
(だから副指標)、`step_cv` は向きが定まらないので採りません。**
同じ操作で `lag_px` は動きません。これが `lag_px` を主指標にした理由です。

#### `new_pct`(新規絵率)— 採りますが、診断の補助まで

分母が出力 frame 数なので、frame rate を上げると絵が増えても値が動きません
(B_talk 18.4% → 17.9%)。**「増えた分の絵が、増えた分の frame をきちんと
埋めているか」を見る指標**としては有効です。素直な x2 で横ばいだという事は、
新しい絵が古い絵と同じ持ち時間を得られていない事を意味します。
主指標にはしません。

#### `drawing_rate`(絵/秒)— 採りますが、主指標にはしません

`絵/秒 4.4 → 8.6` は 2.3 節の二極化を隠します。8.6枚のうち半分は 20.9ms
しか映りません。**枚数だけでは「どれだけの時間映ったか」が落ちます。**
`hold_ms_p50` / `hold_ms_p95` と必ず並べて読みます。

#### PSNR / LPIPS / GMSD — この用途には使えません

時刻を張り直した出力 frame には対応する本物が存在しないので、
そもそも計算できません。正解を作れる形に問題を変形した試験
(絵を1枚おきに間引いて復元する)では有効で、`時刻張り直し.md` 5章で
そちらを使っています。**用途が違うので、どちらも捨てません。**

### 3.7 `lag_px` 自身の弱点と、その扱い

**`lag_px` は「意図的に止めてある絵」を遅れとして数えてしまいます。**
96 frame 保持された絵は、その区間の平均で変位の半分ぶん「遅れている」と
計上されます。しかしそこは補間してはいけない場所で、下げるべき値では
ありません。

B_talk では出力 frame の **53.5%**、C_act では **49.4%** がこの
「封じる区間」(保持 9 frame 以上 / cut を跨ぐ / 変位 64px 超)に属します。
**全区間の平均を取ると、指標は動きようがありません。**

そこで `d9_metric.py` で区間を分けて測り直しました(`out/*.mp4` の実測)。

**手を出した区間だけの `lag_px`(px。小さいほど良い)**

| B_talk | 53.5% | 2.90 | 2.74 (**-5.5%**) | **1.22 (-58%)** | 1.35 (-53%) | 1.15 (-60%) |
| C_act | 37.8% | 6.68 | 5.65 (-15.4%) | **3.95 (-41%)** | 5.40 (-19%) | 3.79 (-43%) |

「封じた区間の割合」は出力 frame 数に対する割合で、fps によって
±0.3pt ほど動きます(A_op は 24/48fps で 25.6%、60/120fps で 25.5〜25.9%)。

**この表の 48絵 と 60絵 を直接比べないでください。** 48絵 だけが「素材の絵を
そのまま出す frame」を持っており、それが 3本の差の全部を作っています。
公平な比べ方と、その結果(3本とも 60絵 が勝つ)は 3.9 にあります。

### 3.8 出力 fps が素材 fps の整数倍でないと、古い絵を出す時間ができる

3.7 の表で **A_op の 60絵 が 13.05 → 17.84px(+37%)と悪化**しています。
原因を追い、**当初これを指標の欠陥と判断しましたが、誤りでした。**
測り直した結果(3.9)、**実在する欠陥で、しかも実装で直せる物**でした。
経緯ごと残します。

`lag_px` が最も悪化した区間を機械的に並べると、3本とも **保持 1〜2 frame の
区間ばかり**が上位に来ます。共通するのは、**出力 frame の表示区間の内側で
絵が切り替わる**という一点です。以下これを **straddle** と呼びます。

出力 frame は `[k/F, (k+1)/F)` の間ずっと同じ画像を出します。絵の切り替わりが
その内側の時刻に来ると、renderer は frame の先頭時刻で属する側を出すしか
なく、**切り替わりが最大で出力 frame 1枚ぶん遅れます。**

**出力 fps が素材 fps の整数倍なら straddle は起きません**(境界が重なる)。
23.976fps と 47.952fps は整数倍、60fps と 120fps は違います。

| clip | 条件 | straddle の frame 割合 | `lag_px`(frame平均) | straddle を除く | straddle だけ |
|---|---|---|---|---|---|
| A_op | 元 23.976 | 0.0% | 13.05 | 13.05 | — |
| A_op | x2素直 47.952 | 0.0% | 13.84 | 13.84 | — |
| A_op | x2絵 47.952 | 0.0% | 13.53 | 13.53 | — |
| A_op | **60絵 60** | **34.6%** | 17.84 | 14.08 | 24.93 |
| A_op | 120絵 120 | 17.7% | 15.64 | 14.01 | 23.21 |
| C_act | 元 23.976 | 0.0% | 6.68 | 6.68 | — |
| C_act | x2絵 47.952 | 0.0% | 3.95 | 3.95 | — |
| C_act | **60絵 60** | **24.1%** | 5.40 | 3.65 | 10.91 |
| C_act | 120絵 120 | 12.0% | 3.79 | 3.42 | 6.53 |
| B_talk | 元 23.976 | 0.0% | 2.90 | 2.90 | — |
| B_talk | x2絵 47.952 | 0.0% | 1.22 | 1.22 | — |
| B_talk | **60絵 60** | **14.2%** | 1.35 | 1.19 | 2.29 |
| B_talk | 120絵 120 | 7.0% | 1.15 | 1.08 | 2.11 |

**当初の誤った読み。** 「metric は表示区間の中央で誤差を決めるので、この1枚に
切り替わりの全量を課している。実害は 16.7ms の遅れに過ぎないから、
A_op の悪化 4.79px のうち 3.76px(79%)は指標の欠陥だ」と書きました。
根拠は、指標が最悪と名指しした frame を拡大したら中間絵がきれいだった事(6.4)です。

**なぜ誤りか。** 拡大して見た frame は**切り替わりを跨いでいない frame**でした。
罰されているのは跨いでいる frame の方で、そちらは表示区間の後半で
**本当に前の絵を出し続けています**。時間で一様に測り直すと(3.9)、
「実際に古い絵が出ていた時間」だけを数えても値はほとんど変わりません。

| clip | 条件 | 時間平均 lag | 古い絵を出している時間 | その時間の lag | それ以外の lag |
|---|---|---|---|---|---|
| A_op | 60絵 | 18.10 | **17.4%** | 33.33 | 14.89 |
| A_op | 120絵 | 15.42 | 9.4% | 31.81 | 13.71 |
| C_act | 60絵 | 5.01 | 12.1% | 13.45 | 3.85 |
| C_act | 120絵 | 3.81 | 6.1% | 9.60 | 3.44 |
| B_talk | 60絵 | 1.36 | 7.7% | 3.28 | 1.20 |
| B_talk | 120絵 | 1.16 | 3.7% | 3.11 | 1.08 |

A_op では **尺の 17.4% で、画面に出ているのが「もう切り替わっているはずの
前の絵」**です。frame 数で平均しても(17.84)時間で平均しても(18.10)
同じ値になります。**指標は正しく、出力の側が古い絵を出しています。**
23.976fps を 60fps へ載せた時の判定ずれ、いわゆる judder そのものです。

**直すのは指標ではなく schedule です。** 出力時刻が絵の開始時刻の
半 frame 以内にある時、その出力時刻を絵の開始時刻へ吸着させれば消えます。
6.5 の「cut が出力 1 frame 遅れる」件と**同じ原因・同じ直し方**です。

### 3.9 出力 fps の違いを公平に比べる — 48絵 と 60絵

主担当から「`lag_free` が3本とも 48絵 < 60絵 なのは、47.952fps が素材 fps の
正確な2倍だから構造的に有利になっているのではないか」という指摘がありました。
**そのとおりでした。**

#### 何が有利になっているか

**47.952 = 23.976 × 2 なので、張り直した schedule は絵1枚につき正確に1枚、
出力時刻が絵の開始時刻に乗ります。**そこは tau=0 なので model を呼ばず、
**素材の絵をそのまま出します。** render の schedule 集計がそのまま示します。

| clip | 絵の枚数 | 48絵 が素材の絵を出した frame | 60絵 | 120絵 |
|---|---|---|---|---|
| A_op | 649 | **650** | 4 | 9 |
| C_act | 257 | **274** | 23 | 47 |
| B_talk | 132 | **133** | 4 | 8 |

metric から見ると、素材の絵は「本物」なので model の誤差が乗らず、
Farneback の雑音の下限(3.4 の 15.5%)も乗りません。**48絵 だけが
この「無料の正解 frame」を持っています。**

そして 48絵 の優位は、その割合と揃っています。

48絵 3.95px に対し 60絵 5.40px で、48絵 の方が 1.45px 良くなっています。
これは 48絵 が強くなったからではなく、**60絵 が 3.8 の judder で悪化した**
ためです(C_act の 60絵 は straddle frame が 24.1% あり、そこだけの lag は
10.91px)。下の「両方が生成 frame を出している時刻だけ」の対照では、
修正後も 60絵 が勝ちます(4.20 対 3.76)。

frame 数で平均するのをやめ、**250Hz の格子の各時刻で、その瞬間に画面へ

素材 frame に乗るかどうかは関係ありません。時間で一様に平均します。

まず **frame 平均と時間平均はほとんど一致しました。**重み付けの選び方は

| B_talk | 81.7% | 1.31 | **1.22** | **60絵** |

**3本とも順位が逆転します。** `lag_free` の「48絵 < 60絵」は、
48絵 だけが持つ無料の正解 frame が作っていた見かけでした。
**48 の方が良い、という読み方は取り下げます。**

主担当の副次的な疑い(120絵 が 60絵 より良いのは 120 が 60 の倍数だから)は
**当たりませんでした。** 60絵 も 120絵 も素材の絵を出す時間は 0.1〜0.2% で
条件が揃っており、両方が生成 frame を出している時刻(99.7〜99.8%)で比べても
120絵 が勝ちます(A_op 15.44 対 18.10、C_act 3.82 対 5.02、B_talk 1.16 対 1.36)。
**刻みが細かいほど古い絵を出す時間が減る、という 3.8 の話がそのまま効いています。**

#### 「60 を既定にする」への影響

**判断は変わりません。むしろ支持されます。**ただし条件が付きます。

- **model の絵どうしで比べれば 60 > 48、120 > 60 です。**目標 fps を上げる
  ほど良い、という 4章の話は成り立っています。
- **48 が持っている「無料の正解 frame」は、それ自体は本物の利点です。**
  雑音の下限(A_op で 3.90px)ぶんは指標が誇張していますが、
  素材の絵が画面に出ている間は model の誤差がゼロなのは事実で、
  **model の誤差が目に見える素材(A_op の二重像)では効きます。**
- **その利点は 60fps でも取れます。**3.8 の吸着(出力時刻が絵の開始時刻の
  半 frame 以内なら吸着させる)を入れれば、60fps でも絵1枚につき1枚は
  素材の絵そのものが出て、同時に古い絵を出す時間(A_op 17.4%)も消えます。
  **48 の利点と 60 の利点を両取りできます。**

**retime 側への申し送りは1つです。** 6.5 の cut の1 frame 遅れと、
3.8 の judder と、48 の無料の正解 frame は、**すべて同じ1つの実装で解決します**
— 出力時刻の絵の開始時刻への吸着。優先度は高いと考えます。

**なお、吸着を入れなくても「出力 fps を素材 fps の整数倍にする」だけで
同じ3つが同時に解決します。**実際に 71.928 と 119.88 を測りました(3.10)。
**この節の「60 を既定にする判断は変わりません」は、3.10 で撤回します。**

model を通らず素材のまま出ます(A_op は絵 649枚に対し 72絵 651 / 120整絵 653、
60絵 は 4、120絵 は 9。C_act は絵 257枚に対し 72絵 283 / 120整絵 301、
60絵 は 23、120絵 は 47)。

#### `lag_px`(時間で一様。手を出した区間のみ、px。小さいほど良い)

| clip | 元 | 48絵 | 60絵 | **72絵** | 120絵 | **120整絵** |
|---|---|---|---|---|---|---|
| B_talk | 2.90 | 1.24 | 1.36 | **1.13** | 1.16 | **1.05** |
| C_act | 6.65 | 4.02 | 5.01 | **3.58** | 3.81 | **3.32** |
| A_op | 13.04 | 13.61 | 18.10 | **12.95** | 15.42 | **12.48** |

**119.88fps が3本とも最良です。** そして 71.928fps が 60fps を3本とも
上回ります。A_op では **60絵 18.10 → 72絵 12.95(-28%)**、
**120絵 15.42 → 120整絵 12.48(-19%)** と大きく動きます。

**A_op で初めて「元(13.04)より良い条件」が出ました**(120整絵 12.48)。
3.7 の表で A_op がどの条件でも悪化していたのは、**素材の性質ではなく
出力 fps の選び方**が効いていた事になります。

#### 内訳 — どこから来た改善か

両方が model の絵を出している時刻だけで比べると、差はほとんど消えます。

| clip | 対照 | 対象時間 | 前 | 後 |
|---|---|---|---|---|
| B_talk | 60絵 → 72絵 | 87.8% | 1.24 | 1.18 |
| B_talk | 120絵 → 120整絵 | 92.7% | 1.09 | 1.09 |
| C_act | 60絵 → 72絵 | 79.8% | 3.91 | 3.83 |
| C_act | 120絵 → 120整絵 | 87.9% | 3.50 | 3.52 |
| A_op | 60絵 → 72絵 | 70.3% | 16.36 | 16.72 |
| A_op | 120絵 → 120整絵 | 82.2% | 14.52 | 14.64 |

**model の絵どうしでは、整数倍かどうかは効きません**(当然です。
どちらも同じ model で同じ tau の近くを作っています)。改善は全部、

1. **古い絵を出す時間が消えた事**(17.4% → 0%。実在の欠陥の除去)
2. **素材の絵そのものが映る時間が増えた事**(0.2% → 17.8〜29.7%)

の2つから来ています。**1 は文句なく本物です。**2 は、
3.9 に書いたとおり雑音の下限(A_op で 3.90px)ぶんは指標が誇張していますが、
**素材の絵が映っている間は model の誤差がゼロなのは事実**で、
model の誤差が目に見える素材(A_op の二重像、7章)では実質的な利点です。

#### 既定値への提案

**出力 fps は素材 fps の整数倍にすべきです。**ただし画面の refresh と
両立しない場合があるので、そのまま「119.88 にせよ」とは書きません。

| 目標 | 整数倍か | 画面と合うか | 評価 |
|---|---|---|---|
| 47.952 (x2) | ○ | 60Hz でも 120Hz でも割り切れない | 絵の時刻は正確。画面側で判定ずれ |
| **60** | **×** | 60Hz と完全一致 | **古い絵が 7.7〜17.4% の時間出る。今の既定** |
| 71.928 (x3) | ○ | どちらとも割り切れない | 絵の時刻は正確。画面側で判定ずれ |
| **119.88 (x5)** | **○** | **120Hz と 0.1% 違い** | **3本とも最良。1001 frame に1枚が重複表示(8.3秒に1回)** |
| 120 | × | 120Hz と完全一致 | 古い絵が 3.7〜9.4% の時間出る |

**120Hz の画面が前提なら 119.88 を推します。**8.3秒に1回、出力 frame が
1枚 8.3ms 余分に表示されるだけで、**尺の 9.4% で古い絵が出る 120fps より
明らかに軽い代価**です。

**60Hz の画面が前提なら、両立する選択肢は在りません。**23.976 の整数倍で
60 を割り切る値は存在しないためです。60 を採る場合は、
**3.8 の吸着(出力時刻が絵の開始時刻の半 frame 以内なら吸着させる)で
古い絵を出す時間を潰すのが唯一の手**です。吸着を入れれば、60fps でも
上の表の 1 と 2 の両方が取れます。

**`時刻張り直し.md` 3.6 の「60 を既定にする」は、見直しの余地があります。**
60 を選んだ理由は「60Hz の画面と揃う」でしたが、**その代価は
尺の 7.7〜17.4% で古い絵が出る事**で、これは測る前には見えていませんでした。
判断は retime 側にお任せしますが、材料としてこの表を渡します。

## 4. どこまで上げれば効果が出るか

`d3_targets.py`。絵の列に対して補間する前提で、目標 fps ごとに
「絵と絵の間を何等分することになるか」と「破綻域に落ちる割合」を出します。
model が跨ぐ変位は絵と絵の変位そのもので、**目標 fps を上げても変わりません**
(等分数が増えるだけです)。破綻の閾値は 32px を使っています
(`時刻張り直し.md` 3.5 の schedule 試験では最終的に 64px を採用したので、
下の `破綻域の生成frame` は広めに見積もった値です)。

| clip | 目標 fps | 等分数 平均 | 同 p50 | 同 p95 | model 呼び出し/秒 | 生成 frame の割合 | うち破綻域 | 出力 frame |
|---|---|---|---|---|---|---|---|---|
| A_op | 48 | 2.2 | 2.0 | 4.0 | 26 | 54.9% | 30.8% | 1440 |
| A_op | 60 | 2.8 | 2.5 | 5.0 | 38 | 64.0% | 35.8% | 1801 |
| A_op | 120 | 5.6 | 5.0 | 10.0 | 98 | 82.0% | 45.9% | 3603 |
| C_act | 48 | 5.6 | 2.0 | 6.0 | 39 | 82.1% | 13.3% | 1438 |
| C_act | 60 | 7.0 | 2.5 | 7.5 | 51 | 85.7% | 13.8% | 1799 |
| C_act | 120 | 14.0 | 5.0 | 15.0 | 111 | 92.9% | 15.0% | 3598 |
| B_talk | 48 | 10.9 | 6.0 | 25.6 | 44 | 90.8% | 13.0% | 1438 |
| B_talk | 60 | 13.6 | 7.5 | 32.0 | 56 | 92.7% | 13.3% | 1799 |
| B_talk | 120 | 27.3 | 15.0 | 64.1 | 116 | 96.3% | 13.8% | 3598 |

読み方は3つです。

**(a) B_talk は 48fps でも「絵と絵の間を平均 10.9 等分」になります。**
元が 4.4 絵/秒しか無いので、frame rate をいくら上げても等分数が増えるだけで、
1区間あたりの跨ぐ変位は変わりません。**48 と 60 と 120 の違いは
「同じ跨ぎを何枚で刻むか」だけ**です。3.7 の表で B_talk の 48絵(1.22px)と
120絵(1.15px)がほとんど同じなのは、この事の裏返しです。

**(b) 効果の上限を決めているのは破綻域の割合で、これは fps をどう選んでも
ほとんど動きません。** B_talk 13.0 → 13.8%、C_act 13.3 → 15.0%。
fps を上げても破綻域の比率は下がりません。

**(c) A_op は 48fps でも 30.8% が破綻域です。** 元が 21.6 絵/秒あるので
等分数は 2.2 しかなく、その2等分の中身が p50 36.4px の大変位です。
**A_op で上げるべき fps は存在しません。**

出力 frame のうち生成 frame が占める割合(B_talk 60fps で 92.7%)は、
実装が背負う計算量の見積もりでもあります。60fps を既定にした判断は
`時刻張り直し.md` 3.6 にあります。

## 5. cut 判定

`d7_cutgate.py`。現行 x2 の cut 判定は **mad(frame 間の平均絶対差) > 18**
だけを見ています。anime は閃光や white-out で mad が跳ねるので、
これだけでは cut でない所まで「cut」として複製に落ちます。

正解は ffmpeg scdet(score >= 10)を使いました。

| clip | scdet の cut | `mad>18` 発火 | 誤検出 | 誤検出率 | 見逃し |
|---|---|---|---|---|---|
| A_op | 37 | 195 | **158** | **81.0%** | 0 |
| C_act(修正後) | 13 | 24 | 11 | 45.8% | **0** |
| B_talk | 6 | 6 | 0 | 0.0% | 0 |

A_op では **195回のうち 158回が cut ではありません**。これが 2.1 の
「静止は 9.9% しか無いのに複製が 37.0%」の中身です。**A_op の中間 frame の
22%(158/719)が、cut でもないのに model を通らず複製になっています。**

C_act は cut 位置の修正後(7.6)で 24回のうち 11回が誤検出、見逃しは 0件です。
**修正前は誤検出 22・見逃し 11 と読めていました**が、それは mad の失敗では
なく正解側が 1 frame ずれていたためでした。

輝度分布の相関を足した `mad>18 かつ 相関<0.90` も試しました。

| clip | 発火 | 誤検出 | 見逃し |
|---|---|---|---|
| A_op | 42 | 16 | 11 |
| C_act(修正後) | 12 | 1 | 2 |
| B_talk | 1 | 0 | 5 |

誤検出は減りますが、**見逃しが 11件・5件と増えます**。cut を跨いで
補間すると2つの shot が溶け合うので、見逃しの方が代価が大きい。
**自前の閾値はどちらも採りません。scdet を使います**(`lib.cut_frames`)。

**C_act の行は cut 位置の修正後の値です(7.6)。** 修正前は誤検出 22・
見逃し 11 でしたが、原因は mad ではなく `lib.cut_frames` の off-by-one で、
**正解の側が 1 frame ずれていました**。主担当が `lib.py` を直しています。
A_op と B_talk は元から正しい位置でした。

**この比較の限界も書いておきます。** scdet を正解として扱っていますが、
scdet も完全ではありません。C_act では閃光を cut と判定している組が
あることが判っています(`時刻張り直し.md` 3.4)。上の「誤検出」の一部は
実は scdet 側の誤りかもしれません。それでも **A_op の 81.0% という
誤検出率は、その程度の揺れでは説明できない大きさ**です。

### 6.4 A_op(OP)— 目視だけでは結論を誤りました

二重像も滲みもなく、D_a と D_b の間の妥当な位置に居ます。画素でも確かめました
(出力 frame 301 は素材 120 から 12.2、素材 121 から 23.7 の距離で、

代表の窓(t=15.14-17.60s)の連続 frame(`results/目視_A_op_連続frame_0.png`)

**A_op について現時点で正しい言い方。**

3. **A_op は素材として補間の余地が無く、どの条件でも二重像が出ます。**

## 7. 64px を超える組は「そもそも何なのか」

speed 担当が flow の推定解像度を 1/4 まで落としても A_op の 64-128px 帯が
まったく動かない事を示しました(blend 0.2050 / model scale=1.0 0.2427 /
scale=0.5 0.2424 / scale=0.25 0.2444。小変位側は 0.0218 → 0.0314 と明確に
悪化するので、knob 自体は効いています)。**「受容野が足りないから追跡できない」
という説明は棄却されました。**

用意した仮説は3つでしたが、**答えは4つ目でした。**

  (a) model の性能不足        … 将来の model で直る
  (b) 素材に中間が存在しない  … どんな model でも当てられない
  (c) 絵の区切り方の誤り      … こちらの実装の問題
  **(d) model は絵と絵の間を等速と仮定しているが、anime の動きは等速でない**

**主因は (d) です。** model は tau=0.5 なら「D0 と D2 のちょうど中間の位置」を
作ります。ところが実際の D1 は **中間ではなく端に居ます**。A_op では
**絵の 65% が D0 か D2 のどちらかに張り付いて**おり、真ん中に居るのは 35% だけです。
model は正しく仕事をしていて、**狙う位置の指定が間違っています。**

(c) も実在し、そのうち1つは主担当が `lib.py` を直しました(7.6)。
(a) は最も小さく、(b) は A_op の粒子と閃光に限られます。

**この章の C_act の数値は、cut 位置の修正(7.6)の後に測り直した物です。**

### 7.1 測り方 — 進行率

判定に要るのは「真の D1 が D0 と D2 の間に居るか」です。被写体が
t_0→t_2 を等速で動いたなら、D0→D1 の変位は D0→D2 の変位の tau 倍のはずです。
この比を **進行率** と呼びます(`d14_bigspan.py`)。

    進行率 = median( flow(D0→D1)・flow(D0→D2) / |flow(D0→D2)|^2 )

大きさの比ではなく **D0→D2 の向きへの射影**で取ります。大きさだけだと、
別方向へ動いた場合まで「進んだ」と読んでしまいます。動いた画素
(|flow(D0→D2)| が上位 10%)だけで中央値を取ります。

    進行率 ≒ tau  … 中間として素直。model が当てられなければ (a)
    進行率 ≒ 0    … D1 は D0 のまま。変化は D1→D2 に在る
    進行率 ≒ 1    … D1 は既に D2。変化は D0→D1 に在る

### 7.2 進行率は中央値で読んではいけない — 分布が二極です

進行率の分布は二極(0 の山と 1 の山)で、その中央値は標本が少し入れ替わるだけで
大きく動きます。実際、A_op の全 3つ組で 0.364、そのうち flow が信用できる組
だけに絞ると 0.492 になりました。**同じ素材で 0.36 と 0.49 です。**
中央値ではなく **「端に何%居るか」** で読んでください。

その3倍を超える組を「偽の分割」と数えると、A_op の 64px以下で
**15/90(16.7%)**、128px超で 3/21 ありました。**そこでは tau の定義そのものが
成立していません**(D0 と D1 が同じ絵なら、真の tau は 0 です)。

閾値をいくつにすべきかは測っていません。判定基準(32 と 3倍)も
分布の形から私が置いたもので、人が付けた正解と突き合わせてはいません。

cut 位置を直した後の分類です(`d14_bigspan.classify`)。

### 7.7 結論と user への答え

**(d) が主因です。** model は等速を仮定して「中間」を作りますが、
**A_op では絵の 72% が D0 か D2 に張り付いています**(flow が信用できる組
だけでも 65%)。B_talk は 31% です。この差が、B_talk で張り直しが効いて
A_op で効かない事の中身です。

**ただし「大変位の帯が壊れるのは非等速のせい」とは言えません。**
7.8 で組ごとに検証したところ、変位を固定した偏相関は **B_talk +0.632 に対し
A_op +0.132** で、**非等速が効くのは素材が素直な所**でした。A_op の大変位帯を
決めているのは非等速ではなく、粒子・effect・遮蔽です。
非等速が決めるのは **「model を使う価値があるかどうか」**で、位置誤差
(ずれ × 変位)が **11.5px** を超えると model は blend に負けます(7.8)。

**(b) は A_op の 128px超に限られます。**吹雪・火の粉・光の粒は個々の粒に
対応が無く、閃光は動きですらありません。ここは model を変えても直りません。

**(a) は最も小さい**です。目視ではっきり model の失敗と言えたのは 2組で、
**いずれも進行率が端に寄っていた組**でした。進行率が tau と一致する組では
model は破綻していません。

**user への答え。**

「動きが大きい所にこそ掛けたい」に対しては:

- **model の性能不足ではありません。**新しい model を待っても直りません
- **素材に中間が無い訳でもありません**(粒子と閃光を除けば)。
  中間の絵は在ります。**ただし等速の位置には在りません**
- **tau の与え方を直すと効くのは、素材が素直な所です**(B_talk 型)。
  **A_op の大変位は tau を直しても直りません**(7.8 の偏相関 +0.132)。
  そこで効く手は「補間しない」だけです

**ただし、これは簡単ではありません。**正しい tau を知るには
**まさに今から作ろうとしている D1 がどこに居るか**を知る必要があります。
D0 と D2 だけからそれを当てられるかは、**測っていません。**
手掛かりはあります。`時刻張り直し.md` 3.1 の tau 掃引では、
**正解を見て最良の tau を選ぶと A_op の LPIPS が 0.14964 → 0.09302(-38%)**
まで下がります。**伸び代は大きい**ので、次に測る価値があるのはここです。

隣り合う3つ組の「ずれ」には相関があります(B_talk -0.46 / A_op -0.28)が、
**符号が負である事の解釈には注意が要ります。**隣り合う3つ組は絵を2枚
共有しているので、1枚の絵の位置がずれると隣同士で逆向きの誤差が出ます。
**この相関の一部は測り方の産物**で、予測できる事の証拠にはなりません。

### 7.8 仮説の検証 — 「位置誤差 ≒ |進行率 − tau| × 変位」

主担当から**「中間絵の位置誤差 ≒ |進行率 − tau| × 跨ぐ変位で、この積の方が
変位単独より品質をよく説明するのではないか」**という仮説を受けました。
組ごとに測って順位相関(Spearman)を取りました(`d17_easing.py`)。

試験集合の全組(B_talk 72 / C_act 117 / A_op 135)について v4.6 で tau の
中間絵を作り、真の D1 との LPIPS を測っています。blend と hold も同条件です。

    X1 = 変位(span)          X2 = |進行率 - tau|          X3 = X2 × X1

#### 結論を先に: **半分は棄却、半分は支持です**

| 予測する物 | X1 変位 | X2 ずれ | **X3 積** | 判定 |
|---|---|---|---|---|
| `LPIPS(model)` そのもの | **+0.881** | +0.393 | +0.857 | **積は変位単独に勝てない → 棄却** |
| `LPIPS(model) - LPIPS(blend)` | +0.321 | +0.290 | **+0.443** | **積が最良 → 支持** |

(3本 324組をまとめた値。clip 別も同じ向きです。)

**「画がどれだけ壊れるか」は変位だけでほぼ決まります。**積を持ち出すと
かえって相関が落ちます(X2 に雑音が乗るぶん、強い予測子を薄めるため)。

**「model を使う価値があるか」は積が最もよく決めます。**これは
主担当が言われていた「正解が端に居ると blend が半分当たる」の機構そのものです。

#### 変位を固定しても「ずれ」は効くのか(順位偏相関)

試験集合は変位で層別に抜いてあるので、全体の相関は変位の効きを過大に見せます。
**変位を固定した偏相関**を出しました。

| clip | `LPIPS(model)` 〜 ずれ(変位固定) | `model - blend` 〜 ずれ(変位固定) |
|---|---|---|
| B_talk | **+0.632** | **+0.447** |
| C_act | +0.229 | +0.030 |
| A_op | **+0.132** | +0.247 |
| 3本 | +0.352 | +0.225 |

**ずれは変位と独立に効きますが、効き方が clip でまるで違います。**
B_talk では +0.632 と強く、**A_op では +0.132 とほとんど効きません。**
つまり **「A_op の大変位が壊れるのは easing のせい」とは言えません。**
A_op の大変位帯では、ずれ以外の物(粒子・effect・遮蔽)が品質を決めています。

- **試験集合は変位で層別に抜いてあります。**全体の相関は「難所を多めに含む

easing は品質をほとんど説明しません(偏相関 +0.132)。

**言えるのは次の2つです。**

1. **easing は「model を使う価値があるかどうか」を決めます。**位置誤差
   (ずれ × 変位)が 11.5px を超えると、model は blend に負けます。
2. **素材が素直な所(B_talk)では、easing が品質をほぼ決めます**(偏相関 +0.632)。
   逆に言えば、**easing を直せば効くのは B_talk のような素材**で、
   A_op の大変位は easing を直しても直りません。

## 8. 残した課題

**指標の側**

- **`lag_px` の下限は区間の変位の 15.5%** です(3.4)。これ以下の差は
  Farneback の局所誤差に埋もれて読めません。B_talk の 60絵(1.35px)と
  120絵(1.15px)の差は、この下限に近く、有意とは言えません。
- **平行移動でしか検算していません**(3.4)。回転・変形・遮蔽が混ざる
  実場面、特に A_op の p90 95.4px という大変位で flow がどれだけ正しいかは
  未検証です。**A_op の数値は他の2本より弱い根拠**として扱ってください。
- **封じる区間の定義が指標に埋め込まれています**(保持 9 frame 以上 /
  cut / 変位 64px 超)。この閾値を変えると 3.7 の表の分母が変わります。
  閾値の根拠は `時刻張り直し.md` 3.3・3.5 にありますが、
  **指標と実装が同じ閾値を共有している**ので、実装側の判定を変えたら
  `d9_metric.py` の定数も合わせる必要があります。
- **straddle は指標ではなく実装の欠陥でした**(3.8)。当初これを
  「指標が過大に罰している」と書きましたが誤りで、時間で測り直しても
  値は変わりません(A_op 60絵 は frame 平均 17.84、時間平均 18.10)。
  **A_op では尺の 17.4% で本当に古い絵が出ています。**指標側に残る課題は
  ありません。**直すのは schedule 側**(出力時刻の吸着)です。
- **`lag_px` は「素材の絵をそのまま出す」方を有利に測ります**(3.9)。
  生成 frame には Farneback の雑音の下限(区間の変位の 15.5%)が必ず乗りますが、
  素材の絵にはほぼ乗りません。**出力 fps ごとに「素材の絵が映る時間」が
  違うので(48絵 18〜45%、60絵 0.2%)、条件を並べる時はこの割合を必ず併記します。**
  按分して補正する形にはしていません。両方が生成 frame を出している時刻だけで
  比べる(3.9 の最後の表)方が、仮定を置かずに済みます。
- **judder が目で見えるかを確かめていません**(6.4・3.10)。3.8 の
  「尺の 17.4% で古い絵が出る」は画素で確かめた事実ですが、**私の目視は
  250ms の窓を静止画で見る作りで、リズムの乱れは検出できません。**
  **3.10 の 72絵 / 120整絵 も、数値だけで目では見ていません。**
  1秒以上の窓で 60絵 と 120整絵 を並べて見る必要があります。
  出力 file は `out/<clip>_72絵.mp4` と `out/<clip>_120整絵.mp4` に在ります。
- **119.88fps を 120Hz の画面へ出した時の見え方を確かめていません**(3.10)。
  8.3秒に1回 frame が重複表示される計算ですが、それが実際にどう見えるかは
  測っていません。「17.4% の judder より軽い」は**計算上の比較**です。
- **59.94fps(23.976 の 2.5倍)を測っていません。**整数倍ではありませんが
  60Hz の画面と一致し、60.000 より素材との比が素直です。60Hz を採る場合の
  選択肢として測る価値があります。

**素材の側**

- **1話・3本・各30秒だけ**です。作品による作画density の差
  (劇場作品・3D混在・止め絵中心の深夜作品)は測っていません。
  特に「絵/秒」と「9 frame 以上の保持が占める尺」の2つは作品差が
  大きいはずで、効果の見積もりはこの2つで決まります。
- 3本とも同じ制作会社の同じ話数です。**独立な標本ではありません。**

**目視の側**

- 3本とも見ました(6章)。ただし **1本あたり数百 ms の窓が3〜4個**で、
  30秒を通しては見ていません。窓は「変位の合計が最大」と
  「指標が最悪」という**指標の側から選んだ**ものなので、
  **指標が見落とす種類の破綻は原理的に見つかりません。**
  無作為な窓での確認は残しています。
- 1人(診断担当)が見ただけで、**人による A/B 比較はしていません。**
  「20.9ms の中間絵が滑らかさに寄与しない」は本書では
  「保持長が二極化している」という物理量までしか示しておらず、
  **人の知覚でそう感じるかは測っていません。**
- **小変位の口パク・瞬きは目で見ていません**(6.5)。
  `時刻張り直し.md` 3.5 が LPIPS 0.003 の代価として数字で記録している
  項目で、B_talk の主要な素材でもあるので、確かめる価値があります。
- **effect の細部が消える件は C_act の1箇所しか見ていません**(6.3)。
  どの程度の頻度で起きるか(閃光・電撃・爆発の区間が尺の何%か)は
  測っていません。

**cut 判定**

- scdet を正解として扱っています(5章)。閃光を cut と誤る事が判っている
  ので、**正解そのものに誤差があります。** 手で正解を付けた区間を
  用意すれば、scdet 自身の精度も測れます。
- **`lib.cut_frames` の off-by-one は主担当が修正しました**(7.6)。
  本書の C_act の数値はすべて修正後に測り直した物です。ただし
  **修正後も C_act の cut 13件のうち1件は画素と合いません**(閃光で両側とも
  大きく変わる組)。scdet 自体の限界で、手で正解を付けない限り測れません。

**大変位の調査(7章)**

- **A_op の大変位帯で品質を決めている物を特定できていません**(7.8)。
  変位を固定すると非等速の効きは +0.132 しか残らず、残りが何かは
  「粒子・effect・遮蔽」と目で見て言っているだけで、**測っていません。**
- **LPIPS が 0.21〜0.25 で飽和します**(7.8)。誤差が大きい領域では
  どの予測子も相関が頭打ちになるので、**大変位帯の相関はすべて過小**です。
  飽和しない指標(位置ずれそのもの)で測り直す価値があります。
- **「積が 11.5px を超えると model が blend に負ける」は関門に使えません。**
  進行率は真の D1 を見て測るので、生成時には判りません。
  今の関門(変位 64px)はその代理です。

- **「正しい tau を D0 と D2 から当てられるか」を測っていません。**
  これが7章の結論の実装に直結する一番大きな穴です。正しい tau を知るには
  **今から作ろうとしている D1 がどこに居るか**を知る必要があり、
  それは定義上こちらに無い情報です。伸び代が大きい事だけは判っています
  (`時刻張り直し.md` 3.1 の tau 掃引で A_op の LPIPS が -38%)。
- **隣り合う3つ組の「ずれ」の相関(B_talk -0.46 / A_op -0.28)は、
  予測できる事の証拠になりません。**隣り合う3つ組は絵を2枚共有するので、
  1枚の位置がずれると隣同士で逆向きの誤差が出ます。**負の相関の一部は
  測り方の産物**です。切り分けていません。
- **進行率には雑音が乗ります。** 128px超では flow の自己整合が崩れるので、
  その帯の値は弱い根拠です(64-128px では fb 誤差が変位の 0.14〜0.22 で、
