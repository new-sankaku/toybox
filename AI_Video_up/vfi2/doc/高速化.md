# 高速化 — 実行基盤の再設計

RTX 4070 Ti 12GB / torch 2.10+cu126 / TensorRT 11.2.1.2 / Windows 11。
素材は Arknights 24話から切った 1080p 30秒 clip 3本 (A_op 720 frame / B_talk 719 / C_act 719)。

速度の計測はすべて `lib.gpu_lock("speed")` の中で行い、GPU 側は CUDA event、
CPU 側 (pipe の読み書き) は wall time で測っている。記録は `results/results.jsonl`。

表はすべて `s10_report.py` が `results.jsonl` から起こしている。手で写さない。

## 0. 要約

| 端から端まで何倍になったか | 旧実装の **1.01〜1.28倍** (30秒 clip → 60fps が 7.5〜10.5秒。実時間の 2.9〜4.0倍速) | 6 |
| その利得はどこから来たか | **ほぼ全部 GPU decode (NVDEC)**。runner と入出力の作り直しだけでは 0.87〜1.10倍で実質同じ | 3, 6 |

## 1. stage ごとの天井 (1920x1080, model=v4.6 fp16)

| stage | 実測 | 1 frame あたり | 何が制約か |
|---|---|---|---|
| decode (ffmpeg rawvideo → pipe → pinned) | 231.9 fps | 4.31 ms | CPU thread・pipe 帯域 |
| H2D 転送 (pinned → cuda) | — | 0.48 ms | PCIe |
| 判定 (box4 + 平均絶対差) | — | 0.146 ms | GPU |
| pack (BGR→RGB・正規化・7ch 組み立て) | — | 0.248 ms | GPU |
| **推論 (RIFE v4.6 bs=1)** | 188.5 fps | **5.322 ms** | **GPU (支配的)** |
| unpack (RGB→uint8 BGR) | — | 0.183 ms | GPU |
| nv12 変換 | — | 0.348 ms | GPU |
| D2H 転送 | — | 0.239 ms | PCIe |
| encode (hevc_nvenc p4) | 334.0 fps | 2.99 ms | NVENC |
| encode (hevc_nvenc p1) | 477.8 fps | 2.09 ms | NVENC |
| encode (p4 + split_encode_mode 3) | 426.3 fps | 2.35 ms | NVENC |

**天井は推論**。1 出力 frame を作るのに GPU 上で
pack 0.248 + 推論 5.322 + unpack 0.183 + nv12 0.348 + D2H 0.239 = **6.34 ms** 掛かる。
補間しない (絵をそのまま出す) 出力 frame は nv12 + D2H の 0.587 ms で済む。

旧設計 (素直な x2) では推論の呼び出し回数が source frame 数の半分以下だったので
decode と encode が見えていたが、新設計は「目標 fps ぶんの出力 frame をほぼ全部
補間で作る」ので、**推論回数が 60fps 出力で B_talk なら 125回 → 約1800回**に増える。
推論の 1回あたりを削るか、呼び出し回数を減らすかの2択になる。

## 2. batch 化 — 1080p では効かない

### 2-1. batch>1 の engine が作れる model は1つだけ

vs-mlrt が配る RIFE v2実装 ONNX 17本のうち、TensorRT の engine が bs=2 で
build できたのは **v4.25_lite だけ**だった。

| model | bs=2 build |
|---|---|
| v4.25_lite | OK |
| v4.0 / v4.2 / v4.3 / v4.4 / v4.5 / v4.6 / v4.7 / v4.8 / v4.9 / v4.10 / v4.15_lite / v4.17_lite / v4.18 / v4.22_lite / v4.26 / v4.26_heavy | NG |

落ちる理由は全部同じで、`Reshape_11` の目標 shape に 2 が焼かれている:

```
IShuffleLayer /Reshape_11: reshape changes volume to multiple of original
non-zero volume. Reshaping [2,4,1088,1920] to [2,2,1088,1920].
```

flow の 4ch を「2枚 × 2ch」へ畳む所が batch=1 前提で export されている。
定数を書き換える graph 手術はできるが、次の 2-2 の通り **1080p では batch に
速度の利が無い**ので手を出さない。

### 2-2. 1080p では batch が遅い (v4.25_lite fp16)

| bs | batch 全体 ms | 1枚あたり ms | fps | VRAM | bs=1 比 |
|---|---|---|---|---|---|
| 1 | 10.561 | 10.561 | 94.7 | 684 MB | 1.00倍 |
| 2 | 23.585 | 11.793 | 84.8 | 1172 MB | 0.90倍 |
| 4 | 47.013 | 11.753 | 85.1 | 2126 MB | 0.90倍 |
| 8 | 95.283 | 11.910 | 84.0 | 4198 MB | 0.89倍 |

**batch は速くならないどころか 11% 遅い。** 1080p の1枚で既に SM が埋まっており、
batch は VRAM だけ線形に食う。前回 960x540 で bs2 が 1.90倍になったのは
「1枚では GPU が埋まらない」小さい解像度の話で、1080p には持ち込めない。

SR (`..\vup`) で fp16 + bs2 が 1.80倍になったのは 1 frame あたりの計算量が
RIFE より桁で小さいからで、**同じ結論を RIFE へ流用してはいけない**。

### 2-3. batch した出力は bs=1 と一致する (実画像で確認)

乱数を入力にした対照では bs=1 との PSNR が 11.4dB しか出ず、sample の混線を
疑ったが、**実画像で測ると混線していない**。乱数は flow 推定が発散するため
fp16 の kernel 差がそのまま出るだけだった。

| 入力 | 全体 PSNR | 各 sample |
|---|---|---|
| 同じ組を 4本並べる | 80.57 dB | 80.57 / 80.57 / 80.57 / 80.57 |
| 別々の組を 4本 | 62.69 dB | 80.57 / 69.93 / 56.91 / 82.20 |

混線していれば 10〜15dB 台に落ちる。57〜82dB は fp16 の kernel 選択差の範囲。
**batch は正しい。ただ速くない。**

## 3. GPU I/O — decode は繋いだ。encode は繋がらない

### 3-1. 手段ごとの単体実測 (`s6_gpuio.py`)

| stage | 手段 | fps | 備考 |
|---|---|---|---|
| decode | ffmpeg CPU + pipe + H2D (現行) | 198.4 | — |
| decode | ffmpeg NVDEC (画素は取り出さない) | 610.7 | pipe で受ける口が無い |
| decode | PyNvVideoCodec (GPU 直・採用) | 817.4 | — |
| decode | 対照: ffmpeg CPU decode のみ | 929.1 | — |
| encode | D2H + pipe + hevc_nvenc (現行) | 348.5 | — |
| encode | PyNvVideoCodec (GPU 直) | — | `Tensor.__dlpack__() takes 1 positional argument but 2 were given` |

`ffmpeg -hwaccel cuda -hwaccel_output_format cuda` は素材を受け付けるし速いが、
**pipe で受け取る以上どこかで hwdownload が要る**。GPU 上に置いたまま torch へ
渡す口が無いので採らない。

**encode 側は繋げない。** PyNvVideoCodec の `Encode()` は torch tensor を
DLPack で受け取ろうとするが、`Tensor.__dlpack__()` の引数の数が合わず落ちる。
torch 側の DLPack の版と PyNvVideoCodec が期待する版が違う。回避するなら
CUDA array interface を持つ別の入れ物 (cupy など) を挟むことになり、それは
D2H を消すために新しい依存を1つ増やす話なので、今回は「できない」とした。
encode は D2H 0.239ms + pipe で 348.5 fps 出ており、天井 (推論 188.5 fps) の
1.85倍あるので、繋いでも全体は動かない。

### 3-2. NVDEC を実際に繋いだ (`fastio.NvdecDrawingSource`)

`DrawingSource` (pipe 版) と同じ口を持つ NVDEC 版を作った。要点は2つ。

- NVDEC の surface は decoder が使い回すので、次の `Decode()` を呼ぶ前に
  複製を確定させる必要がある。main の stream を同期すると推論待ちに巻き込まれ
  るので、**専用 stream を持って自分だけ同期する**
- NV12 → BGR は GPU 上で行う (BT.709 limited。素材の色は ffprobe で確認)。
  **要る絵だけ**変換するので、捨てる frame に色変換の費用は乗らない

画素と順序が合っているかを ffmpeg の bgr24 展開と突き合わせた。順序が狂えば
PSNR は桁で落ちるので、これは順序の検算も兼ねている。

| clip | 枚 | PSNR 最小 | 平均 | 最大 |
|---|---|---|---|---|
| B_talk | 12 | 47.46 | 47.54 | 47.64 |
| A_op | 12 | 47.55 | 47.58 | 47.69 |

47dB台。差は chroma の補間法だけ (NVDEC は nearest、ffmpeg は双一次に近い)。
**品質の計測は今まで通り `lib.load()` (ffmpeg bgr24) を基準にすること。**
NVDEC 経路は出力を作る時だけ使う。

### 3-3. 端から端まで繋いだ時の利得

同じ schedule・同じ呼び出し回数で decode だけ pipe と NVDEC を入れ替えた時の比
(6-2 の交互測定・2巡ぶんの幅)。

| 条件 | A_op | B_talk | C_act |
|---|---|---|---|
| x2 出力 (絵の列) | 1.04〜1.06倍 | 1.25〜1.30倍 | 1.24〜1.39倍 |
| 60fps 出力 (絵の列) | 1.00〜1.02倍 | 1.19〜1.20倍 | 1.14〜1.17倍 |
| 60fps・全部補間 (uniform) | 1.00倍 | 1.05倍 | 1.05倍 |

**推論の回数が少ないほど効く。** 当然で、decode は推論と別 thread で走るから、
推論が詰まっている限り decode の速さは見えない。B_talk の x2 は 1438 frame の
出力に対して model 呼び出しが 525回しかなく、decode (719 frame) が相対的に重い。
逆に 60fps で全部補間する条件では推論が 1795回で完全に律速し、decode を 4倍
速くしても全体は 5% しか動かない。

A_op が他の2本より利が薄いのは、絵が 649枚 (1枚 1.11 frame) と多く、
同じ 1440 frame を出すのに model 呼び出しが 561回要るから。B_talk は絵が
132枚 (1枚 5.45 frame) しかなく、呼び出しは 525回でも decode すべき frame は
同じ 719枚なので decode の比重が高い。**GPU decode が効くのは「絵が少なくて
保持が長い」素材**で、それは会話や限定 animation の側。

## 4. flow の scale — 速度と品質の対照

flow の推定を低解像度で行う。v2実装 (`rifelib.Rife`) は掛けられないので
v1実装 (`rifev1.RifeV1`) だけの話になる。

**この章の主題は「scale を下げると model が扱える変位の上限が上がるか」。**
64px を超える変位では 11種のどの model も blend / hold に負ける、という結果が
model 比較の側で出ている。scale=0.5 なら flow は半分の解像度で推定されるので、
128px の変位が network から見れば 64px 相当になる — これが 64px の壁を動かせる
唯一の未検証の手段だった。**結論は「動かない」。** 4-4 に根拠を置く。

### 4-1. 推論単体と品質 (`s7_scale_nvenc.py` / `s9_scalequal.py`)

品質は `m1_testset.py` の試験集合 (連続する3枚の絵 D0,D1,D2 のうち真ん中を
両端から作って本物と比べる) で、`m3_bench.py` と同じ GPU 版 metric・同じ
層別の重み付けを使った。n は A_op 135組 / B_talk 72組 / C_act 121組。

| scale | pad | 推論 ms | fps | 速度比 | A_op LPIPS/GMSD | B_talk LPIPS/GMSD | C_act LPIPS/GMSD |
|---|---|---|---|---|---|---|---|
| 1.0 | 1920x1088 | 5.24 | 190.8 | 1.00 | 0.2020 / 0.1092 | 0.0162 / 0.0472 | 0.0977 / 0.0409 |
| 0.5 | 1920x1088 | 3.309 | 302.2 | 1.584 | 0.2037 / 0.1149 | 0.0168 / 0.0480 | 0.0981 / 0.0417 |
| 0.25 | 1920x1152 | 2.9 | 344.8 | 1.807 | 0.2082 / 0.1198 | 0.0177 / 0.0467 | 0.0982 / 0.0409 |

悪化率にすると:

| scale | A_op LPIPS | A_op GMSD | B_talk LPIPS | B_talk GMSD | C_act LPIPS | C_act GMSD |
|---|---|---|---|---|---|---|
| 0.5 | +0.8% | +5.2% | +3.7% | +1.7% | +0.4% | +2.0% |
| 0.25 | +3.1% | +9.7% | +9.3% | -1.1% | +0.5% | ±0% |

### 4-2. 新しい export でも scale を掛けられるようにした

`rifev1._apply_scale` は Constant の**出力名** (`onnx::Resize*` / `onnx::Mul*`)
で倍率の定数を拾う。この命名は古い export のもので、**v4.15_lite 以降は
`/blockN/Constant_*` になるため1個も拾えず**「この重みは scale を掛けられません」
で止まっていた。品質最良の v4.26_heavy がここに入る。

| model | 倍率 Resize | 倍率 Mul | 既存実装で scale |
|---|---|---|---|
| v4.0 / v4.2 / v4.3 / v4.4 / v4.5 / v4.6 | 11 | 7 | OK |
| v4.15_lite / v4.17_lite / v4.18 / v4.22_lite / v4.25_lite / v4.26 / v4.26_heavy | 0 | 0 | NG (名前が違うだけ) |

graph は同型で、pyramid の各段が down Resize (倍率<1) → conv → up Resize
(倍率>1) と、flow の大きさを直す Mul の対を持つ。

| model | Resize の倍率 | Mul の倍率 |
|---|---|---|
| v4.6 | 0.125 / 8 / 0.25,0.25 / 4 / 0.5,0.5 / 2 / 1,1 / 1 | 8, 0.25, 4, 0.5, 2, 1, 1 |
| v4.26_heavy | 0.0625 / 16 / 0.125 / 8 / 0.25 / 4 / 0.5 / 2 | 16, 0.125, 8, 0.25, 4, 0.5, 2 |

なので名前ではなく**倍率の値**で分けられる (1未満は down で ×scale、1より
大きければ up で ÷scale)。`s9_scalequal.py` に値ベースの書き換えを置いた。
`rifev1.py` は他 Agent の資産なので触っていない。

**検算**: 既存実装が扱える 6 model × scale 2種で、両者が同じ値を出すことを
確かめてから使う (`verify_against_v1`)。古い export には倍率 1.0 の定数が
混ざっていて値だけでは down/up を分けられないので、**1.0 以外の定数 172個**が
一致することを見た。v4.26 系には 1.0 が1つも無いので判別は一意に決まる
(`new_export_ok`)。合わなければ止まる。

書き換えが正しいことは結果でも確かめられる。**v1実装 scale=1.0 の値が、
別途 v2実装で測ってあった v4.26_heavy とほぼ一致した**:

| A_op の帯 | 0-4px | 4-8px | 8-16px | 16-32px | 32-64px | 64-128px | 128-px |
|---|---|---|---|---|---|---|---|
| v1実装 scale=1.0 (今回) | 0.02170 | 0.01704 | 0.03367 | 0.07423 | 0.19498 | 0.22277 | 0.19703 |
| v2実装 (m3_bench の記録) | 0.02352 | 0.01855 | 0.03576 | 0.07554 | 0.19499 | 0.22295 | 0.19714 |

32-64px 以降は小数第4位まで一致している。

| C_act | 64-128px | 0.21436 | **0.20286** | 0.21272 | 0.21518 | 0.21486 | 0.20459 | 0.21100 | 0.22456 | **対照 (blend)** |

**scale を下げても、どの帯でも model は対照を上回らない。**

- **64-128px**: scale=0.5 で v4.26_heavy が僅かに改善する (A_op 0.22277 →
  0.21882、-1.8%) が、blend 0.20500 には 6.7% 足りない。C_act では scale を
  下げると悪化する (0.20459 → 0.21100 → 0.22456)。**壁を越えた cell は1つも無い**
- **128-px**: scale を下げると **必ず悪化する**。A_op heavy 0.19703 → 0.20320 →
  0.22573、C_act heavy 0.36932 → 0.39237 → 0.40505。対照 (0.15981 / 0.14993) との
  差は縮むどころか開く
- **32-64px (model が勝っている帯)** でも scale を下げると悪化する
  (A_op heavy 0.19498 → 0.19838 → 0.21285)。**scale を下げて変位の余裕が増える、
  という効果はどの帯にも現れない**
- GMSD でも同じ。A_op / C_act の 64px 超は全帯で blend か hold が最良

model を v4.6 から品質最良の v4.26_heavy に替えると 64-128px は
0.24267 → 0.22277 と 8.2% 良くなるが、それでも blend に届かない。
**壁は model 由来でも scale 由来でもない。** 「両端の絵の間に対応が無い」
という素材側の性質で、flow を推定する解像度を変えても対応は生まれない。

実務上の結論: **跨ぐ変位が 64px を超える組は model へ渡さず、blend か hold
へ落とす関門を置くのが正しい。** この関門は scale の設定では動かせない。

落とし先は帯で分かれる。

| 帯 | A_op の最良 | C_act の最良 | 落とし先 |
|---|---|---|---|
| 64-128px | blend 0.20500 (hold 0.25928) | blend 0.20286 (hold 0.21436) | **blend** (2 clip とも blend) |
| 128-px | blend 0.15981 (hold 0.16782) | hold 0.14993 (blend 0.27690) | **素材で割れる** |

128px 超は 2 clip で逆を向く。C_act は hold が blend の 1.85倍良く、
A_op は blend が hold より 5% 良いだけ。**差が大きいのは C_act の側
(cut に近い大変位で blend すると二重像が出る) なので、迷うなら hold。**
なお `r5_render.py` の `MV_GATE = 64.0` は既にこの値だが、落とし先が hold
一択で blend が無い。64-128px を blend へ送る口は retime 担当の領分。

### 4-5. 悪くなるのは「難しい帯」ではなく「易しい帯」

A_op で scale=0.25 にした時、**0-4px 帯が +44.0%** 悪化するのに対し
**32-64px 帯は +4.2%、64-128px 帯は +0.7%** しか動かない (v4.6)。
「変位が大きい所ほど低解像度 flow で潰れる」という直感と逆になる。

理由は、大変位の帯は scale=1.0 でも既に LPIPS 0.2 台で破綻しており、
scale を下げても「壊れ方が少し変わる」だけだから。一方 0-4px の帯は
scale=1.0 なら 0.02 とほぼ正解で、そこを低解像度 flow で潰すと相対的な
悪化が大きく出る。**scale を下げる代価は、動きの少ない所の細部で払う。**
速度のために scale を下げるのは有りだが、**大変位のために下げるのは無意味。**

## 6. 端から端まで

### 6-1. 何と何を比べたか

旧実装は `r5_render.py` (retime 担当が書いた物)。新実装は
`fastio.py` + `runner.py` + `s8_e2e.py`。

比較を成り立たせるため、**新実装にも `r5_render.schedule_for()` が作る
schedule をそのまま流した** (`--plan retime`)。model の呼び出し回数まで
一致するので、差は入出力と runner の作りだけになる。

条件は旧実装の `x2絵` (fps_out = 2×source) と `60絵` (fps_out = 60)。

| 新 pipe | C_act | 60 | 4 | 9.10 | 9.58 | 1.053 |
| 新 NVDEC | C_act | 60 | 4 | 8.08 | 8.23 | 1.019 |

旧実装の幅 (最大 1.85倍) が新実装 (最大 1.17倍) より大きく見えるが、
**これは実装の差ではなく時間帯の差**。6-2 の交互測定の中だけで見ると旧の幅は
1.00〜1.06倍しかない。旧を大きく外した測定は、他 Agent が重い処理を回していた
時間帯に集中している。

意味のある教訓はこちら:

- **canary は推論の GPU 時間しか見ない。** 6.89秒 対 12.13秒 の測定は両方
  canary 5.4ms・clean だった。汚染源が CPU・NVENC・disk 側にあると素通りする
- **速度の比較は必ず交互に測る。** 別々の時間帯の値を並べると、干渉を実装の差と
  読み違える。実際、交互測定の前は「新 pipe が旧の 1.02〜1.21倍」「新 NVDEC が
  旧の 1.06〜1.60倍」という数字が出ていた。交互に測った真値は
  **pipe 0.87〜1.10倍・NVDEC 1.01〜1.28倍**で、pipe の利は丸ごと幻だった
- 代表値には最小を採る。干渉は遅くする向きにしか働かない

## 7. 効かなかった手段 — 蒸し返さないための一覧

| 手段 | 期待 | 実測 | なぜ効かないか |
|---|---|---|---|
| runner と入出力の作り直し (pipe のまま) | 1.2〜1.5倍 | **0.87〜1.10倍 (実質同じ)** | 旧実装も既に reader/writer thread と pinned pool を持っていた。入出力は元から天井ではない (6-2) |
| 推論の batch 化 (1080p) | 1.5〜2倍 | **0.89〜0.90倍 (遅い)** | 1080p の1枚で既に SM が埋まる。VRAM だけ線形に増える (2章) |
| batch engine の build | 17 model | **1 model (v4.25_lite) だけ** | vs-mlrt の ONNX が `Reshape_11` に batch=1 を焼いている |
| CUDA Graph | 1.24倍 | **1.028倍** | TensorRT が既に1回の `execute_async_v3` に畳んでいる。1.24倍は GPU が汚染された状態の値 |
| NVENC の preset を軽くする | 推論が速くなる | **preset 依存より測定のばらつきが大きい** | 2巡で preset の順位が入れ替わった。速度の設定として使えない |
| GPU encode (PyNvVideoCodec) | D2H と pipe が消える | **動かない** | `Tensor.__dlpack__()` の引数不一致。加えて現行 encode は 348.5 fps で天井 (188.5 fps) の 1.85倍あり、繋いでも全体は動かない |
| ffmpeg NVDEC を pipe で受ける | GPU 直 decode | **口が無い** | pipe で受ける以上どこかで hwdownload が要る |
| GPU decode (全部補間する条件で) | 4倍速い decode | **1.00〜1.05倍** | decode は別 thread。推論が詰まっている限り見えない (3-3) |
| flow scale 0.25 | 0.5 より更に速い | **0.5 から 1.05倍だけ** | pad が 1152 へ増え、推論以外が残る。品質の代価だけ増える (4章) |
| 目標 fps を 47.952 と丸める | 同じ | **1.41倍 遅い** | 出力時刻が絵の時刻と一致せず、只で写せた frame が補間対象へ落ちる (6-5) |
| **大変位のために flow scale を下げる** | 64px の壁が動く | **動かない。128px 超は逆に悪化** | 128px の変位が network から見て 64px 相当になっても、両端の絵に対応が無いことは変わらない。壁は素材側の性質 (4-4) |

補足: 「batch は速くなるはず」は SR (`..\vup`) で fp16+bs2 が 1.80倍だった
実績から来ているが、あちらは 1 frame あたりの計算量が RIFE より桁で小さい。
**解像度と計算量が違う系の結論を流用しない。**

もう1つ、効かなかった訳ではないが **効くと言い切れなかった** 物を挙げておく。
GPU decode の利得は素材で 1.01倍から 1.28倍まで開く。A_op のように絵が
1枚 1.11 frame しか保たない素材では、model 呼び出しが増えて decode が完全に
隠れる。**「NVDEC にしたので何割速くなる」と一般化して言えない。**

## 8. 残した課題

| 課題 | 状況 | 次に何をするか |
|---|---|---|
| 推論そのものを軽くする | 手付かず | **残っている唯一の大きい手**。天井は推論 (5.322ms)。model を替える (models 担当) か、flow scale 0.5 (1.20〜1.28倍) か、蒸留・枝刈りしか無い |
| flow scale 0.5 を採るか | 測り終えた・未決 | 全体 1.20〜1.28倍 と LPIPS +0.4〜3.7% の交換。ただし scale は v1実装でしか掛からず、v1 は素で v2 の 0.92〜0.97倍。採るなら v1 へ寄せる判断が要る (4-6) |
| 下限比 1.25〜1.46倍 の残り | 未解明 | 絵の列を使う条件では入出力が隠れ切っていない。`s5b_stepbreak.py` を e2e の中で回して、どの stage が漏れているか特定する |
| GPU encode | 「できない」 | `Tensor.__dlpack__()` の不一致。cupy を挟めば通る可能性はあるが、依存を1つ増やす価値は無い (encode は天井の 1.85倍速い) |
| NVDEC の chroma 補間 | 差 47dB | 出力を作る時だけ NVDEC を使い、品質計測は `lib.load()` を基準にする運用で回避している。両方を NVDEC へ揃えるなら全 Agent の再測が要る |
| 測定の汚染 | 部分的に対処 | canary は推論の GPU 時間しか見ない。CPU・NVENC・disk の干渉は捕まらないので、`others_on_gpu()` (GPU に居る他 process 数) を記録に足した。根本的には計測を1台に占有させるしかない |
| batch engine の graph 手術 | やらない | `Reshape_11` の定数を書き換えれば bs>1 の engine は作れるが、2章の通り 1080p では batch に速度の利が無い |
| 64px 超をどう捌くか | 測り終えた・実装は retime 担当 | 跨ぐ変位が 64px を超える組は model へ渡さない関門が要る。128px 超は hold、64-128px は blend (4-4)。`r5_render.py` の `MV_GATE=64.0` は既にこの値だが、落とし先が hold 一択で blend が無い |
| 新しい export の scale | `s9_scalequal.py` に置いた | 値ベースの書き換え。`rifev1.py` へ取り込むかは所有者の判断 (4-2)。取り込めば v4.18 / v4.25_lite / v4.26 でも scale が使える |
