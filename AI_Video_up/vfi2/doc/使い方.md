# フレーム補完の使い方 — コマ数を2倍にする

`2_動画_アニメ_フレーム補完_47fps.bat` の説明書です。

---

## これは何をする物か

アニメの**コマ数を元の2倍**にして、動きを滑らかにします。
23.976fps のアニメなら 47.952fps（およそ48コマ）で出ます。

普通の「コマ数2倍」の道具はアニメには効きません。アニメは同じ絵を
2コマ・3コマと続けて見せているので、コマとコマの間に1枚差し込んでも
**同じ絵の複製が増えるだけ**だからです。実際に測ると、会話の場面では
差し込んだ絵の 81.8% が複製でした。

この道具は、まず動画を**「絵」の列**に畳み直します。同じ絵が3コマ続いて
いれば、それは3コマではなく絵1枚として数えます。そのうえで、絵と絵の
あいだの時刻に新しい絵を作ります。これで初めて、1秒あたりに見える
絵の枚数が実際に増えます。

---

## 使い方

1. `2_動画_アニメ_フレーム補完_47fps.bat` に、動画ファイルか、動画の
   入ったフォルダをドラッグ＆ドロップします
2. 黒い画面が出て進み具合が表示されるので、終わるまで待ちます
3. 元の動画と同じ場所に、名前の後ろに `_47fps` の付いた動画ができます

複数まとめて放り込めます。フォルダを放り込むと、その直下の動画を
まとめて処理します（下のフォルダまでは辿りません）。

**同じ名前の出力がすでにある動画は飛ばします。**作り直したい時は、
前の出力を消してから放り込んでください。

---

## 出力される物

| | |
|---|---|
| コマ数 | 元の**厳密な2倍**（23.976 → 47.952） |
| 尺 | 元と同じ。早送りにも遅回しにもなりません |
| 解像度 | 元と同じ |
| 映像 | H.265（HEVC）。NVIDIA のハードウェアで書きます |
| 音声 | 元のまま入ります（作り直しません） |
| 字幕 | 元のまま入ります。字幕用の書体も一緒に入ります |
| 入れ物 | 元が mp4 か mov で字幕が無ければ mp4、それ以外は mkv |

字幕のある動画を mp4 で出すと字幕を捨てることになるので、
その場合は mkv で出します。

---

## 掛けない方がいい物

### OP・ED

**効果がありません。むしろ残像が出ます。**

OP や ED は本編と作り方が違い、1コマずつ別の絵が描いてあることが
多いためです。実測すると OP は1秒あたり 21.6 枚の絵があり、本編の
会話場面（4.4枚）の5倍でした。元から動きが細かいので、増やす余地が
ほとんどありません。

そのうえ、絵と絵のあいだの動きが大きすぎます。OP では絵と絵で
画面の物が中央値 36 画素ぶん動いており、4分の1以上が 64 画素を
超えていました。ここまで動くと、間の絵を作る仕組みが対応する場所を
見失い、**にじんだ絵**を作ります。

本編だけを切り出してから掛けるか、OP・ED はあきらめてください。

### 実写・3DCG

この道具は「同じ絵が何コマも続く」というアニメの作り方を前提に
しています。実写のように毎コマ絵が違う素材では、ただの2倍と同じに
なるだけで、得がありません。

---

## わざと補間しない所があります

全部を滑らかにしているわけではありません。次の3つは**わざと元のまま**
にしています。どれも、補間すると元より悪くなることを測って確かめた
場所です。

### 1. 意図的に止めてある絵

アニメには、絵を4秒間そのまま止めておく、といった演出があります。
ここを補間すると、**4秒かけて次の絵へ溶けていく**という、元には無い
動きになってしまいます。元は4秒止めてから、1コマでパッと切り替えて
いるのです。

そこで、**同じ絵が9コマ（0.375秒）以上続く場所は補間しません。**
本編1話ぶんで見ると、尺のおよそ4分の1がこれに当たります。

### 2. 動きが大きすぎる所

絵と絵で画面の物が 64 画素より大きく動いている場所は補間しません。
ここを無理に埋めると、間の絵を作る仕組みが単純な重ね合わせにすら
負けます。1話ぶんで尺の1割強がこれに当たります。

### 3. 場面の切り替わり（カット）

別の場面へ切り替わる所を補間すると、前の場面と次の場面が混ざった
絵が1枚できてしまいます。ここも元のまま切り替えます。

**合わせて、本編1話のうち尺の3割ほどは元のままです。**
残りの7割で、1秒あたりに見える絵の枚数が増えます。

## どれくらい時間がかかるか

RTX 4070 Ti での実測です。

| 素材 | 走査 | 生成 | 合計 |
|---|---|---|---|
| 30秒（会話の場面・1080p） | 1.6秒 | 6.2秒 | 9秒 |
| 5分（本編・1080p） | 19秒 | 79秒 | 1分40秒 |
| 23分40秒（1話まるごと・1080p） | 1分35秒 | 5分40秒 | 約7分30秒 |

走査はおよそ 350コマ/秒、生成はおよそ 200コマ/秒（出力側のコマ数）です。
**動きの細かい素材ほど遅くなります。**間の絵を作る回数が増えるためです。

**初めて動かす時だけ、さらに数分かかります。**中で使う仕組みを
その解像度専用に組み立てるためです。組み立てた物は保存されるので、
2本目からはかかりません。解像度が変わると組み立て直します。

### メモリとディスク

**素材が長くなってもメモリは増えません。**30秒から15分まで尺を振って
測った結果です。

| 素材の尺 | 走査中のメモリ |
|---|---|
| 5分 | 943 MB |
| 10分 | 967 MB |
| 15分 | 981 MB |

1分あたり 3.8 MB しか増えず、1話へ引き伸ばしても約 1.0 GB です。
動画を丸ごとメモリへ広げていれば 1分あたり 8.3 GB 増えるので、
けた違いに小さいことが確かめられます。走査中に作られる一時ファイルは
**ゼロ**です。

ディスクは、出来上がる動画のおよそ2倍を一時的に使います
（映像だけのファイルを作ってから、音声と字幕を入れた完成版を作るため）。
1話でおよそ 1.5 GB です。完成すると一時ファイルは消えます。

途中で黒い画面を閉じると止まります。書きかけの出力は消えるので、
中途半端なファイルは残りません。

## パソコンが重くなる時 — `--低負荷`

処理中も同じパソコンで他の作業をしたい時は、バッチファイルの最後の行の
末尾に `--低負荷` を足してください。**CPU の使用を4割ほどに抑えます。**

5分の素材で測った代価です（CPU は12個ぶんの機械）。

| 設定 | 時間 | CPU（何個ぶん） | 1話に直すと |
|---|---|---|---|
| 既定（速度優先） | 1分26秒 | 1.84個 | 約7分30秒 |
| `--cpu 4` | 1分32秒 | 1.58個 | 約8分 |
| `--cpu 2` | 1分43秒 | 0.92個 | 約9分 |
| **`--低負荷`** | 1分46秒 | **0.70個** | **約9分30秒** |

`--低負荷` は3つのことを同時にやります。使う CPU の数を4分の1に絞り、
画像処理ライブラリの内部の並列も絞り、**処理の優先順位を下げて**
他の作業に順番を譲ります。

`--cpu 4` のように数字で指定することもできます。小さいほど CPU を
使わなくなり、そのぶん遅くなります。

**出来上がる動画は変わりません。**どの設定でも、絵の切り替わりの
判定結果は同じでした（5分素材で 2,518 枚、カット 57 か所）。
遅くなるだけで、中身は一致します。

## 細かい設定

普段は触らなくて構いません。バッチファイルの最後の行に足します。

| 書き方 | 意味 |
|---|---|
| `--fps x2` | 元の厳密な2倍（既定） |
| `--fps 60` | 60fps ちょうど |
| `--fps x3` | 元の3倍 |
| `--enc "-preset p4 -cq 20"` | 画質と速さ。`-cq` は小さいほど高画質で大きいファイル（既定 20） |
| `--suffix _48` | 出力名に付ける文字（既定は出力コマ数から作ります） |
| `--plan-only` | 作らずに、何コマ作ることになるかだけ表示します |
| `--decode pipe` | GPU の復号を使わず、ffmpeg で読みます（色がおかしい時に） |
| `--scan cpu` | 1周目の下調べを GPU でなく CPU で行います |
| `--低負荷` | CPU を抑えて他の作業に譲ります（上の節） |
| `--cpu 4` | 使う CPU の数の上限を決めます |
| `--model v4.6` | 間の絵を作る仕組みの種類 |

`--fps` に `47.952` のような**丸めた数を書かないでください。**
出力の時刻が元の絵の時刻とずれて、そのまま写せるはずのコマまで
作り直すことになり、1.41倍遅くなります。倍率で指定する `x2` なら
そうなりません。

## 動かない時

**「venv が見つかりません」と出る**
`vup\venv` が要ります。`vup\README.md` の手順で作ってください。
このバッチは既存の3本と同じ venv を使います。

**「VFR らしき素材です」と出て止まる**
コマの間隔が一定でない動画です。この道具はコマ番号から時刻を
決めているので、間隔が一定の動画にしか掛けられません。
先に一定のコマ数へ変換してから掛けてください。

**出力の色がおかしい**
`--decode pipe` を足してください。GPU の復号は 8bit・BT.709 の
動画を前提にしており、それ以外は自動で ffmpeg 側へ切り替えますが、
判定しきれない素材があります。

**途中で止まって「失敗」と出る**
理由がそのまま表示されます。黙って別のやり方に切り替えることは
しません（何が起きたか分からなくなるためです）。

## 中身の説明（作る人向け）

処理は3巡です。

1. **走査** — 動画を1回読んで、「絵の切り替わり」「場面の切り替わり（カット）」
   「絵と絵のあいだの動きの大きさ」の3つを求めます。**動画を丸ごとメモリへ
   広げません。**広げると 30秒の 1080p で 4.5GB、1話なら 197GB になり
   成立しません。持っているのは絵1枚ぶんの縮小画像だけです
2. **生成** — GPU で復号し、間の絵を作り、GPU で符号化します。
   映像だけを書きます
3. **合成** — 元のファイルから音声・字幕・書体を、作り直さずに移します

### どこを GPU でやっているか

1周目の走査は既定で GPU です。内訳は次のとおりです。

| 処理 | どちら | 備考 |
|---|---|---|
| 復号 | GPU（NVDEC） | 出てくる画素は ffmpeg の復号と**完全に同じ**です |
| 縮小・絵の切り替わり判定 | GPU | |
| 場面の切り替わり（カット）検出 | GPU | ffmpeg の `scdet` と**同じ式**を GPU で計算します |
| 絵と絵の動きの大きさ | **CPU** | 下に理由 |
| 2周目の復号・生成・符号化 | GPU | |

**動きの大きさ（オプティカルフロー）だけは CPU に残っています。**
使っているのは OpenCV の Farneback 法で、この環境の OpenCV には CUDA 版が
入っていません。別の計算方法へ替えることはできますが、「64 画素より大きく
動いたら補間しない」という判定の値はこの計算方法で測って決めたものなので、
替えると判定の値を全部測り直すことになります。効果が読めないうちに
作り直さない、という判断です。

そのため、**絵が細かく切り替わる素材ほど CPU を使います。**OP のように
ほぼ毎コマ絵が変わる素材では CPU が上限に張り付きます。

**CPU を使うのは1周目だけです。**5分素材で測った内訳です。

| 区間 | 時間 | CPU（何個ぶん） | GPU 計算 |
|---|---|---|---|
| 1周目・下調べ | 17秒 | **5.6個** | 13% |
| 2周目・生成 | 69秒 | **0.9個** | 84% |

時間の8割を占める2周目は GPU の仕事で、CPU はほとんど使いません。
CPU が重いのは前半の短い区間だけ、という形です。そこも
`--低負荷` で抑えられます（下の「パソコンが重くなる時」）。

カット検出については、「差が大きいところをカットと呼ぶ」という単純な
やり方では `scdet` に勝てないことが先に測ってありました（OP で 195回
反応して 158回が誤検出）。そこで閾値を作り直すのではなく、`scdet` の計算式
そのものを GPU に書き直しました。出力は ffmpeg の値と、表示の丸め
（小数3桁）の範囲内で一致します。

実装は `vfi2/vfi.py`。時刻の計算は `vfi2/retime.py`、入出力は
`vfi2/fastio.py`、推論は `vfi2/runner.py` にあり、この3つは
検証時の物をそのまま使っています。

設計の根拠は次の4本です。

| | |
|---|---|
| `doc/時刻張り直し.md` | 絵の列・代表時刻・関門・目標コマ数の決め方 |
| `doc/高速化.md` | 速度の実測。何が効いて何が効かなかったか |
| `doc/診断.md` | 素直な2倍がなぜ効かないか |
| `doc/model比較.md` | 間の絵を作る仕組みの選定 |

判定の値の検算は次の8本です。

| | |
|---|---|
| `t1_scan.py` | 走査を原寸の実測と突き合わせ |
| `t2_thresh.py` | 同じ絵と見なす閾値の選定 |
| `t3_look.py` | 出力の画素を元と突き合わせ |
| `t4_scangpu.py` | GPU 走査と CPU 走査の一致（復号・画素・判定の3段） |
| `t5_scdgpu.py` | GPU のカット検出と ffmpeg `scdet` の一致 |
| `t6_util.py` | CPU と GPU の使用率の実測 |
| `t7_scale.py` | 尺を振ってメモリが尺に比例しないことの確認 |
| `t8_cpubreak.py` | 走査の CPU の内訳（何が CPU を食っているか）|
