# 時刻の張り直し — 絵の列に対する補間

素直な x2（frame と frame の間を1枚作る）で「効果が出ていない」件に対する
答えです。原因と対策を実測で確かめ、出力 file まで作りました。

計測の生の記録は `vfi2/results/results.jsonl`、実装は `vfi2/retime.py`
（純粋な計算）と `vfi2/r1_*.py` 〜 `vfi2/r8_*.py`（実験）です。

---

## 0. 結論

**素直な x2 が効かない理由は測って確定しました。** 会話場面では、素直な x2 が
作る中間 frame の **81.8% が「同じ絵と同じ絵の間」** で、ただの複製です。
1秒あたりの異なる絵の枚数は 4.4 枚から 8.6 枚にしかならず、しかも増えた分は
絵の切り替わりの直前直後に固まるので、動きの型は保持→跳躍のままです。

**絵の列へ張り直すと、実際に増えます。**（数値は6章）

**ただし上限があります。** 会話場面の **52.9%、戦闘場面の 44.9% は「意図的に
止めてある絵」** で、ここは補間してはいけません（画素を確かめました。96 frame
保持の区間は先頭との box4 が最大 3、48 を超える画素は 0 で、完全な静止画です）。
効果はこの外側でしか出ません。

**OP（1コマ打ちの action）では効果が出ません。** 元から 21.6 絵/秒あり、
絵と絵の間の変位が中央 36.4px・26.8% が 64px 超で、model が単純平均に負ける
領域です。張り直しても呼び出しの 3割は関門で封じられます。

---

## 1. 素材の実測

30秒ずつ切った lossless clip 3本（Arknights 24話、1080p、24000/1001 fps）。

| clip | 場面 | frame | 絵 | 1枚あたりframe | 絵/秒 | cut | 同じ絵の隣接pair | 絵間変位 p50 px | p90 px | 64px超 |
|---|---|---|---|---|---|---|---|---|---|---|
| A_op | OP(1コマ打ち・大変位) | 720 | 649 | 1.11 | 21.61 | 37 | 9.9% | 36.4 | 95.4 | 26.8% |
| B_talk | 会話(限定animation) | 719 | 132 | 5.45 | 4.4 | 6 | 81.8% | 1.8 | 19.9 | 0.0% |
| C_act | 戦闘(本編action) | 719 | 263 | 2.73 | 8.77 | 13 | 67.7% | 5.2 | 70.2 | 12.0% |

**「同じ絵の隣接pair」がそのまま、素直な x2 が無駄に作る frame の割合です。**
B_talk では 81.8%、C_act では 67.7% の中間 frame が複製にしかなりません。

保持長の内訳。「1枚あたり 5.45 frame」は平均で、実体は違います。

| clip | 1/2/3/4 frame 保持の枚数 | 5〜8 | 9以上の枚数 | 同 割合 | 9以上が占める frame | 同 尺の割合 | 最長 frame |
|---|---|---|---|---|---|---|---|
| A_op | 1:589/2:53/3:5/4:1 | 1 | 0 | 0.0% | 0 | 0.0% | 6 |
| B_talk | 1:10/2:22/3:86/4:2 | 3 | 9 | 6.8% | 380 | 52.9% | 96 |
| C_act | 1:166/2:45/3:37/4:2 | 3 | 10 | 3.8% | 323 | 44.9% | 60 |

B_talk は **3コマ打ちが 86枚で主流**、そこに 9 frame 以上の長い保持が 9枚だけ
混ざり、その 9枚が **尺の 52.9% を占めます**。平均の 5.45 はこの偏りの産物で、
「1枚が 5.45 frame 保持される素材」ではありません。設計はこの二層構造の方に
合わせる必要があります。

---

## 2. やっている事

1. frame の列を「絵」の列へ畳む（`lib.drawing_runs`。box4 が 16 未満なら同じ絵）
2. 絵 D_k に代表時刻 t_k を与える
3. 目標 fps の各出力時刻 T について、それを挟む D_k, D_k+1 を求め、
   `tau = (T - t_k) / (t_k+1 - t_k)` で model を呼ぶ
4. 補間してはいけない pair では D_k をそのまま出し、t_k+1 で切り替える
   （元の切り替わり時刻はそのまま保たれる）

`vfi2/retime.py` は 1〜4 のうち **時刻の計算だけ**を持ちます。model にも素材にも
依存しないので、`python retime.py` で自己検査が回ります（8項目）。
判定（cut・静止・大変位）は呼び出し側が bool の配列にして渡す形にしてあります。

---

## 3. 設計判断

### 3.1 絵の代表時刻は run の先頭に置く

run の先頭（`t_k = r_k / fps`）か、run の中央（`r_k + (L_k-1)/2`）か。
コマ打ちが一定な所では両者は必ず同じ tau を出すので、**割れるのは
コマ打ちが混在する所だけ**です。そこを別掲して測りました。

3つ組 D_k-1, D_k, D_k+1 の真ん中を両端から作り、本物と比べます（正解あり）。

| clip | 3つ組 | うち割れる組 | LPIPS head | LPIPS center | LPIPS tau=0.5 固定 | 割れる組だけ head | 割れる組だけ center | tau を振った最良 |
|---|---|---|---|---|---|---|---|---|
| A_op | 305 | 52 | 0.14964 | 0.14983 | 0.15030 | 0.13212 | 0.13338 | 0.09302 |
| B_talk | 106 | 29 | 0.01749 | 0.01806 | 0.01749 | 0.02679 | 0.02892 | 0.01069 |
| C_act | 188 | 75 | 0.05982 | 0.06084 | 0.06136 | 0.04844 | 0.05094 | 0.03450 |

**先頭を採ります。** 3本とも head が良く、割れる組だけで見ると差は
B_talk 7.4%・C_act 4.9%・A_op 0.9% です。

schedule ごと突き合わせた試験（5章）では差がもっとはっきり出ます。
中央を代表時刻にすると、出力の時刻が保持長の半分だけ後ろへずれます。
ずれ量が保持長ごとに違うので**一定の遅延ではなく揺れ**になり、
全出力の LPIPS が A_op で 0.101 → 0.244、B_talk で 0.078 → 0.115 に悪化します。

### 3.2 コマ打ちの混在は実測の保持長をそのまま使う（均さない）

均すと動きは一定になりますが、原作者の意図した「溜め」が壊れます。
どちらが良いかは、**張り直した結果が元の絵の位置を再現できるか**で測れます。

均した場合、落とした絵の LPIPS は 3本とも大幅に悪化しました。

| clip | 均さない | 均す | 悪化 |
|---|---|---|---|
| A_op | 0.20638 | 0.23762 | +15.1% |
| B_talk | 0.14015 | 0.20970 | +49.6% |
| C_act | 0.06939 | 0.08108 | +16.8% |

全出力で見るとさらに開きます（B_talk 0.078 → 0.159、C_act 0.028 → 0.044）。
**均しません。** コマ打ちの偏りは誤差ではなく情報です。

3.1 の表の「tau=0.5 固定」列も同じ事を別の角度から言っています。
コマ打ちの比を無視して真ん中を採ると、A_op 0.14964 → 0.15030、
C_act 0.05982 → 0.06136 と悪化します（B_talk は主流が3コマ打ちで
一定なため同値）。

なお `60均し` の出力は比較用に残してあります（`out/*_60均し.mp4`）。
**均すと model 呼び出しが 803 回から 1468 回へ 1.8倍に増えます。**
長い静止が圧縮されて短い pair へ均され、そこに出力時刻が集中するためで、
**遅くなったうえに元の間合いが壊れます**。

### 3.3 意図的な静止は保持 9 frame 以上で封じる

96 frame（4秒）保持された絵と次の絵の間を補間すると、**4秒かけて次の絵へ
溶ける**という、元には無い動きを作ってしまいます。元は 4秒止めてから
1 frame で切り替えています。

閾値は保持長の分布の切れ目から採りました（1章の表）。B_talk は 1〜4 frame に
120枚、5〜8 に 3枚、9以上に 9枚と、8 と 9 の間で分かれます。C_act も同じ形です。
**保持が 9 frame（0.375秒）以上の pair を封じます。**

この判定が本当に静止を捕まえているかを画素で確かめました。

| clip | 区間 | 保持 | 先頭との box4 最大 | 48 を超える画素 最大 |
|---|---|---|---|---|
| B_talk | frame 619-714 | 96 | 3 | 0 |
| B_talk | frame 259-342 | 84 | 5 | 0 |
| B_talk | frame 173-226 | 54 | 3 | 0 |
| C_act | frame 382-441 | 60 | 3 | 0 |
| C_act | frame 526-574 | 49 | 7 | 0 |
| C_act | frame 59-103 | 45 | 9 | 0 |

判定の閾値 16 に対して box4 は最大 9、48 を超える画素は 1つもありません。
**完全な静止画です。** ここは補間の対象ではありません。

### 3.4 cut は跨がない

3つ組が cut を跨ぐ場合の LPIPS。

| clip | 組数 | model | hold | blend |
|---|---|---|---|---|
| A_op | 73 | 0.44336 | 0.33315 | 0.33003 |
| B_talk | 12 | 0.40687 | 0.26085 | 0.30174 |
| C_act | 25 | 0.20798 | 0.30611 | 0.15181 |

A_op と B_talk では model が hold の 1.3〜1.6倍悪く、C_act でも blend に
負けます（C_act で model が hold に勝っているのは、scdet が閃光を cut と
判定している組が混ざっているためで、真の cut の証拠にはなりません）。
**cut を跨ぐ pair は封じます。**

### 3.5 大変位は 64px で封じる

前回の検証では「跨ぐ変位が 32px を超えると model は単純平均に負ける」でした。
絵の列で補間すると跨ぐ間隔が広がるので、この領域に入りやすくなります。
3本の素材で測り直しました（横軸は model が実際に跨ぐ変位）。

<!--GATE-->

閾値は **32px と 64px と関門なしを schedule ごと突き合わせて**決めました
（5章の試験）。落とした絵の LPIPS:

| clip | 補間しない | 32px | 64px | 関門なし |
|---|---|---|---|---|
| A_op | 0.19829 | 0.19907 | 0.20638 | 0.22085 |
| B_talk | 0.14116 | 0.14134 | **0.14015** | 0.14015 |
| C_act | 0.07343 | 0.07317 | **0.06939** | 0.07116 |

**64px を採ります。** B_talk と C_act では 64px が最良で、補間しない場合を
下回ります（C_act は 5.5% 改善）。32px にすると B_talk の一番効く帯
（32〜64px で model 0.0443 対 hold 0.0939、model が 2.1倍良い）を捨てることに
なります。

**A_op ではどの閾値でも「補間しない」に勝てません。** これは隠さず書きます。
OP は絵と絵の変位が中央 36.4px あり、この試験（絵を1枚おきに間引くので
間隔が本番の2倍）では 72px 相当を跨ぐことになるためです。本番の間隔では
36.4px なので関門の内側に入りますが、model が明確に得をする帯ではありません。

小変位側にも関門を置くかは検討して**置きませんでした**。0〜4px の帯では
model が hold に負けます（B_talk 0.00736 対 0.00416、C_act 0.00920 対
0.00600）。ただしこの帯は口パクや瞬きのような「移動ではない変化」で、
正解の絵の側がそもそも中間を持たない（パッと切り替わる）ため、
中間を作れば必ず負ける測り方になっています。差の絶対値は LPIPS で 0.003 で、
**ここを封じると B_talk の pair の半分が消えて張り直しの意味が無くなります**。
払っている代価として数字を残します。

### 3.6 目標 fps は 60 を既定にする

- **48（正確には 47.952 = 元の2倍）**: 出力時刻が元の frame 時刻と正確に
  重なるので、絵の列に対する補間でも元の絵がそのまま出る frame が残ります。
  ただし 60Hz の画面では 5:4 の判定になり、揃いません。
- **60**: 元の frame 時刻とは重ならないので、封じた区間以外は
  **すべて生成 frame**になります。5章の試験はまさにその代価を測っており、
  B_talk で LPIPS 0.078（元の絵をそのまま出す場合は 0.077）と、実質的に
  差がありません。60Hz の画面と揃います。
- **120**: 出力 frame が倍になり処理も倍（B_talk 9.2秒 → 16.6秒）ですが、
  異なる絵の枚数は 27.3/秒 → 54.1/秒 と、封じていない区間では確かに増えます。
  120Hz の画面が前提なので既定にはしません。比較用に出力してあります。

**60 を既定にします。**

## 4. 実装

| file | 役割 |
|---|---|
| `retime.py` | 絵の列 → 出力 schedule。**model にも素材にも依存しない純粋な計算**。`python retime.py` で自己検査 |
| `r_model.py` | model 呼び出しの薄い層。中身は `../vfi/rifelib.py` の `Rife`。別 Agent の `vfimodels.py` / `runner.py` が出来たらここだけ差し替える |
| `r1_cadence.py` | 絵の列・保持長・pair ごとの変位・cut を実測 |
| `r2_anchor.py` | 代表時刻（先頭 / 中央）を tau 掃引で決める |
| `r3_gate.py` | cut・大変位・尺の関門を model / hold / blend の対照で決める |
| `r4_recon.py` | 絵を1枚おきに間引いて張り直し、元の frame と突き合わせる |
| `r5_render.py` | schedule を流して出力 file を作り、実効速度を測る |
| `r6_smooth.py` | 出力の滑らかさを共通 metric（`smooth.py`）で測る |
| `r7_look.py` | 比較動画を作る |
| `r8_report.py` | `results.jsonl` から本書の表を組み立てる |

`retime.py` の中心は `build(runs, n_frames, fps_in, fps_out, anchor, block, even)`
だけで、`block` は「この pair は補間しない」という bool の配列です。
判定の中身（cut / 保持長 / 変位）は呼び出し側（`r5_render.schedule_for`）に
あるので、判定を変えても時刻の計算には触りません。

出力側は素材を1回だけ順に decode し、schedule が要る「絵の先頭 frame」だけを
GPU に残します。schedule の絵 index は単調に進むので、GPU 上に置くのは
常に2枚で足ります。

model は `v4.6`（fp16 TensorRT）を使いました。前回の検証で 5.32ms/回と最速級で、
品質が最良の `v4.25_lite` との差は LPIPS 0.0162 対 0.0153 しかありません。
**張り直しは model 呼び出し回数を桁で増やす**ので、速い側を選んでいます。

## 5. 正解が無い出力をどう評価したか

時刻を張り直した出力の frame には、対応する本物がありません。
測り方を2つ用意しました。

### (a) 絵を1枚おきに間引いて復元する（正解あり）

絵 D_0, D_2, D_4, … だけを残し、落とした絵の frame は直前の絵で埋めた素材を
作ります（限定 animation で実際に起きている形そのものです）。この素材の
絵の列に対して、**元の frame 時刻**へ張り直します。出力 frame は元の frame と
1対1で対応するので、全部に正解があります。

- 残した絵に当たる出力 → copy で一致するはず（実装の検算になる）
- 落とした絵に当たる出力 → model が作る。**ここが試験**

跨ぐ間隔が本番の2倍になるので、**本番より辛い側**の数字が出ます。
代表時刻・関門の閾値・均しの有無を、この1つの試験で横並びに比べています。
落とした絵に当たる出力は A_op 364 / B_talk 392 / C_act 256 frame です。

### (b) 滑らかさ（正解なし・共通 metric）

`vfi2/smooth.py`（別 Agent が作った共通の判定軸）で測ります。

- `lag_px` … 時刻 t に出ているべき絵と実際に出ている絵の**位置のずれ(px)**。主指標
- `step_px` … 隣接する出力 frame 間の跳び幅(px)。副指標

この2つを分けないと「効いた/効かない」が判定できません。`lag_px` は保持の
長さで決まり **frame rate を上げただけでは減りません**。`step_px` は
frame rate に反比例して減ります。素直な x2 が効かないのはこの非対称が理由です。

### (c) 数えられる物

出力 frame 数・1秒あたりの異なる絵の枚数・複製でしかない出力 frame の割合を、
**schedule から（画素を見ずに）** と **出力 file から（画素で）** の両方で
出しています。前者は設計の意図、後者は実際に起きた事です。
