# 切り出し成果物の在り処

切り出したmp4と再生画面から撮ったスクショ(png)、切り抜きへ添えた字幕file(srt/vtt/ass)が
**どこに出来るか**と、それを画面から辿る経路をまとめる。時刻軸の扱い(IN点がどこに着地するか)は
`CLIP_TIMEBASE.md`、字幕fileの中身と原点は `CLIP_SUBTITLES.md` が持つ。ここは置き場と
名乗りだけを扱う。

## 置き場

```
<一時保存先(work root)>/<配信者unique_id>/_clips/          切り出しmp4・reel・作品
<一時保存先(work root)>/<配信者unique_id>/_screenshots/    スクショ(png)・shortの表紙
```

置き場は**配信者folderの下**で、同じfolderに録画の素材(`ts/`)と元mp4(`mp4/`)が並ぶ。
配信者ごとの片付け — folderごと消す(`scripts/purge_streamers.py`)・別driveへ移す・容量を
見る — が、録画と成果物で別の場所を指さないようにするためである。

**動画と静止画はdirを分ける**。決め方(work root固定・配信者folderの下・file名の規約)は
どちらも同じで、違うのはdir名だけである。切り出しmp4が数百本並ぶ中に1枚ずつpngが混ざると、
file managerで開いたときにどちらの成果物も目で追えない。分けても一覧・移動・容量・片付けは
`layout.iter_clip_dirs()` が返す**両方**を見るので、画面から辿る口は1つのままである。

**作る先は常に一時保存先**である。`tictok/core/layout.py` の `clip_output_dir()` /
`still_output_dir()` が唯一の決定点で、`clipper.clip_path()` / `reel.reel_path()` /
`work.work_path()` / `work.scene_cache_dir()` が前者を、`clipper.still_path()` が後者を使う。
録画がどちらのrootに在るかは出力先に影響しない。

配信者を読み取れないstem(規約外の名前)から出た成果物だけは、root直下の `<root>/_clips/` /
`<root>/_screenshots/` へ落ちる。録画自体が同じ条件でroot直下へ落ちる(`layout.mp4_dir`)ので、
置き場の決め方を揃えてある。一覧・移動・容量の集計はどちらの置き場も見る
(`layout.iter_clip_dirs`)。

以前は録画の所在(`layout.record_root_of`)でrootを決めていた。切り出しはDBに行を持たず
file systemだけが台帳なので、これは「同じ操作なのに成果物の在り処が録画ごとに変わり、人には
辿れない」という状態そのものだった(実測2026-08-08: 一時保存先に7本、最終保存先に11本)。

最終保存先へ移るのは容量画面の**「最終保存先へ移動」で録画に随伴したとき**だけである
(`tictok/api/disk.py` の `_clip_relocation_items` / `_relocate_clip_group`)。移し先は
rootからの**同じ相対位置**なので、最終保存先でも `<最終保存先>/<配信者>/_clips/`(スクショは
`_screenshots/`)になる。判断は
「その録画が最終保存先に在るか」の一点で、成果物が録画より先に移ることはない。録画を移した
後に切り出した分(一時保存先にだけ在る成果物)も、次の移動で拾う。持ち主の分からない成果物
(録画の行が消えたもの)は動かさず、件数だけ計画に出す。

したがって「出力済みclip」tabは今も**両rootを見る**: 一時保存先には新しく作った物、
最終保存先には録画ごと移し終えた物が在る。

作品のシーンcache(`.scenes`)と落ちた回の中間dirは移動しない。焼き直しは常に一時保存先で
走るので、cacheが付いて行くと次回必ず外れる。

移行(いずれも1度きり。既定はdry-runで、`--apply` で実行):

* `scripts/migrate_clips_layout.py` — root直下の `<root>/_clips/<配信者>/` に在る実体を
  `<root>/<配信者>/_clips/` へ移す。両rootが対象(最終保存先にも随伴済みの実体が在る)。
  `<root>/_clips/` 直下のfile(配信者dirに入っていないもの)は受け皿の中身なので動かさない
* `scripts/consolidate_clips.py` — それ以前、出力先が録画の所在で決まっていた頃に最終保存先へ
  出てしまった分を一時保存先へ引き取る
* `scripts/migrate_stills_layout.py` — `_clips` に在るスクショ(png)を `_screenshots` へ移す。
  両rootが対象。動かすのは `parse_clip_name()` が `still` と読む名前のpngだけで、規約外の
  名前のpngとcache(`.scenes`)・中間dirの中身には触れない

録画横断のpool(avatars/emotes/gift_icons)とは基準が違う。あちらはwork root固定
(`layout.pool_root`)で、混同すると移送済み録画のavatarが1件も解決できなくなる。

## file名

```
<元録画のstem>_<開始HHMMSS>-<終了HHMMSS>[_ラベル].mp4          切り出し
<元録画のstem>_<開始HHMMSS>-<終了HHMMSS>[_ラベル].overlay.mp4  焼き込み切り抜き
<元録画のstem>_reel<件数>_<開始>-<終了>[_ラベル].mp4            連結(reel)
<元録画のstem>_shot<位置HHMMSSCC>[_ラベル].png                 スクショ
<元録画のstem>_shot<位置HHMMSSCC>[_ラベル].overlay.png         スクショ(焼き込みから)
<元録画のstem>_shot<位置HHMMSSCC>[_ラベル].up.png              スクショ(Up出力から)
```

stem は `NNNNN_<配信者>_YYYYMMDD_HHMMSS`。ラベルは**見どころのメモ**(`bookmarks.memo`)で、
file名に使えない文字だけを落として40文字で切る(検索語をそのまま使えるよう日本語は落とさない)。

以前はメモ(見どころ)とラベル(切り出し)が別の表の別の列で、片方を直すともう片方が古い言葉の
まま残った。表を統合したので列は1つで、揃える仕組みそのものが要らない。

同じ範囲・同じ版で作り直すと**同じfileを上書きする**。履歴は残らない。

切り出しの秒はいずれも**要求した範囲**である。高速(stream copy)で切ると実際の内容は直前の
keyframeまで手前へ伸びるため、file名の開始秒より前から始まる。名前から実尺は分からない。

スクショの秒だけは逆に**実際に採れたframeの位置**である(下2桁は1/100秒)。1 frameがそのまま
成果物なので、名前が中身と食い違わないことを優先している。秒へ丸めないのも同じ理由で、
同じ秒の中で位置を変えて撮った2枚が同じfileを奪い合わないようにするためである。

読み戻しは `clipper.parse_clip_name()` が唯一の実装で、組み立て側と対で直すこと。読めない
名前には素性を作らず `None` を返す(一覧は「規約外」として素通しさせる)。

## 画面から辿る

| 経路 | どこで在り処が分かるか |
|---|---|
| mp4切り出し(単発・その場で切る) | 再生画面の状態欄に出力path |
| mp4切り出し(素材版=焼き込みで全尺出力が無い) | queueへ載る。完了時に状態欄へ出力path |
| mp4を一括書き出し | 完了時に見どころtabの状態欄へ出力先dir。Job画面の結果列にも出る |
| 1本に連結(reel) | 完了時に状態欄へ出力path |
| スクショ | 完了時にtoastと状態欄へ出力path(押した場所に依らずtoastで届く) |
| 出来上がったfileそのもの | 配信者動画の「出力済みclip」tab(`GET /api/clips`) |

「出力済みclip」tabは両rootの置き場(`layout.iter_clip_dirs`)を走査して実物を並べる唯一の
場所で、再生・削除も
ここが持つ。DBには成果物の行が無いので、走査結果が常に唯一の真実である。落ちた回の中間dir
(`.clip_*` / `.smartcut-*` / `.precise_*`)は成果物として数えず、件数だけ別に出す。

## スクショ(png)

シーン検索・見どころの2画面のplayerに「スクショ」buttonがある(シーン検索は
`S` key でも同じ)。押すと**今表示している1 frame**が原寸のpngで `_screenshots` へ出る。範囲は要らない
(IN/OUTの有無に関わらず押せる)。素材版はシーン検索では**今再生している版**、見どころtabの
playerは常に元録画である(あちらは元録画しか再生しない)。

実装は `tictok/media/still.py`。要点は3つで、いずれも実測に基づく:

1. **読む素材は再生に使ったものと同じ**にする。mp4と素材(.ts)は時間軸が別物なので、HLSで
   再生している録画をmp4から抜くと画面で止めた位置と別の絵が出る
   (`hls_source.plays_from_hls` で判断する)
2. **`-ss` へ要求時刻をそのまま渡さない。** HLS入力は要求より後ろのsegment境界へ着地する。
   実録画(00058_streamer_a)の直接seekは1時間地点で **要求+2.88秒**、2時間地点で **+2.90秒**
   だった。数秒手前から復号して `select='gte(t,要求)'` で採ると +0.001〜0.017秒に収まる
   (`-copyts` + `-itsoffset` でfilterの `t` をmedia軸へ揃える。焼き込みプレビューの1 frame
   抽出と同じ作り)
3. **着地は測って確かめる。** 前置きが足りるかは素材で決まるので、`showinfo` で実際の位置を
   読み、離れていれば前置きを広げて撮り直す。それでも寄らない録画がある(実測: 冒頭10.127秒
   まで映像frameが無い録画)ため、無限には広げず**実際の位置**を返してfile名もその値で付ける。
   要求とずれた場合は画面が「要求 x / 実際 y」と名乗る

所要は実測で **0.3秒**(2時間地点でも同じ。前置きぶんしか復号しないので開始位置に依らない)。

### queueの即時lane

投入は他の成果物と同じ永続queue(`media_job_queue`、kind=`still`)を通る。押した後の結末が
Job画面という同じ場所に出るためである。ただし通常のworkerの列には並べない:

- 通常のworkerは既定2本で、**同じ録画で走っているjobがある間は次を拾わない**
  (`claim_next_pending_media_job`)。長い焼き込みの裏で押した1枚が数時間保存されないことになる
- そこで `INSTANT_KINDS`(現在は `still` のみ)専用のlaneを1本持つ
  (`TICTOK_MEDIA_QUEUE_INSTANT_WORKERS`、既定1)。laneは録画の排他を無視して拾う —
  対象は**録画にも中間fileにも書き込まない種別だけ**で、読んで別fileを1つ出すだけだから安全
- 順番の優先度(`STILL_JOB_PRIORITY`)とは別物である。priorityは待機列の順、laneは枠

同じ録画から連続して撮れるよう、録画単位の二重投入judge(`_NO_PER_RECORDING_DEDUPE`)は通さない。
位置が違えば別の1枚である。

## 誰が消すか

**誰も自動では消さない。**

- 保持policy(`record/retention.py`)の対象外。日数で捨ててよい派生物ではなく、人が範囲を
  選んで作った成果物であるため
- 録画の削除に道連れされない(`api/files.py` の `_recording_derived_paths` の範囲外)。
  元録画が消えた切り出しも実在する成果物なので、一覧は素性なしのまま並べる
- 「派生物を削除」(焼き込み・Up出力・cache)にも含まれない

「最終保存先へ移動」は消す操作ではない(録画に合わせて置き場を変えるだけ)。
消す口は「出力済みclip」tabの削除だけである。容量画面には種別「切り出しclip」として合計bytesが
出る(`record/disk_scan.py`)ので、増え方はそちらで見る。スクショも同じ扱いで、同じ場所から消す。

## 見どころ(素材の候補)との関係

`bookmarks` 表は**範囲の候補**であって成果物ではない。尺(`end`)を持つ行だけがmp4にでき、
点は「後でまた見たい場所」として残る。元の録画のpathと最後に書き出した日時は一覧の列では
なく**行のtooltip**が持つ(どちらも範囲を詰める・並べるという普段の作業では読まない値で、
列にすると位置・尺・メモの幅を奪うだけだった)。

一括書き出しは由来の行へ `exported_at` / `exported_path` を書き戻す。これは「いつ・どこへ
出したか」という**過去の事実**で、今もそのfileが在るという意味ではない(出力先の掃除はDBを
通らない)。在るかどうかは「出力済みclip」tabが実物を見て答える。範囲を直しても消さない —
その出力fileは今も在るからで、次に書き出せば新しいpathで上書きされる。

2026-08-15までは切り出し候補を `cut_list` という別表に持ち、範囲付きの見どころを『昇格』で
写していた。分けた理由は「グループごとにIN/OUTの詰め方が変わるので所属を共有できない」
だったが、実データでは21件中20件が範囲もグループもラベルも一致し、詰め直しは一度も
起きなかった。表を1つに畳み、グループを跨いで別々に詰めたい場合は行ごと複製する。

## 同じ範囲の行を増やさない

shortの自動生成も作った範囲を見どころへ書き戻す(`_record_short_cut`)。同じ場面を二度
出さないための `taken` は範囲を決める時に一度読むだけなので、同じ録画へjobが重なると双方が
同じ台帳を見て同じ範囲を作る。**台帳へ書くこの1箇所が最後の関門**で、同じ録画の同じ範囲
(端の差が1 frame以下 = `CUT_SAME_RANGE_TOLERANCE`)の行が既に在れば、行を増やさずその行を
書き出し済みにする。

機械が新しく作る行は `origin='auto'` で入る。人が付けた印と混ぜて並べると、覚えの無い行が
一覧を埋めるので、画面は既定でこれを出さない(「自動生成も出す」で呼び出す)。既に在る行の
`origin` は動かさない — 人が付けた見どころと同じ範囲を機械が作っても、その行は機械の物に
ならない。

既に在る重複は自動では消さない。一覧の行が「重複n」を名乗り(同じ範囲の件数と所属グループを
tooltipで出す)、どちらを残すかは1列目の「視聴」で中身を観て決める。
グループ間の複製(`bulk` の `copy`)は意図的な操作なので、この印は出るが妨げない。

始末は「重複を選ぶ」→「選択を削除」の2手に分ける。押した瞬間に消える口は作らない
(どちらを残すかは中身を観て決める物である)。選ぶのは表示中の行のうち**同じグループに同じ
範囲が2行在る**組の2件目以降で、各組の先頭は残す。印が範囲だけで数える(list全体)のに対し
選ぶ側がグループまで見るのは、別グループの片割れが上記の意図的な複製だからである。

行が増える口は3つしかない: 人が入れる(再生画面の「見どころに記録」)、グループ間の `copy`、
shortの自動生成の書き戻し。**書き出し(一括書き出し・連結・作品)は行を増やさない** —
`exported_at` / `exported_path` を既存の行へ書き戻すだけである。
逆に、行を消すとその範囲は `taken`(`_short_taken_ranges` = 範囲を持つ見どころそのもの)から
消えるので、同じ録画へshortの自動生成をもう一度かければ同じ場面が再び選ばれ、行として
戻ってくる。

## 並び

グループを選んでいる間は `position` 順(=書き出し順)。選んでいない間(「全て」「未分類」)は
**配信日順**で、同じ配信の中は開始位置順にする。そこに並ぶのは書き出し順を持たない行で、
並べる根拠になるのは素材の時間軸しかないためである。表の「順」は行の属性ではなく**表示順
そのもの**で、グループ未選択時は意味を持たないため列ごと畳まれる(`vd-cutlist-flat`)。
「出所」列も同じで、自動生成を出していない間は畳まれる(`vd-hide-origin`)。

書き出し順はグループを選んでいる間、**行を別の行の上へドラッグ**して変えられる
(`POST /api/groups/{id}/order`)。掴んだ行を一度抜いてから落とした行の手前へ入れ、複数選択
していれば表示順のまま連れて行く。並びは作品と連結が繋ぐ順そのものなのに、これまで画面に
変える手段が1つも無く、行を入れた順のまま固定されていた。

完成尺の中での開始位置を出す「頭出し」列は廃した。同じ範囲の行でも並びの位置が違えば違う
値になる(上から尺を積み上げた累計であるため)ので、行の値と読み違える形でしか使われず、
位置・尺・メモの幅を奪うだけだった。

## 位置と尺を変える

一覧の「位置」「尺」は入力欄で、2つは独立に効く(位置は窓ごと動かして尺を保ち、尺は位置を
据えたまま終端だけを動かす)。尺の欄を空にすると点へ戻り、点の尺欄に長さを入れれば範囲に
なる。範囲を詰める作業は「あと少し」の繰り返しなので、絶対時刻の打ち直しだけを口にしない:

- `1:23:45.6` / `23:45` / `45.6` の絶対時刻
- `+2` / `-1.5` のように符号を付けると、**今の値からの増減**
- 欄にfocusしたまま `↑` `↓` で ±0.1秒(shiftで±1秒・altで±10秒)
- 尺の候補は作品の型(`clip_presets.target_seconds`)から引く(`<datalist>`)

視聴paneの「頭を今に」「今までを尺に」は、観ている再生位置で端を決める。時刻を打ち直すより
観ながら決める方が速くて正しい(何秒かは覚えていないが、ここから、というのは見れば判る)。

配信中に押した見どころ(`pts_mapped=0`)だけは、録画の確定まで欄を触らせない。startは
wall-clockから出した暫定値で、finalizeでPTS軸へ載せ直されるためである。
