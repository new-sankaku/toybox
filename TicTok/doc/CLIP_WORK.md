# 切り抜き作品（複数シーンの完成品）

グループ（`clip_groups`）1件を、投稿できるmp4 1本にする経路。

## なぜ新しい段が要るのか

既存には出口が2つあり、どちらも「複数シーンの完成品」にならない。

| 既存 | 入口 | 出口 |
|---|---|---|
| `reel`（切り出しの連結） | N シーン | stream copyで繋いだだけ。テロップも音も足せない |
| `short` | **1** シーン | 焼き込み・間の詰め・高画質化・検品・題名まで通った完成品 |

`short` は仕上げ工程を全部持っているが入口が1シーンしかなく、`reel` は N シーンを受けるが
仕上げ工程を1つも通らない。**この2つを繋ぐのがここで作るもの**で、job kind は `work`
（画面では「作品の書き出し」）。`reel` は消さない — 素材を通しで俯瞰するのに数秒で出る
ことがその価値で、仕上げを通すとその速さが失われる。

設計図の側は既に在る。範囲を持つ見どころ(`bookmarks`)の行が1シーン、`group_id` が所属、
`position` が繋ぐ順で、`recording_id` は行ごとに持つので**複数の録画を跨いだ作品が最初から
表現できる**。尺を持たない行(点)は素材にならないので外し、外した件数は結果で名乗る。

## 段の並び

```
グループ（見どころを position 順）
  │
  ├─ シーンごと ── 原本の時刻軸 ────────────────────
  │    切り出し(precise)
  │    焼き込み … テロップ / コメント / ギフト / スコアバー
  │    間の詰め … 無音を落とす
  │
  ├─ 連結 ── ここから作品の時刻軸 ──────────────────
  │    解像度・codecを揃える
  │    シーン間の転換
  │    効果音
  │    通しBGM / 通しのラウドネス
  │
  ├─ 高画質化 … 作品全体に**1回だけ**
  │
  └─ 検品 → 題名・説明・hashtag・表紙
```

### 時刻軸が2つに割れる理由

演出をどこへ置くかは好みではなく、**その要素が何の時刻を持っているか**で決まる。

* テロップ・コメント・ギフトは**原本の時刻**を持つ。シーンごとに元の録画も位置も違うので、
  連結後にまとめて焼くことはできない。→ シーンの段
* 転換・効果音・BGM・シーン番号は**連結して初めて存在する**。原本にはその時刻が無い。
  → 作品の段

副次的な利点として、焼き込みの filter graph へ演出を積まずに済む。既存の焼き込みは個人
マルチの描画で 32KB 上限に接触した実績があり、同じgraphへ演出を足すと壊れる。

### 高画質化を作品全体に1回だけ掛ける

現在の `short` はシーンごとに掛けている。作品でそれをやると **GPU時間が シーン数倍**になる。
Up出力は実時間の数倍かかる工程なので、ここは作品の段へ移す。

副産物として、シーンの段の出力は中間物になる。中間はグループの作業dirへ置き、成果物が
出来た時点で消す（`short.py` の workdir と同じ決め方で、出力と同じvolumeへ置く）。

## 複数の録画を跨ぐ

跨げることを前提に作る。`concat.check_compatible` が既に解像度・codecを照合しているが、
**揃わないときに拒否するのではなく揃える**。素材が揃わないのは配信側の都合であって
利用者の操作ミスではなく、拒否すると「この5シーンは作品にできません」としか言えない。

揃え方は finalize の混在解像度対応と同じ（単一解像度へ再encode）。作品はどのみち全編
再encodeを通るので、追加の世代は増えない。

どの寸法へ揃えるかは**シーンの多数決ではなく最大**を採る。多数決だと、1シーンだけ高い
ものが引き伸ばしで潰れる。

## 効果音

`assets/sfx/` へ置き、`fonts.py` と同じ方式で初回だけ取得する（manifest + SHA-256 の固定）。
repoへ binary を入れないのと、上流が別の物を配り始めたときに黙って別の音で焼かないため。

**CC0（権利放棄済み）のみを採る。** 帰属表示が要る licence を混ぜると、成果物の投稿ごとに
表記の義務が付いて回り、それを機械が保証できない。出所と licence は `assets/sfx/README.md`
と成果物の sidecar の両方へ書く。

取得に失敗したら**焼き込みと同じく演出を止める**（別の音で代替しない）。

### 引き金は既に検出済みのものだけを使う

音を鳴らす場所を新しく検出しない。既に在る観測だけを使う:

| 引き金 | 出所 |
|---|---|
| シーンの継ぎ目 | 連結の接合点（作品の段が自分で知っている） |
| 笑いの山 | `laugh_audio` / `laugh_text` |
| ギフト着弾 | events |
| Battle の開始・終了 | `battles` |
| 作品の頭・尻 | 自明 |

**密度に上限を置く**（n秒に1回まで）。入れすぎが品質を落とす主因で、上限が無いと
ギフトが連続した区間で音が重なって潰れる。

ダッキング（本編の音を一時的に下げる）は既定OFF。配信音声は源が HE-AAC 67k で既に痩せて
おり、下げると聞こえなくなる。

## 型（clip_presets）

既存の `clip_presets` は「1シーンの作り方」だった。作品用の列（転換の種類・BGM・効果音の
密度・シーン番号を出すか）を**同じ表へ足す**。

シーンの型と作品の型を別表にしないのは、利用者が型を2つ選ぶことになり、組み合わせの
数だけ「試していない組」が生まれるため。1行が「この作品をどう作るか」を全部持つ。

## 検品

`clip_gate` を作品単位で通す。シーン単位では通さない — 1シーンが黒い作品を落とすべきか
どうかは作品を見ないと決まらず、シーンで落とすと「N-1シーンの作品」が黙って出る。

作品固有の項目を足す:

* 接合点で映像・音声が途切れていないか（reel で実測した穴と同じ検査）
* 効果音が本編を潰していないか（区間ラウドネスの差）
* シーン数が要求どおりか

落ちても成果物は消さない（既存の作法どおり）。

## 題名・説明

N シーンぶんの文字起こしをまとめて局所LLMへ渡す。秒はmodelに書かせない（章立て・`clip_meta` と
同じ約束）。表紙は**シーンの原本**から撮る — 作品から撮ると間の詰めと連結で動いた分を
写し直す必要がある。

cacheの `target_id` は `group:<group_id>` とし、グループの内容が変われば作り直す。

## 自動化の範囲

**候補までを機械が出し、どれを使うかは人が決める。**

```
録画おわり → 文字起こし → 盛り上がりを探す → グループの下書きを作る
                                                  ↓
                                        人が棚で○×を付けて「作品にする」
```

全自動で作品まで作らないのは、盛り上がり検出が答えられるのが「笑いが起きた場所」までで
「面白いか」ではないため。外れの回に高画質化のGPU時間を丸ごと使う。

下書きは未分類ではなく**下書きのグループ**として作る。未分類へ入れると、人が作った棚と
機械が出した候補が同じ場所で混ざる。

## 実装の順序

| # | 内容 | これで何ができるか | 状態 |
|---|---|---|---|
| 1 | `work` job（シーン仕上げ + 連結 + 検品） | **N シーンのテロップ入り完成品が出る** | **実装済** |
| 2 | 効果音 | 継ぎ目・テロップに音が入る | **実装済**（ギフトは素材のみ・未配線） |
| 3 | 映像エフェクト（ズーム・フラッシュ・速度） | 「編集されている」見た目になる | 未着手 |
| 4 | 強調テロップ（語単位） | 一語だけ色とサイズが変わる | 未着手 |
| 5 | グループ下書きの自動作成 | 朝、候補が棚に並んでいる | 未着手 |

1 が終わった時点で目的の物（複数シーンの完成品）は手に入る。2〜5 は見栄えと手間の削減で、
1 に依存する。

### 効果音を置く場所（2 の前提）

引き金は**既にミリ秒で時刻が分かっているものだけ**を使う。検出の粗さがそのまま音のズレに
なるためで、盛り上がり候補は10秒bucket・笑い声は1秒刻み（窓2秒 / hop 1秒）で、どちらも
音を置ける精度ではない。

| 引き金 | 出所 | 精度 |
|---|---|---|
| シーンの継ぎ目 | 連結が自分で作る時刻 | ミリ秒 |
| テロップの出現 | 文字起こしsegmentの開始 | ミリ秒 |
| ギフト着弾・Battle開始終了 | event の時刻 | ミリ秒 |
| 衝撃・間 | 音量の急変（未実装・spectral flux） | 10ms |
| 笑いの山 | `laugh_audio` | **1秒。足りない** |

笑いを引き金にするのは、立ち上がりを別に取り直してからにする。この5つのうち笑いだけが
粗く、そこを土台に据えると他の4つまで巻き込んで倒れる。

実装は `tictok/media/sfx.py`（型の `sfx` 列で on/off・既定 off）。素材の選び方と落ちた
候補の内訳は `assets/sfx/README.md`。

### 実素材で測って分かったこと

3シーン54秒の作品を作り、**効果音なしの版と音を差分**して、差が出た時刻を計画と突き合わせた。

* 継ぎ目の音は計画どおり **18.03s / 36.09s** に入っていた（部分尺の積算そのもの）
* **継ぎ目とテロップが同一msへ重なっていた。** シーンの頭は発話の開始へ吸着させるので、
  「継ぎ目 ＝ そのシーン最初のテロップ」は例外ではなく**必ず起きる**。2音が同時に鳴れば
  1つの濁った塊にしかならないので、種類を跨いだ間引き（`MIN_CROSS_GAP_SECONDS`）を足した。
  直後の再測定で計画10箇所すべてが一致した
* 差分法は本編が大きい箇所（-8〜-25dB）で偽陽性を出す。AAC 再encodeの差なので、静かな
  箇所での一致だけを根拠に採ること

この2つ目は、件数（「12箇所置いた」）を見ている限り絶対に出てこない。**成果物を測る**まで
分からなかった種類の欠陥である。

### 窓焼き込みが要求より1.5秒後ろから始まっていた（既存の欠陥・修正済み）

「セリフとテロップが合っていない」という指摘から掘って見つかった、**範囲焼き込みそのものの
欠陥**。作品・short・範囲焼き込みの全部が踏んでいた。

`_run_ffmpeg` の窓経路が `-ss` へ `win_start + media_offset` を渡していた。しかし `-ss` は
**media軸**で、container start_time は ffmpeg 側が足す（`media/concat.py` が実測で確立した
規則と同じ）。足し戻しは二重計上になる。

映像だけが後ろへずれ、字幕・コメント・ギフトは要求どおりの軸へ置かれるので、**焼いた物が
全部およそ1.5秒遅れて出ていた**。

実HLS録画3本を音の相互相関で測った（一致度0.98〜0.997）:

| シーン | 修正前 | 修正後 |
|---|---|---|
| 725.76s 要求 | +1.514s | **-0.003s** |
| 1415.13s 要求 | +1.481s | **+0.070s** |
| 2137.54s 要求 | +1.488s | **-0.029s** |

ずれ量は container start_time の実測値（1.517秒）そのもの。`_signature` の版を30→31へ上げて
既存cacheを無効化してある（上げないと、直した後に焼き直しても古い出力へcache hitする）。

**この欠陥は「文字起こしと焼いた文字を突き合わせる」検証では絶対に出ない。** どちらも同じ文字起こしから
出るので必ず一致する（実際そう測れて、一度は「合っている」と報告した）。外部の基準——原本の
映像・音そのもの——と突き合わせて初めて出た。

## 微調整できること

作品は「押す → 数分待つ → 1本出る」の箱にしてはいけない。1シーンの端が0.5秒ずれている
だけで全部やり直しなら、人は直すのをやめる。

* **IN/OUT を後から直せる**（`PATCH /api/bookmarks/{id}` が start/end を受ける）。直せないと
  0.5秒のために行を消して取り直すことになり、並び(`position`)まで失われる。相対入力(`+2`)と
  ↑↓の刻み、視聴paneの「頭を今に」「今までを尺に」も同じ理由で置いてある
  （[CLIP_OUTPUT.md](CLIP_OUTPUT.md) の「位置と尺を変える」）。
* **繋ぐ順を後から変えられる**（`POST /api/groups/{id}/order`）。一覧で行を別の行の上へ
  ドラッグする。
* **下見**（`GET /api/groups/{id}/work-plan`）。作らずに、何をどの順で繋ぐか・何が焼かれるか・
  作れない行はどれかを返す。
* **シーン単位のcache**（`<配信者>/_clips/.scenes/`）。変わったシーンだけ焼き直す。

### cacheの持ち方

焼き込みのcache判定は **`video_overlay._signature` に任せる**。あれは設定・event・文字起こし・
時刻mapまで見る署名で、30版ぶんの無効化知識が積まれている。ここで組み直せば必ず食い違い、
**設定を変えたのに古い絵が返る**という最も気付きにくい形で壊れる。作品側が自分で判定するのは
焼き込みを通さない切り出し（precise）と、その後段（間の詰め＋TS化）だけである。

そのため下見が名乗るのは「前回作った中間が今も在る」という**事実**までで、「焼き直さない」
とは言わない。焼き込みが焼き直すと決めればその値に関わらず作り直される。

中間は必ず tmp 経由で置き換える。出力pathへ直接書くと、途中で落ちた回に**断片が正しい
partの顔をして残り**、指定を元へ戻した次の回にそれへ cache hit して、切れたシーンを繋いだ
作品が黙って出る。

`.scenes` は成果物として並べず、残骸とも別に数える（`/api/clips` の `cache_*`）。消すべき
fileと、消さない方が得なfileを同じ数字に混ぜると、画面はどちらの意味でも読めない量を出す。

## 実装済みの範囲と、まだ無いもの

`tictok/media/work.py` の `make_work()` と、job kind `work`
（`POST /api/groups/{id}/work`）、見どころtabの「作品にする」まで。

まだ無いもの:

* **`.scenes` の自動掃除が無い。** 今は溜まる一方で、量を `/api/clips` が報告するだけである。
  日数での掃除を retention へ入れるまでは、人が消すしかない。
* **シーンごとの上書きが無い**（このシーンだけテロップ無し、等）。型は作品全体に効く。
* **解像度の違う録画を跨いだグループ**は連結の手前で止まる（`_require_uniform`）。揃える
  処理を入れるまでは、黙って片方へ寄せるより止めて理由を名乗る方を採る。
* **接合点で映像・音声が途切れていないかの実測**は検品に入っていない。今ある尺の照合
  （範囲の合計 − 間の詰め）は、両trackが揃って短く終わった回は捕まえるが、途中の穴は
  尺の合計に現れない。
* **題名・説明・hashtag・表紙**は作っていない（shortにはある）。file名はグループ名を使う。
* **実際に成果物を再生しての確認が済んでいない。** 上記はすべてtestと実codeの範囲の話で、
  出来上がった動画を観ての確認は別に要る。

### 4 が最後になる理由

語単位のテロップには word timestamps が要るが、`transcription.py` の `model.transcribe()`
は今それを要求していない。既存の文字起こしは語の時刻を持たないので**再文字起こしが要る**。ここだけ
既存資産の作り直しを伴うため、他の3つより後ろへ置く。

版で判別して、語時刻を持たない文字起こしでは従来どおり文章単位のテロップを焼く（拒否しない）。
