# シーン検索が索引へ載せる本文

表記ゆれの畳み込み(ウザ = うざ)と、返信の宛先(`@表示名`)を索引から外す話。どちらも
「原文は残し、照合用の本文だけを作り替える」という同じ形をとる。

---

## 表記ゆれ (ウザ = うざ)

## 何が起きていたか

「ウザ」で引くと「うざ」が出なかった。同じ語なのに片方しか出ないので、**その配信には
無い話題**として読めてしまう。原因は照合が全部code point比較だったこと。

- FTS5の`trigram` tokenizer … ASCIIの大小しか畳まない(かなは別文字)
- SQLiteの`LIKE` … 同上。2文字以下のqueryはこちらへ落ちる

そして材料の書き方が揃わない。Whisperの文字起こしは漢字・カタカナ寄りに書き、コメントは人が
打つのでひらがな・全角半角が混ざる。同じ語を探しているのに、材料の側で表記が割れている。

## どうしたか

照合用に畳んだ本文を別に持ち、**索引もqueryも畳んだ形で**突き合わせる。

| | 中身 |
|---|---|
| `search_hits.body` | 原文。画面に出すのはこちら |
| `search_hits.body_norm` | `tictok.search.normalize.index_fold` を通した照合用の本文 |
| `search_fts` | 索引するのは`body_norm`(external content FTS5) |

畳むもの / 畳まないもの:

| 畳む | 例 | 畳まない | 理由 |
|---|---|---|---|
| ひらがな → カタカナ | うざ = ウザ | 濁点・半濁点 | ウザとウサは別語 |
| 半角カナ → 全角カナ | ｱｲｳ = アイウ | 小書き文字 | ッとツは別語 |
| 全角英数記号 → 半角 | ＬＩＶＥ = LIVE | 長音記号 | ー を消すと別語が混ざる |
| 英大文字 → 小文字 | Ramen = ramen | | |
| 全角空白 → 半角空白 | | | |

## 守る前提: 畳み込みは文字数を変えない

一致箇所の強調(`\x02`…`\x03`)は、畳んだ本文で見つけた位置を**そのまま原文へ当てて**
付ける。1文字が2文字になる変換を混ぜると囲む位置がずれるので、`fold`は必ず1文字を1文字へ
写す(testで全Unicodeを走査して担保)。NFKC正規化を使わないのはこれが理由 — NFKCは
`ｶﾞ -> ガ`(2→1)や`㍿ -> 株式会社`(1→4)のように長さを変える。

FTS5の`highlight()`も使わない。索引しているのが`body_norm`なので、返ってくる文字が
「うざい」から「ウザイ」へ化ける。強調は`normalize.mark`がPython側で付ける — 副産物として、
FTSを通らない2文字以下の検索にも同じ強調が付くようになった(以前は付かなかった)。

既知の限界: 半角カナの濁音(`ｻﾞ`)は2文字で1音なので`ザ`へは畳めない(長さが変わる)。
`ｻ゛`までは寄るが`ザ`とは一致しない。文字起こしにもコメントにも実例が無いため許容している。

## 返信の宛先 (`@表示名`) は索引に載せない

### 何が起きていたか

「語で一致」で人の名前を打つと、その人**宛**の返信が全部出てきた。TikTokの返信コメントは
本文の先頭へ `@表示名 ` を置いて送られるので、宛先が本文の一部として索引に載っていた。

実測(索引668,456行):

| | 件数 |
|---|---|
| 本文が`@`で始まるcomment | 7,497 |
| うち宛先が既知の表示名で切れる | 7,075 |
| 例: `✙てぃ🐕໒꒱` を含む行 | 102 → **うち101件が宛先** |

宛先は「誰に向けた発言か」であって発言の中身ではない。名前で場面を探しているのに、
その人への返信で埋まると探しているものが埋もれる。

### どうしたか

`normalize.blank_mention` が先頭の`@表示名`を**空白へ置き換え**てから畳む
(`index_fold = fold(blank_mention(...))`)。原文の`body`は触らないので、画面には
今まで通り `@よい おやすみなさいー` と出る。消さずに空白で埋めるのは、「畳み込みは
文字数を変えない」という上の前提を索引側でも崩さないため。

### 名前をどこで切るか

**最初の空白まで、では切れない。** 表示名そのものに空白を含むものがある
(`Maiza Santos`、`🐉　白　龍　🐉`。先頭メンション7,497件中531件)。空白で切ると名前の後半
(`Santos`)が索引へ残り、その語で引けば結局その人の返信が全部出る。

そこで既知の表示名(`users`表のnicknameとunique_id、実測31.8万件)で**最長一致**を取る。
`Storage.mention_names`が出所で、読み込み0.4秒・TTL 600秒で持つ。当たらないのは我々が
一度も観測していないuserへの返信で(実測422件)、そのときだけ空白で切る。

TTLの間に現れた新規userへの返信は名前で切れず空白へ落ちるが、その録画の索引を張り直せば
直る。常に最新であることより、録画ごとのindex投入で毎回31万件を読まない側を取っている。

**意味検索(embedding)も同じ扱い**。passageに埋め込むのは宛先と話者名を落とした本文で、
画面に出す`body`は`話者名: 発言`のまま(`semantic._flush_passage`の`embed`と`body`)。
話者名を混ぜていた頃は、commentのpassage本文の40.5%が話者名の繰り返しだった。既にindex済みの
passageは張り直すまで古い本文のvectorのまま残る(語で一致と違い、意味検索は版で作り直さない)。

---

## 索引の作り直し

索引へ載せる本文の作り方は`normalize.FOLD_VERSION`で版を持つ。**畳む範囲や宛先の外し方を
変えたら必ず上げること**。索引は投入時の版のまま残るので、上げないと新ruleのqueryが旧ruleの
索引を引き、「その語だけ何も出ない」形で静かに壊れる。

| 版 | 中身 |
|---|---|
| 1 | 表記ゆれの畳み込みのみ |
| 2 | 先頭の返信メンションを外す(`blank_mention`) |

起動時の`Storage._migrate_search_index`が版の食い違いを見て、全行を作り直し
FTSを張り直す(`db_maintenance.search_fold_version`が版marker)。実測(版2 / 668,456行):
表示名の読み込み1.2秒 + 作り直し1.9秒 + FTS再構築4.0秒 + commit 0.6秒 ≒ 8秒。

## 及ばない範囲

意味検索(`/api/search/semantic`)は語ではなくembeddingの近さで引くので、表記ゆれの
畳み込みは通らない(model側が吸収する領域)。宛先と話者名だけは意味検索でも落としている
— 上の「返信の宛先」を参照。
