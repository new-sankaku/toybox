# 最終保存先への退避

作業先(`record_dir`, SSD想定)に残っている完了録画を、最終保存先(`record_dir_final`, HDD想定)
へ移す。画面は動画容量(`/capacity`)の「最終保存先への退避」区画、API は
`GET|POST /api/storage/relocate`。

## なぜ恒常的な機能が要るか

finalize時の `Recorder._relocate_to_final()` は**失敗しても作業先に残す**設計である
(recorder.py: 「On failure the mp4 stays in the working dir」)。偽の最終位置を作らない正しい
判断だが、裏を返すと**失敗のたびに取り残しが積もる**。取り残す要因は複数ある:

- 容量不足 / cross-volume の I/O error / Windowsのfile lock
- **`recording_keep_hls = 1`**: `_relocate_to_final()` は `if not self._keep_hls:` の中でしか
  呼ばれないため、この設定1つで退避そのものが起きなくなる

一度きりの後始末scriptでは、次に同じ状況になったときまた手が要る。

## 常時表示の指標

動画容量画面の先頭に **「一時保存先 N本/X GB → まだ移していない M本/Y GB → 最終保存先 …」**
を常時出す。`/api/capacity` の `placement` に載せてあるので追加の問い合わせは要らない。

取り残しだけでなく**両方の保存先の本数と容量**を出すのは、取り残し0が「移し終えた」のか
「そもそも録画が無い」のかを区別できないため。所在の内訳はDBの `bytes` で出し、fileの
statは取らない(完了録画は数千本あり、画面を開くたび全件statすると数秒待たされる)。実測が
要るのは移動対象だけで、そちらは下記のとおり実sizeを測る。`bytes` 未記録の行は0として
足さず、`unknown_bytes` の件数として別に出す。

この数字が出ていれば、移動が呼ばれていない状態(keep_hls=1 等)に**堆積が始まった時点で
気付ける**。実際、今回は97GB積み上がるまで誰も気付かなかった。

## 画面の語

「退避」は使わない。同じ画面にDBのbackupが並んでおり、以前は**どちらも「退避」**で
別物が同じ語で表示されていた。動画側は **「移動」**、DB側は **「DB backup」** と書く。
保存先の呼び方も設定画面に合わせる(**一時保存先 / 最終保存先**。「作業先/退避先」とは
呼ばない — 設定画面と突き合わせられない)。

## 対象の選び方

「**完了 かつ 作業先配下 かつ 実体がある かつ 退避先に同名が無い**」もののみ。

| 除外するもの | 理由 |
|---|---|
| `status != 'completed'` | 録画中のfileを動かさない。実行直前にも再確認する |
| 作業先の外にあるもの | 既に退避済み |
| **DBにpathがあるが実体が無い** | 移すものが無い。実測で**132本中82本**がこれ(retention削除済み)。件数に混ぜると「82本移せる」という嘘になる |
| 退避先に同名が既にある | 上書きすると既に退避済みの実体を壊す |

容量は**DBの `bytes` ではなく実fileのsize**で数える。実測で16本がDB値と1KB以上ずれており、
移送量として読むならディスク上の実体が正しい。

除外した件数は画面に出す(黙って落とすと件数が合わない理由を辿れない)。

## 移送とDB更新の順序

実体は **`Recorder._move_recording_files(src, dst)` をそのまま使う**。mp4 と、そこから派生する
持続file一式(`relocatable_artifact_paths`)を移す。派生側1件の失敗は致命的でない。
moverを二重に持つと、いずれ片方だけ直されて挙動が分かれる。

> この関数は `self` を一切使っていなかったので `@staticmethod` にした。既存の
> `self._move_recording_files(src, dst)` はそのまま解決するので**呼び出し側の挙動は不変**。
> 過去に終わった録画にはRecorder instanceが無いため、これが最小の再利用手段である。

順序は **移送成功 → DBの `path` を更新** で固定する。

- serverは再生・出力で `recordings.path` の絶対pathをそのまま使う(`_safe_recording_path`)。
  **移動してDBを更新しないと再生が壊れる。**
- 逆に**DBだけ更新するともっと悪い**(存在しないpathを指す)。だから移送が成功した後にだけ書く。
- **失敗したら作業先に残し、DBも更新しない。** 作業先も許可されたrecord rootなので、
  再生も出力もそのまま続く(degradedだが壊れていない)。

## 1本の失敗で全体を止めない

1本がlockされているだけで残り全部を諦めるのは、この機能の目的(取り残しを減らす)に反する。
失敗は件数と理由を集めて報告し、次へ進む。

## 実行はjobに載せる

79GBの移送は分単位かかるため `_tracked_job` に載せる。進捗は本数ベース(`N/M本 filename`)で、
browserを再読込しても復帰でき、job画面から取り消せる(`cancel.check_cancelled()` を本の
区切りで見る)。

## 移送で何を一緒に運ぶか

録画から派生するfileは**mp4の現在地**から解決される(`record_root_of`)。したがってmp4だけを
移すと、残りは旧rootに取り残され、以後どの経路からも参照されなくなる。2026-07-22に実測した
取り残しは **197 file / 12.10GB**:

| 取り残されたもの | 何が起きるか |
|---|---|
| `.overlay.mp4` / `.up.mp4` | 焼き込み・高画質化の**完成品が画面から消える**(6本 12.1GB) |
| `.timing.json` | 焼き込みが概算timingへ落ち、**コメントが動画とズレる**(134本) |
| `.overlay.meta` | cacheが当たらず、**全編を再encode**する(37本) |
| `.thumbs.*` / `.waveform.json` | hover用sprite・波形をffmpegで作り直す |

削除も容量表示もmp4の現在地を基準に列挙するため、録画を消しても旧rootの残骸は永久に残る。
よって**mp4と派生fileは常に一緒に動かす**(`relocatable_artifact_paths`)。列挙元は削除・容量
表示と同じ関数で、定義を二重に持たない。

renderが作って自分で消す中間物(CFR base・comment layer)は運ばない。移送は完了録画にしか
起きず、そこに在る中間物は定義上どのrenderも参照しない孤児で、起動時のsweepが回収する。

過去ぶんの後始末は `scripts/repair_relocated_artifacts.py`(dry-runが既定、`--apply`で実行)。

### 一方で、移送に付いていってはいけないもの

録画横断のpool(`avatars/` `emotes/` `gift_icons/`)は**work rootにただ1つ**置く
(`layout.pool_root`)。書くのは収集時のcollectorで、書き込み先はwork root固定であり、mp4の
現在地では解決できない。ここをmp4基準で解いていたため、**final dirへ移送された録画だけ
avatarが1件も解決できず、全コメントがイニシャル円盤へ黙って縮退していた**(署名付きCDN URLは
失効しており、その場での再取得も効かない)。録画ごとのartifact(`.sidecars/`)とは基準が違う。

## やらないこと

- **`.ts`(HLS)の削除は含めない。** 退避は可逆(退避先にfileが残る)だが、`.ts` 削除は
  不可逆で再処理の材料を失う。同じbuttonに混ぜると事故になる。別機能として扱う
- 退避先から作業先へ戻す操作は用意していない
- `record_dir_final` が未設定/作業先と同じなら**機能ごと表示しない**(移す先が無い)
