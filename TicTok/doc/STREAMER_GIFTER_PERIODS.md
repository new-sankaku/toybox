# 配信者画面のGifter（週と日）

配信者タブの先頭に並ぶ2つの節。どちらも投稿へ貼る文字列を作るための口で、**同じ窓・同じ
行**から数える。実装は `tictok/store/streamers.py` の `streamer_mention_week`、画面は
`static/streamers.js` の「週のメンション」「日のGifter」。

## 週が3種あることを先に押さえる

同じ画面に「週」が3つ在り、境目がそれぞれ違う。取り違えが最悪の結末なので、画面の名乗りには
必ず時刻を入れる。

| 呼び名 | 境目 | 使う場所 |
| --- | --- | --- |
| `week`（暦） | 月曜 0:00 | 期間別ランキング・人×期間の一覧 |
| `week_sat` (`WEEK_SATURDAY`) | 土曜 7:00 | 週のGifter（メンション一覧） |
| `day_shift` (`DAY_SHIFTED`) | 毎日 7:00 | 日のGifter |

時刻は `WEEK_START_HOUR = 7` の1か所だけが持つ。SQL側の式（`_PERIOD_SQL`）とPython側の
`_period_key` / `_period_bounds` が同じ境界を出すこと ―― 片方だけ直すと、期間の一覧と
その中身が別の切り方になり、合計が合わなくなる。

## 日の境目を7時にした理由

投稿の周期に合わせた週が土曜7時始まりなので、**日も同じ時刻で切る**。

- 0時で切ると、深夜まで続く配信が2日に割れる。
- さらに土曜の未明（0〜7時）のGiftが「週は前の週・日は当日」という別々の箱に入り、
  **日ぶんの合計が週の合計と一致しなくなる**。画面はこの一致を根拠に日を並べているので、
  ここが崩れるとどちらが本当か読めない。
- 7時で切れば、週はちょうど7日に分かれる（`test_seven_days_tile_the_week_exactly`）。

日のkeyは**窓が始まる日の日付**。未明の分は前日のkeyへ入るので、終わる日で名乗ると一覧の
並びと日付が1日ずれて読める。

## 日ぶんの貢献（貼る文面）

`days[]` の各要素が1日ぶんで、`post_text` が投稿へそのまま貼る文字列。

```
トップ3貢献
🥇 [表示名] 🥈 [表示名] 🥉 [表示名]
1k⬆️11名
```

- 上位の人数は `MENTION_MEDALS` の長さが決める。見出しの数字もそこから作るので、
  メダルを増減させても文面が食い違わない。
- 「1k⬆️◯名」の下限は `MENTION_POST_MIN`（1,000💎）で、◯は**その日にその額以上を投げた
  人数**。上位3人も含む。0人の日はこの行ごと落とす ―― 「1k⬆️0名」と貼ると、大口が
  居なかったのか数え忘れたのかが貼った先から読めない。
- 表記が小文字（画面の区分名は「1K以上」）なのは、投稿の文面がこの形だからである。
  数字は文面へ直接書かず `_coin_label(MENTION_POST_MIN)` から作る。

### 顔ぶれをそのまま貼る文面（`roster_text`）

上位3人だけでは足りないときの口。札の右に「Top◯」のボタンを置き、`post_text` とは
別に写す。

```
1. [表示名]　5,000
2. [表示名]　4,000
3. [表示名]　3,000
```

- メダルではなく番号で並べる ―― 印の在る3人より下まで載るからである。
- 額まで入れるのは、順位の根拠を貼った先でも読めるようにするため。並びは画面の表と同じ。
- 行数は `_MENTION_DAY_ROSTER`（10人）で顔ぶれと同じ上限。ボタンの題の人数も実際の
  行数から作る ―― 決め打つと、10人に満たない日だけ題と中身の件数が食い違う。

### 名前の省略形

貼る文面の名前は、**その人に省略形が付いていればそれ**に置き換わる(`_post_name`)。
`user_aliases` 表(`identity_key` -> 省略形)が唯一の置き場で、人ごとに1つ ―― 週にも
配信者にも紐付かないので、同じ人はどの日でも同じ名乗りになる。

- 置き換わるのは **`post_text` と `roster_text` だけ**。応答の行(`roster[]`)の
  `nickname` は表示名のままで、省略形は `alias` として隣に載る。画面の表は順位の
  **根拠**なので、省略形だけにすると文面の🥇が誰なのかをそこで確かめられない。
- `users` 表へ列を足さないのは、あちらが event の来るたび最新の非空値で上書きされるから
  である ―― 同じ列へ書くと、次の配信で消えて付け直しになる。人が付けた層は別の表に置く
  (字幕の直しを `transcript_corrections` へ分けたのと同じ理由)。
- 1人を指さない `identity_key`(`''` / `'(unknown)'`)には付けられない。別人が畳まれた跡
  なので、付けると**別人の名前として貼られる**。
- 長さの上限は `USER_ALIAS_MAX`(40文字)で、応答の `alias_max` が画面の入力欄へそのまま
  渡る。画面へ数字を書き写すと、上限を動かした日に「入力できたのに保存で弾かれる欄」が
  できる。
- 口は `PUT /api/user-aliases`(body に `identity_key` と `alias`)。空文字は「外す」で、
  行ごと消える ―― 空の行を残すと「省略形を付けた人」を数えられない。識別子を path では
  なく body で受けるのは、`identity_key` が表示名にもなり得るためである(表示名には
  `/` も `?` も入る)。
- 人がやり直すしか復旧手段の無い表なので、`dbmaint.GUARDED_TABLES` と
  `row_trash.ROW_TRASH_TABLES` の両方に入れてある(退避のJSONにも載る)。

画面の口は「日のGifter」の見出しの下に畳んである枠で、並ぶのは**その週の日ぶんの顔ぶれに
出た人だけ**。文面へ載り得るのはこの人たちで、週の一覧まで広げると数百人の欄から相手を
探すことになる。並びはトップ3に出た日数の多い順で、次に1日の最高コイン順 ―― 省略形が
要るのは繰り返し上位に出る人だからである。保存したら画面は `/mentions` を引き直す
(文面を組むのはServerなので、画面側で名前だけ差し替えると名乗りの形が2つに割れる)。

### サブアカウントの統合

同じ人が別アカウント(サブ)で投げていることがある。**日ぶんだけ**、その2つを1人へ畳んで
数える(`user_merges` 表: `member_key` -> `primary_key`)。

- 畳むのは**行の束ね方だけ**。数えるGift eventは畳む前とまったく同じなので、日ぶんの
  コイン合計は週の合計と一致したままである。変わるのは人数と順位で、`accounts` が
  その行に畳んだアカウント数を名乗る(1なら束ねていない)。
- **週の一覧は畳まない。** あちらは@で呼ぶ相手の一覧で、@IDはアカウントごとに別物
  である ―― 束ねると呼べない相手ができる。
- 名前・省略形は**主アカウントの物**。畳んだkeyで `users` / `user_aliases` へJOINする
  ので、サブ側の名乗りで貼られることはない。
- **段は作らない。** 主が既に誰かへ束ねられていればその主へ寄せ、主だった人を移すときは
  その束ねの全員が付いて行く。段を許すと「AはBへ、BはCへ」の途中で環ができ、畳み先が
  引く順で変わる。
- 1人を指さない `identity_key` は束ねられない(省略形と同じ理由)。
- 口は `PUT /api/user-merges`(body に `member_key` と `primary_key`) /
  `DELETE /api/user-merges`(body に `member_key`) / `GET /api/user-merges`。
  応答の `merges[]` は「日のGifter」と同じ `/mentions` にも載る ―― 束ねたサブは日の
  顔ぶれから消えるので、名乗りを返さないと外す相手を画面から選べない。
- `user_aliases` と同じく `dbmaint.GUARDED_TABLES` と `row_trash.ROW_TRASH_TABLES` の
  両方に入れてある。
- eventもusers表も書き換えない。観測した事実(どのアカウントが投げたか)は残したまま、
  人の判断だけを別の層に置く。外せばその場で元へ戻る。

画面の口は省略形の枠の右。左の表の**名前を掴んで**、主にしたい行か、右の束ねの札へ
重ねる。掴み手を名前だけにしてあるのは、行を掴み手にすると同じ行の省略形の欄で文字を
選べなくなるからである(欄の中のdragが行のdragに化ける)。外すのは札の中の「外す」。

### @IDの取れていない人を外さない

週のメンション一覧は@IDの無い人を貼る文字列から落とす（@で呼べないため）。
**日ぶんは落とさない。** ここは呼びかけではなく順位の名乗りなので、貼れない人を外すと
1位が別人の名前に化ける。

### 文面はServerが組む

画面側で組み立てさせると名乗りの形が2つに割れる（週の `post_label` と同じ理由）。
日ぶんは行ごとの取捨が無いので、完成した文字列をそのまま返せる。画面はそれを丸ごと
出して、押す前に確かめられるようにする ―― 行数を決め打つと、名前が折り返した日だけ
最後の行が隠れる。

## 並べる日の決め方

- 選んだ週を7時始まりの日で割り、**新しい日が先**。投稿するのは直近の日なので、
  探して下まで送らせない。
- Giftの無かった日も残す。抜くと「誰も投げなかった日」が「配信の無かった日」に化ける。
- まだ始まっていない日は並べない。0件として出すと「その日は誰も投げなかった」に読める。
- ただし**Giftの在る日は時刻に関わらず必ず並べる**。「まだ来ていない日」という判断で
  実際に在るGiftを画面から消してはならない。

## 数え方と負荷

日ごとに窓を張り直さず、週の窓を1本のqueryで `GROUP BY 日, 畳んだkey` する
(`_gift_day_rankings`)。週の一覧とまったく同じ行から数えるためで、別々に引くと合計が
食い違ったときにどちらが本当か読めない。畳んだkeyは `COALESCE(m.primary_key,
e.identity_key)`(サブアカウントの統合)で、束ねが無ければ `identity_key` そのものである。
実測では `user_merges` へのJOINぶんの差は出ない(gift event 7日ぶん・532人で40ms前後、
束ねの有無で±5ms)。

顔ぶれは `_MENTION_DAY_ROSTER`（10人）で切るが、人数・コイン・「1k⬆️」の数は全員ぶん。
切った件数も返すので、画面が「これで全部」と名乗ることはない。

実測（`wicha_3111`・gift event 24,652件・1.6GBのDB）:

| 対象 | 時間 |
| --- | --- |
| 週の一覧 | 6.0 ms |
| 日ぶん7日 | 8.3 ms |
| `/mentions` 応答ぜんたい | 110 ms |
