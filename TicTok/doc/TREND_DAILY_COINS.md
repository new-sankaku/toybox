# 推移のコインを日次にする（配信者タブ）

配信者タブの **■ 推移** で、コインだけを配信ごとではなく**日ごと**に数える。
コメント/分・平均同接・Peak同接・配信時間は配信ごとのまま。

## なぜコインだけ日次か

「1配信=1本」で並べたコインの棒は、**その日いくら出たかを指さない**。理由は2つある。

**1. 1配信が複数のsessionに割れる。** reconnectのたびに新しいsessionが立つ。実測（2026-08-29
時点のtictok.db）:

| | 実測 |
|---|---|
| 配信者×日で2本以上のsessionがある日 | 113日中81日 = **71.7%** |
| 1配信(`live_create_time`単位)あたりのsession数 | 最大7本（218配信中190配信は1本） |

例: `pomiiiip` 2026-08-23 は同じ配信が 3.9分 / 2.9分 / 0.5分 / 12.1分 / 163.1分 の
5 sessionに割れている（`live_create_time` はすべて 21:39:46）。

**2. 配信が日を跨ぐ。** 終了済み284 sessionのうち **101本(35.6%)** が日を跨ぐ。
session合計を開始日へ寄せると、日付が変わった後に出たコインまで前日ぶんとして数える。

上の2つは掛け合わさる。上記5本目のsessionは 08/23 22:00 → 08/24 00:43 で、コイン46,184の
一部は 08/24 のぶんである。

率(コメント/分)と水準(同接)は**足せない量**なので、sessionが割れても値そのものは歪まない。
歪むのは足し算で意味が出る量、つまりコインだけである。

## 数え方

コインの日次は **event時刻**で数え直す。session合計を日付へ振り分けるのではない。

- 源: `events.time` を `strftime('%Y-%m-%d', ..., 'localtime')` で日へ落として `SUM(diamonds)`
- 対象kind: `gift` のみ。実測で `diamonds > 0` のeventはgiftだけ（全1,415,612件中34,657件）
- 対象session: profileが返す`sessions`と同じ集合（制限中を除く直近limit件）。母集合を
  揃えないと、画面の通算KPIや大口の日次人数と突き合わせられない
- 場所: `Storage.streamer_profile` → payloadの `daily_coins: [{date, diamonds}]`

localtimeなのは heatmap・cohort・期間別ランキングと同じ軸へ揃えるため（`PERIOD_RANKING.md`）。
下の **■ 大口（実弾）の日次人数** と同じ日付・同じ数え方になるので、コインの棒と帯の人数を
縦に読み比べられる。

計算量は配信者1人あたり実測36〜79ms。`gift` は全eventの2.4%しかなく、
`idx_events_session_kind_time` が効くのでcacheは要らない。

## x軸を実日付にした

コインが1日1点、他の段が1配信1点になると、**等間隔のcategory軸では縦に読めない**。
1日に5配信あった日と2週間空いた日が同じ幅で並ぶためである。

そこで推移の6段すべてを **1目盛=1日の実数軸**に載せた（`common.js` の
`createSessionTrendChart`）。

- x = 0 は窓の最初の暦日の0時。session点は日内の実時刻を小数で持つ（20:00 → `+20/24`）
- コインの棒は日の真ん中(`n + 0.5`)に立ち、幅1日
- 配信の無い日はそのぶん横に空く（点を作らない ―― コインの段だけは0の点を置く）

副作用として、**コメント/分は棒から線になった**。棒の幅はChart.jsが隣の点との実間隔から
決めるので、3分しか離れていないreconnect断片が並ぶ日は棒が1px未満に潰れる。率はもともと
量ではないので、水準の段(同接)と同じ線で読む。

縦線(crosshair)は段ごとに点の数が違うため、indexではなく**x値**を共有する
（`linkCrosshair(charts, { byValue: true, tolerance: 0.5 })`）。toleranceの0.5は「同じ日の中で
一番近い点」の意味で、これがないと配信の点にcursorを置いてもコインの棒を読めない。

## 移動平均は別の段に、3本

コインの移動平均は棒と同じ段に重ねない。線が棒に埋もれて形を追えないためである。

窓は短期・中期・長期の3本。単位ごとに呼び側(`streamers.js` の `TREND_UNITS`)が決める。

| 単位 | コインの粒度 | 移動平均の窓 |
|---|---|---|
| 配信ごと | 日 | 7日 / 14日 / 25日 |
| 週合計 | 週 | 4週 / 8週 / 13週 |
| 月合計 | 月 | 3か月 / 6か月 / 12か月 |

日足の定番は日本株・FXが 5/25/75、欧米が 20/50/100/200 だが、**この画面で引ける期間が
実測で最長72日（配信日58日）しかない**ため、75日線・200日線は1点も引けない。7/14/25は
手元の履歴で3本とも意味を持つ範囲で選んである。履歴が100日を超えたら75日を足せる。

3本は同じ指標の平滑度違いなので色は変えず、量の段(薄→濃)と線の太さ(細→太)で
「短期→長期」の順序を出す。rampの隣り合う2段は2pxの線では見分けが付かない。

窓が埋まるまでは線を引かない。埋まるまでを手元の点だけの平均で描くと、左端で3本が同じ点の
平均になり、重なったまま始まる（窓の長さの違いが消える）。窓が埋まる点が1つしか無いときだけ
点を出す ―― 線にならず段がまるごと空に見えるためである。

窓は**暦日**で数える。配信のあった日だけを数えると、窓の実長が配信頻度で伸び縮みする。
配信の無い日は0コインの日として窓に入る。

## 週/月まとめ

コインの週合計・月合計は、session合計からではなく**日次の点を畳んで**作る。日を跨いだ
配信のコインが期間の境目でどちらへ入るかを、日次の段と食い違わせないためである。

端の期間は窓の外まではみ出す（6/29から始まる窓でも6月の棒は6/1から立つ）。軸の端は
日数ではなく**棒の左右端**から採ること ―― 日数で決めると端の棒が切れる。
