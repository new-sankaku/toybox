# 映像jobが止まったときに、続きを流す

一括投入は数時間かかる。投げて寝るのが普通の使い方なので、その間に起きた事故を**人が
見張っていなくても拾い直せる**必要がある。2026-07-24の一括再mp4化では見張っていなかった
結果、次が同時に起きた。

- 02:03 serverをCtrl+Cで再起動 → 走っていた2本が `interrupted`。ffmpegも道連れ(`0xC000013A`)
- 03:48 最終保存先(K:)がbusから消えた → 書き込み中のffmpegが `-22` で死亡、10秒後のretryは
  「元の.tsセグメントが見つかりません」で即 `failed`(K:ごと見えないので当然)

どちらも外的事象だが、恒久的な破損にしたのはこちら側である。**書きかけのmp4を残したまま、
原本を`_backup/`に置いたまま、誰も拾い直さなかった。** 62分の録画が12分に、3時間30分の録画が
117MB(moov無し・再生不可)に置き換わり、DBはcompletedのままそれを指していた。

## 1. 失敗したら押す前の状態へ戻す

`_restore_backup()` は**書きかけのmp4を消してから**退避を戻す。ffmpegは走り出した瞬間に
出力fileを作るので、「最終mp4が無いときだけ戻す」という条件だけでは復元が永久に素通りする。
起動時の `_restore_reprocess_backup()` も同じで、判定は「最終mp4が在るか」ではなく
**「在るmp4が完成品か」**(ffprobeで尺が読めるか)で行う。中断はほぼ必ず断片を残すため、
存在だけで打ち切ると原本は`_backup`に置き去りになる。

戻せて初めて、やり直しが安全になる。順序を逆にすると断片の上から作り直しが始まる。

## 2. 待てば直るものは失敗にしない（`JobDeferred`）

保存先volumeの不在は、数十秒のretryでは埋まらない一方で人の介入も要らない(挿し直せば戻る)。
`JobDeferred` は attempt を消費せず、job行を待機へ戻す:

- `not_before` まで `claim_next_pending_media_job()` が拾わない(既定60秒、`TICTOK_MEDIA_JOB_DEFER_SECONDS`)
- `deferred_since` から総待ち時間を数え、上限(既定2時間、`TICTOK_MEDIA_JOB_DEFER_TIMEOUT_SECONDS`)
  を超えたら初めて `failed` にする。待ち続けるqueueは、動いているように見えて何も進まない
- 画面のbadgeは「待機中」ではなく **「復帰待ち」**。順番待ちと理由が違うものを同じ言葉で
  並べると、queueが詰まっているようにしか見えない

判定は `_media_job_runner` の1箇所で行う。実行**前**に record root を確認し、実行**中**に
落ちた場合も「失敗の中身を問わず、rootが消えていれば保留」とする。volumeが無い状態で出る
診断(「.tsが見つかりません」等)はどれも二次症状で、そのまま失敗として残すと原因の分からない
欠落が一括の中に散らばる。

## 3. 中断は自動で待機列へ戻す

再起動で中断したjobは、原状へ戻した後に自動で `pending` へ戻る(`requeue_media_jobs(auto=True)`)。
中断は「やらないことにした」ではなく「途中で止まった」であり、投入された意図はまだ生きている。

無条件ではない。`params.auto_requeues` に回数を数え、上限(既定3、`TICTOK_MEDIA_JOB_AUTO_REQUEUE_LIMIT`)
で打ち切る — processごと落とすjobを無条件に戻すと、起動のたびに同じ落ち方を繰り返す。

## 4. 失敗ぶんの再投入は「同じ行を戻す」

`POST /api/jobs/{job_id}/retry` はgroup idも受ける。一括のgroupを指すと、その中の
failed / interrupted / cancelled **だけ**を待機へ戻す(完了済みはやり直さない)。Job画面の
group行には「失敗ぶんを再投入」が出る。

新しい行を足すのではなく元の行を戻すのは、group行が「N本中M本」で数えられているため。
失敗行を残したまま新規行を足すと母数だけが増え、何度やり直してもgroupは完了に到達しない。

## 5. 終わったことを画面の外へ残す

group全体が終わった時点で `media_queue.group_finished` を ops_events へ1行残す
(成功数 / 失敗数 / 失敗したjob_id)。失敗があれば severity=warning なので、Notifier経由で
webhookにも届く。Job画面を開いていなければ何も残らない、という状態を無くすのが目的である。

## 6. 再encodeの完了判定に「入力と同じ尺か」を足す

`reencode_single_resolution()`(混在解像度の単一化)は **exit 0 でも完走とは限らない**。
実測(streamer_a_20260618_222816):

| 工程 | 入力 | 出力 |
|---|---|---|
| 結合(stream copy) | .ts 435本 | 266,969 frame / 177.9分 ✓ |
| 単一解像度へ再encode | 266,969 frame / 177.9分 | **23,444 frame / 14.5分**、exit 0 |

配信の途中でHLSのsegment分割が止まり、残り2時間43分が1本のsegment(1.08GB)に入っていた録画で、
順に読んだdecoderが14.5分の地点で止まった(seekすれば30分・90分・150分のどこでも復号できるので、
素材が壊れているわけではない)。ffmpegは正常終了し、91%を捨てた出力がそのまま元mp4と
差し替えられた。

そこで出力の尺を入力と突き合わせ、`REENCODE_MIN_COVERAGE`(98%)を下回れば失敗として扱う。
scale/padはframeを増減させないので、正常な再encodeでは尺がそのまま残る。判定は既存のCFR
再試行の入口に繋げてあり、CFRでも足りなければ**出力を消して**`None`を返す — 中身の足りない
tmpを完了印付きで残すと、起動時のsweepが「完成品が在る」と読んで切れた方を差し替える。
そのとき録画は正規化前の**混在解像度だが完全なmp4**のまま残る(`recording.normalization_failed`)。

## 7. 作り直しの完成判定に「素材と同じ尺か」を足す

recorderの検証は「video streamが1本ある」までしか見ないため、途中で切れた結合も合格する
(実測: 62分の録画が12分のmp4に置き換わり completed として畳まれた)。再mp4化は出来たmp4の尺を
**HLS playlistのEXTINF合計**(=素材そのものの尺)と突き合わせ、`_REPROCESS_MIN_COVERAGE`(95%)を
下回れば失敗として扱い、原本を戻す。

正常な作り直しは実測で素材の 100.0〜100.2% に収まる。切れた例は 20% / 24% だった。
