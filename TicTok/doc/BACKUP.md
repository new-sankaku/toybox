# バックアップ

失っていいdataと、失うと二度と戻らないdataを分け、後者だけに費用を払う。この文書は
**何を守るか**を先に決め、そのあとで仕組みを述べる。順序が逆だと「取れるものを全部取る」
になり、容量と時間を使い切ったところで肝心な物が落ちていることに気付く。

## 1. 何が消えてはいけないのか

判定の軸は1つ、**作り直せるか**である。作り直せる物は、作り直す費用が backup を取る費用を
上回るときだけ守る。

### 二度と戻らない（最優先）

| data | 置き場 | 量 | 戻らない理由 |
| --- | --- | --- | --- |
| 配信のevent・session・録画の台帳 | `tictok.db` | 1.65 GB | 過去の配信は再取得できない。TikTokは履歴APIを持たない |
| HLS原本 `seg*.ts` / `pack*.ts` | `<一次>/<配信者>/ts/<stem>/` | 31.0 GB | 同上。mp4も焼き込みも切り出しも、すべてこれが源 |
| avatar / emote / giftアイコン | `<一次>/avatars` ほか | 73.4万 file / 0.63 GB | CDN URLは署名付きで期限切れ。取り直す手段が無い |
| TikTok本体のhighlight動画 | `<一次>/<配信者>/highlights/` | 0.08 GB | 配信者が消せば消える |
| 人の判断が入った行 | `tictok.db` | — | 下記 |

「人の判断が入った行」を表で名指しすると、`bookmarks`(見どころ 192) /
`clip_groups`(19) / `clip_presets` / `transcript_corrections`(字幕の直し 1,070) /
`settings`(121) / `monitored_targets` / `user_aliases`(貼る文面の省略形)。行数は小さいが、**もう一度やる方法が「人がやり直す」
しか無い**という点で原本と同じ性質を持つ。件数が小さいことは、守らなくてよい理由にならない。

### 作り直せるが、作り直すのが高い

| data | 量 | 作り直す費用 |
| --- | --- | --- |
| 完成mp4 | 8.6 GB | ts結合。時間はかかるが機械だけで済む |
| sidecar(波形・サムネ・gain曲線・無音区間・笑い声) | 少量 | 一部はGPU推論。録画本数ぶん |
| 文字起こし `transcripts` (484) | DB内 | whisperの再実行。GPU時間が本数ぶん |
| 意味検索index | 0.66 GB | `scripts/rebuild_semantic_index.py` で再構築可 |
| 検索index `search_hits` / `search_fts` (100万) | DB内 | 起動時backfillが張り直す |
| model・checkpoint | 0.36 GB | 公開元から再取得＋再export可(`models/laugh/EXPORT.md`) |
| font・効果音 | 0.12 GB | `tictok/record/fonts.py` / `tictok/media/sfx.py` の manifest が URL と SHA-256 を持つ |

このうち **意味検索index と 検索index は backup を取らない**。DBから決定的に再構築でき、
再構築の手順が repo に入っている。model・font・効果音も取らない ―― 出所と digest が
codeに書いてあり、それ自体が backup である。

### 守り方が違うもの

**`.env`** は API key を含む。**複数のdriveへ平文で撒かない。** 設定値の退避
(`_config/`)にも値は書かず、**設定されているkey名だけ**を記録する。key本体は
password manager など、この仕組みの外で持つこと。値を撒けば、driveを1台紛失した時点で
鍵が漏れる ―― backupが増やしたのは安全ではなく攻撃面である。

**`journal/`**(407 MB) は event の追記log で、DBの writer が停滞・crash しても event が
残るための最後の防波堤。DBの backup とは**別の失敗**を守っているので、片方があれば
もう片方が要らないという関係ではない。ただし守る窓は短く(既定14日)、DBへ復元された時点で
役目を終える。

#### journalとDB snapshotの隙間

起動時の `recover_from_journal` は、journalの件数がDBを上回るsessionだけを、journalの
行で**全置換**する。件数で決めてよいのは、起こる失敗が「両方とも末尾を失う」形だから
である ―― processのcrashはDBのbuffer滞留分(末尾)を失い、電源断はjournalのpage cache
(末尾)とDBの未fsync分(末尾)を失う。どちらも同じ流れの末尾なので、多い側が少ない側を
含む。互いに違う場所が欠ける(歯抜け)には、journalの追記が**断続的に**失敗する
(disk fullが解消してまた詰まる等)という前提が要り、その場合はjournalが多ければDBだけに
在る行が消え、DBが多ければ警告して見送る。journalの追記失敗は `storage.journal_append_failed`
に残る(実DBのops_eventsで0件)。

snapshotへ戻したときの穴は別にあった。journalにはevent/viewerしか無く、snapshotより
後に始まった配信は**session行が無いので黙って戻らなかった**。さらに `sessions.id` は
AUTOINCREMENTで、その連番(`sqlite_sequence`)もsnapshotと一緒に戻る。戻した後の最初の
配信が失われた配信と同じidを取り、次の起動でjournalの件数がDBを上回るので置換が走り、
**別配信者のeventがその配信に混ざる**(2026-09-02、scratchpadの `id_reuse_probe.py` で
実測: carolの配信にbobの5件が入った)。

そこでjournalにsessionの印を足した。`create_session` が `{"t":"s","r":[id, unique_id,
started_at, bucket_seconds, conn_instrumentation]}`、`delete_session` が `{"t":"d","r":[id]}`
を残す。復元は:

- 行が無いsessionは、`s` があり後に `d` が無いときだけ行ごと蘇らせる(`connecting` の
  まま置き、直後の `cleanup_stale_sessions` が中断sessionと同じ手順で確定する)。
  印の無い旧journal・削除済みは蘇らせない。
- 行が在っても、`s` の unique_id / started_at と違えば別の配信なので触らず警告する
  (`storage.journal_session_mismatch`)。
- 復元の前に `sqlite_sequence` の sessions をjournalに現れる最大idまで進める
  (`storage.session_sequence_advanced`)。印の無い旧journalでもこれだけは効く。

**`logs/`**(2.6 GB) は診断用で、失っても data は戻る。backup しない。

## 2. 保存先の構成

```
一次保存(SSD)        C:\...\TicTok\recordings     録画中の書き込み・poolの正本・成果物を作る先
  │
  ├─ 定期backup ──→  <backup先>\_primary_backup\   元を残したままの控え(丸ごと)
  │
  └─ 移動 ────────→  最終保存先1  K:\80_Tiktok      ┐ 相互mirror
                     最終保存先2  J:\...            ┘ 常に同じ内容

DB  C:\...\tictok.db  ── snapshot ──→  <DB退避先>  本体とは別drive
設定  DB settings 表  ── export ────→  一次保存 と 全ての最終保存先 の `_config/`
手入力データ(8表)         ── export ────→  同じ `_config/` に `tables-<時刻>.json`
```

**「移動」と「backup」は別物である。** 移動(relocate)は一次保存から実体を運び出して元を
消す片道の操作で、目的は一次保存のSSDを空けること。backupは元を残したままの控えで、目的は
一次保存のdiskが壊れたときに残ることである。同じ場所を指していても役割が違うので、
folderを分ける(`_primary_backup`)。混ぜると、「移動済みだから消してよい」と
「控えだから消してはいけない」が同じfileに同時に成り立つ。

### 控えは「前回と同じdrive」にしか書かない

外付けdriveのletterは、差す順序やhubの構成で入れ替わる。`K:\Backup` に別のdriveが見えている
状態で走ると、台帳が無いので**初回として一次保存先の31GBを丸ごと写し始める** ―― 本物の
控えは古いまま置き去りで、運用logには「完了」と出る。driveが外れているだけなら親folderが
無いので止まるが、別のdriveが同じ場所に居ると親folderが在るので素通りする。

そこで `_primary_backup/root-id.txt` に乱数の識別子を置き、DB側(`db_maintenance` の
`record_backup_root`、保存先の文字列と組)に控えて、**書き始める前に突き合わせる**。
無い・違うなら1byteも写さず、運用log(`record_backup.job_failed`)で名乗る。差し直して
letterが戻れば次の周期で一致する。本当にdriveを替えたなら、設定の保存先を**別のfolder名**に
変える(控えは保存先の文字列と組なので、値が変われば新しい先の識別子を採用し直す)か、
古いdriveの `root-id.txt` を新しいdriveへ写す。同じ文字列で保存し直しても変更にはならない
(画面は全keyを送るので、値が同じ保存を「採用し直せ」の合図には出来ない)。
DBを古いsnapshotへ戻して控えが無くなった場合は、控え側(backup先の識別子)が正である。

台帳(`ledger.json`)と別のfileに置くのは、台帳が「読めなければ空から始める」約束だから
である。同居させると、台帳の破損と別のdriveを区別できない。

### 最終保存先が2つある意味

**振り分けではなく相互mirror。** 1台のdiskが壊れても退避済みの録画が残るためのもので、
両系統は常に同じ内容でなければならない。したがって:

- 移動は**両方へ書けたときだけ**成立する。片方に書けなければ移動そのものを行わない。
  片側だけが最新という状態は、次の障害で気付かないままdataを失う唯一の経路である。
- 読み出しは全系統を探す。片方が外れていても再生・出力は続く。
- 後から2系統目を足した場合は「最終保存先の再同期」で揃える。

**揃っているかは、突き合わせた回にしか分からない。** 移送は必ず全系統へ書くので、成功の記録
だけを見ている限り片方が古いことは永久に現れない —— 実測(2026-09-03)で、移送は8日前まで
成功し続けたまま `J:\80_Tiktok` 側に 12,293 file / 543GB が欠けていた(2系統目を後から
足した分)。DBには二次保存先の台帳が無いため、答えを出す方法は両rootの全dirを辿る走査だけ
である(`mirror.compare_roots`、実測1.9秒 / 12,340 file)。

走査は画面のpollには乗せない。代わりに**走った回の要約を残す**: `db_maintenance` の
`mirror_compare_result` に、時刻・系統ごとの欠け(`missing_by_dst`)・食い違いの件数を書く
(`disk._store_mirror_check`)。バックアップ画面はこれを読んで経路の状態を決め
(`_lane_state(..., gap=True)` → `degraded` / 理由 `unsynced`)、「いま突き合わせる」で
走らせ直せる。

**確かめていない状態を「揃っている」と書かない。** 一度も走っていない回(`at` が空)と
再同期の直後(`stale`)は欠けとして立てない —— 前者を赤にすると本当に欠けた日の警報と
見分けが付かず、後者に残っている件数は**実行前の**姿だからである。件数を0へ書き換えないのも
同じ理由で、複製に失敗した分まで「揃った」と読ませることになる。

## 3. いつ走るのか

**「配信が終わった」を全体の状態として扱わない。** 配信者を複数監視していれば、ある録画が
終わった瞬間に他が走っているのが普通である。実測(2026-09-02、確定録画529本・76日):

```
終了時に他の録画が進行中だった:  156本 (29.5%)
同時録画の最大:                    5本
1日の終了本数:            中央値 7 / 最大 21
```

最初はここを「最後の終了から静穏時間だけ待つ」という**全体gate**で書いた。同じ実測へ当てて
みると、走った回の **65.4%が他の録画の進行中**で、書き込み中の`.ts`を写しに行っていた。

しかもその形は**監視数が増えるほど成立しなくなる**。同じ実測を多重化して測ると:

| 配信者 | 録画/日 | 「最後の終了から15分静か」が成立する時間 | 最長の未成立 |
| --- | --- | --- | --- |
| 4 | 6.9 | 94.1% | 0.9時間 |
| 20 | 34.6 | 74.2% | 1.1時間 |
| 80 | 138.4 | **30.6%** | 3.1時間 |

全体の静けさに依存する条件は、監視数という**外から決まる量**に振り回される。

### 待つのをやめた

奪い合いを避けるために待っていたが、その前提を実測すると崩れた。録画の書き込みは1本
**0.10 MB/s**(実測: 452本 259GB / 総尺)、1人1日あたり0.85GB。

| 配信者 | 録画量/日 | backup所要/日 | 1日に占める割合 |
| --- | --- | --- | --- |
| 20 | 17 GB | 2分 | 0.1% |
| 80 | 68 GB | 8分 | 0.5% |

80人でも1日8分である。周期を静けさに合わせる価値より、**監視数に依らないこと**のほうが
大きい。

### 代わりの形

- **周期は固定**(監視数に一切依らない)。
- **録画1本ずつを見て、落ち着いた物だけを写す。** 動いている録画は写す対象から外すだけで、
  待たない。「走ってよいか」ではなく「何を写すか」の問題にしている。

「落ち着いていない」は4条件で、1つでも当たれば除外する ―― まだ終わっていない / 確定処理中 /
派生物のjobが控えている(ts結合・波形・サムネ・文字起こし) / 終了から静穏時間が経っていない。
3つ目まで見るのは、最終保存先への移送(`api.disk._run_relocation`)と**同じ条件**にするため。
素材を触る操作が2つあって片方だけ緩いと、移送では触らない録画をbackupが触る。

**除外は「まだ見ていない」であって「消えた」ではない。** だから削除の伝播からも外す ――
ここを間違えると、控えに在る正しいfileへ削除の印が付く。

合図をDBの終了時刻から引くのは、process内の合図(`core.sweep_signal`)が**再起動で消える**
ためである。録画が終わった直後にserverを落とすと、その録画は合図を失う。

### 失敗したときの形

3つの退避(DB snapshot / 設定値 / 一次保存のfile)は**独立して失敗し、独立して印を進める**。
「どの録画まで済んだか」の印は退避ごとに別のkey(`backup_db_after_recording_at` など)で、
1つの印にまとめる形は捨てた ―― まとめると「3つとも済んでから進める」しかなく、file backupの
先が外れている周期ごとにDBのsnapshotまで取り直す。

失敗した退避は**指数backoff**で再試行する(60秒→2分→4分→…、上限60分)。退避が失敗する
理由はほぼ「退避先のdriveが外れた・満杯」で、60秒後に直っていることは無い。上限を置かない
場合の被害を実測で押さえた(2026-09-02、DB 1.65GB):

| 工程 | C:(NVMe) | K:(SMR 5400rpm) | J:(CMR) |
| --- | --- | --- | --- |
| backup APIでのcopy | 5.7秒 | 17.8秒 (92MB/s) | 9.2秒 (179MB/s) |
| integrity_check(読み戻し) | 16.9秒 | 21.9秒 | 21.6秒 |

`integrity_check` はdriveに依らず75〜100MB/sのCPU律速で、snapshot 1回はK:で約40秒。
60秒周期で取り直すと**1日860回・1.4TB**をSMR driveへ書いて消すことになる。K:の92MB/sは
CMR cacheが吸った初回の値で、この繰り返しでは20〜30MB/sまで落ち、同じdriveの移送と
file backupを道連れにする。backoffの上限60分なら最悪でも1日24回である。

file backupの下限間隔での見送りは失敗ではないが済んでもいない。fileの印だけ進めず、間隔が
明けた最初の周期で写す(DBと設定値の印は進んでいるので取り直されない)。

**結果はops_eventsへ残す**(完了・失敗・中断)。textのlogだけでは、退避先が外れたまま
何週間も失敗し続けていることに誰も気付かない ―― backupが黙って止まるのは、backupの事故の
うち最もよくある形である。ops_eventsに乗れば通知(webhook)の対象になる。

DB snapshotは画面の手動保守(VACUUM・checkpoint)と**同じlock**を取る。snapshotは読み
transactionを数十秒握るので、別々のlockだとその最中にVACUUMが走り出し、書き込みを止めた
上でreaderに阻まれて失敗する。

退避先の**親folderは作らない**(DB・fileとも同じ規則)。`parents=True` で作ると、driveが
外れている間にsystem driveの同じpathへ空folderが生まれ、そこへ世代が積み上がる。指定した
folderの直下だけは作るので、`H:\TicTokDB` のような設定はdriveが在れば自分で用意される。
落ちた回の書きかけ(`.partial`)は次の退避の頭で掃く ―― 次の世代は別の名前を取るので、
掃かないと落ちた回数ぶん(1本1.65GB)退避先を食う。

## 4. 誤ったDELETE / DROP をどうするか

### 防げないことを先に言う

**外部processからのDELETE/DROPは、このserverでは原理的に防げない。** `sqlite3.exe` でも
DB Browser でも、fileを開けば誰でも書ける。serverに何を足しても、server**を通らない**書き込みは
止められない。防げるふりをするほうが危険なので、前提を「事故は起きる」に置く。

### 本当の失敗は「事故に気付かないまま世代が回ること」

backupがあっても戻せなくなる経路はただ1つ、**事故のあとに世代が回転して、事故の前の姿が
刈り取られること**である。誤ったDELETEは気付くまでに日数がかかる種類の事故なので、
世代を「回数」で数えると、配信が続いた日に事故の前の姿が先に押し出される。

したがって対策は3つ:

1. **世代を暦で数える。** 直近N日は1日1つ、それより古いのは1週1つ。押し出す速さを
   配信の本数ではなく暦が決めるようにする。既定(日次14日・週次8週)で自動世代は最大20本
   前後、1本1.65GBで**退避driveに約33GB**を要求する。
2. **行数の急減を検知したら、刈り取りを凍結する。** 退避の直前に19表の行数を数え(実測51ms)、
   前回より閾値を超えて減っていたら古い世代を消すのをやめる。減ること自体は正常にも
   起きるので**処理は止めない** ―― 止めると正常な運用が壊れる。行うのは凍結と、
   運用log・通知で名乗ることだけ。解除は人の操作でのみ。
3. **行数の記録はDBの中に置かない。** DBが壊れたときに一緒に失われる。退避先の台帳に置く。

### 物差しを3本立てにした理由

割合ひとつでは小さい表を守れない ―― 30行の表から1行消えれば3.3%で、既定の2%を必ず超える。
そのため手入力データ(`settings` / `bookmarks` / `clip_groups` / `transcript_corrections` /
`monitored_targets`)を見張りから外すと、**最も復旧手段の無い場所がちょうど無防備になる**。
表ごとにORで判定する:

| 物差し | 既定 | 何を捕まえるか |
| --- | --- | --- |
| 0行化 | 閾値なし | `DROP TABLE`＋再作成も `DELETE FROM <表>` も最終形は0行 |
| 絶対数 | 50,000行 | 割合の許容量がDBの成長で膨らむのを止める天井 |
| 割合＋最小幅 | 2% ＋ 500行 | 最小幅があるので同じ割合を大小どちらの表にも当てられる |

既定値は推測ではなく、`tictok/store/` の全DELETE経路を読み、実DBで1操作あたりの実削除量を
数えて決めた(2026-09-02)。

| 表 | 通常の1操作で消える最大 | 経路 |
| --- | --- | --- |
| events | 36,892（中央値 4,140） | session削除のcascade |
| transcript_corrections | 1,070（全件が録画1件に集中） | 録画削除のcascade |
| markers | 351 | session削除のcascade |
| bookmarks | 59 | 「表示中をすべて削除」 |
| settings | 0（DELETE経路がcodebaseに存在しない） | — |

この調査で分かった前提が1つある: **行が大量に減る経路はすべてoperatorの明示操作**で、
背景loopが黙って行を消す経路は`ops_events`の刈り込み以外に存在しない。つまり検知が鳴る
＝直前に人が大きな操作をした、である。

### serverの中からの事故は防ぐ

外部からは防げなくても、この codebase 自身の bug や migration の誤りからは守れる。
書き込み接続に authorizer を取り付け、`DROP TABLE` / `DROP INDEX` / `DROP TRIGGER` /
`DROP VIEW` を既定で拒否し、migration の区間だけ `dbmaint.allow_schema_drops()` で
明示的に許可する。DELETEは拒否しない ―― 行の削除はUIの正常な機能そのものである。

費用は実測した。statement cacheが効くので、実運用の形(同一SQLの繰り返し)では差が出ない。

| 測定 | 無 | 有 |
| --- | --- | --- |
| 同一SQL 20,000回 select | 209.6ms | 202.2ms（誤差） |
| 新しいSQLのprepare 2,000回（最悪値） | 76.3ms | 108.9ms（+16.3µs/文） |

### 3段目: 消えた行そのものを残す

割合も行数も、**小さい表の部分削除**には届かない。そこは物差しを増やしても解けない ――
「見どころ192件のうち59件が消えた」は、同じ59件が正常な一括削除でも消えるので、行数だけ
からは原理的に区別する情報が存在しない。

そこで、人がやり直すしか復旧手段の無い8表 (`bookmarks` / `clip_groups` / `clip_presets` /
`transcript_corrections` / `settings` / `monitored_targets` / `user_aliases` /
`user_merges`) に
**`AFTER DELETE` trigger**
を張り、消えた行を `row_trash` へJSONで写す。

**triggerはschemaの一部なのでengineが強制する。** つまり **authorizerが届かない外部process
からの削除でも発火する** ―― 1段目の穴をここが塞ぐ。実測(2026-09-02、実DBのcopy):

| 検証 | 結果 |
| --- | --- |
| 直接 `DELETE` | 捕捉 |
| FK cascade削除 | 捕捉(3/3) |
| **別processからの `DELETE`** | **捕捉(20/20)** |
| `DROP TABLE` 後 | triggerは消えるが、それまでの退避行は残る |

実データでの復元も通した: 見どころ192件から外部processで20件消し、`row_trash` の20件を
`scripts/restore_deleted_rows.py` で戻して192件に復帰。memoも秒も全列そのままだった。
二度目の復元は「同じidの行が既に在る」として現行を壊さずに断る。

`events` を入れないのは実測による ―― session 1件の削除で 0.60秒→1.09秒、退避に **30.1MB**
積まれる。対象表の1年ぶん(数百KB)と桁が5つ違う。この費用は、画面から1件消す操作で
0.035ms→0.125ms、最大のcascade(録画1本で字幕の直し1,070行)でも +6ms。

保持は既定365日。実測で対象への削除は1日0.63件・1行300〜450 byteなので、1年ためても
数百KBにしかならない。DB退避の暦層(約70日)より長いのは**戻せる単位が違う**ためで、
snapshotへの復旧は全体が巻き戻るが、こちらは行1本だけ戻せる。

### 3段は互いの代わりにならない

| | 守るもの | 届かないもの |
| --- | --- | --- |
| authorizer | serverの接続の `DROP` | 外部process |
| 行数の見張り | 大量削除・0行化。事故の前の姿を刈らせない | 小さい表の部分削除 |
| `row_trash` | 論理的な誤削除(行単位で戻せる) | **DB fileの喪失** |
| snapshot | DB fileの喪失・破損 | 1行だけ戻すこと(全体が巻き戻る) |

`row_trash` は **DBの中に在る**。これが最も重要な境界である ―― DB fileが壊れた・消えた・
diskごと落ちたなら退避行も一緒に失われる。そこを守るのは別driveのsnapshotであり、
逆にsnapshotは1行を戻すために全体を巻き戻す。**2つは代わりにならない。**

### 捕まえられないもの

正直に書く。ここに挙げたものは、この仕組みでは検知できない。

- **外部processからのDELETE・DROP。** 防止も検知も、事後の行数の比較でしか効かない。
- **「bookmarks 192件のうち59件を誤って消した」。** 同じ59件が「表示中をすべて削除」という
  正常な操作でも消えるので、**行数だけからは原理的に区別する情報が存在しない**。
- **小さい表の部分削除。** 行数の見張りでは検知できない(3段目の `row_trash` が戻す側で
  受ける)。
- **`UPDATE` による書き換え全般。** 消えた行だけが対象で、見どころのメモを誤って上書き
  した・切り出しの範囲を誤って詰めた、は1件も残らない。`settings` の更新(upsert)も同じ
  理由で対象外 ―― そちらは `_config/` の世代が守る。
- **退避表そのものを消された場合。** `row_trash` へのDELETEにはtriggerを掛けていない
  (掛ければ無限に自分を退避し続ける)。空にされれば、それまでの退避は戻らない。
- **保持日数を過ぎた行。** 既定365日を越えた誤削除に気付いても、その行はもう無い。
- **親が先に消えている行。** 録画ごと消した場合、見どころだけを戻すことはできない
  (孤児として静かに入れず、その行だけが理由付きで失敗する)。

誤検知も残る。最大級のsessionを1件削除すると鳴る(eventsの2.4%が一度に消える)。監視対象や
グループが1件だけの状態でそれを消しても鳴る ―― こちらは「その表が空になった」が事実として
正しいので、条件としては誤っていない。鳴った結果は刈り取りが止まるだけで、画面から1回
解除すれば戻る。

### fileの誤削除

一次保存からfileが消えても、backup先からはすぐには消さない。厳密なmirrorにすると、
誤削除がそのまま控えへ伝播して「控えがあるのに戻せない」になる。既定は消さない
(`record_backup_keep_deleted_days = 0`)。

## 5. 設定値

設定値は `tictok.db` の `settings` 表にしか無く、DBを失うと設定も同時に失われる。
一次保存と全ての最終保存先の `_config/` へ、人が読める形で書き出す。

**世代を残す。** 上書きにしないのは、設定を誤って変えたときに前の値へ戻せることが
この機能の目的だからである。中身が前回と同じなら新しい世代は作らない。

**書けない保存先があっても、書ける保存先には書く。** ここは移動と逆の判断である。移動は
片側だけ新しいと次の障害でdataを失うが、設定値は読む人が時刻を見て新しい方を採れる。

### 手入力データも同じ場所へ

4章の8表(`bookmarks` / `clip_groups` / `clip_presets` / `transcript_corrections` /
`settings` / `monitored_targets` / `user_aliases` / `user_merges`)は、snapshotにも入るが、SQLiteを開ける環境が無ければ読めず、
1.65GBを開いて数百KBを取り出す作業になる。`core/tables_export.py` が同じ `_config/` へ
`tables-<時刻>.json` として、**列名も値も表に在るまま**書き出す(加工した瞬間に元の値が
失われる)。実測(2026-09-02)で1,407行・530KB・0.04秒。世代の規則は設定値と同じ
(同じ内容なら作らない・30世代・partial→rename)。設定値と分けるのは読む人が違うからで、
設定値は復旧の最初に、こちらはserverが動いた後に読む。

**現時点では機外(offsite)へは出さない。** 全copyが同一機・同一userに在ることは変わらず、
このfileを手作業で外のmediaへ持ち出す前提である。機外への自動copyは行っていない。

## 6. 実測（2026-09-02）

書き込み先の実測。256MBを8MBずつ書いてfsync / 800 byteのfileを1000本。

| drive | 逐次 | 小file |
| --- | --- | --- |
| D: | 149.5 MB/s | 30.1 file/s |
| H: | 108.2 MB/s | 343.1 file/s |
| J: | 164.7 MB/s | 127.5 file/s |
| K: | 136.4 MB/s | 437.5 file/s |

この表が設計を決めている。**avatars 733,604 file を素のfile copyでD:へ写すと約6.8時間**
かかり、最速のK:でも28分。一方 ts原本31GBは逐次なのでD:で約4.5分で済む。だから
pool(avatars / emotes / gift_icons)だけは1本のarchiveに固め、それ以外を差分copyする。
「大きいfileは差分copy・小さいfileはarchive」の2本立ては、速度の好みではなく
**そうしないと成立しない**という結論である。
