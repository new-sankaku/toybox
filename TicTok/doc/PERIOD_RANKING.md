# 期間別ランキング（月 / 週 / 日）

配信者タブの **Gifter** と **Battle Gifter** を、暦で切った期間ごとに並べる。

## 効く範囲

**この2つの表だけ**。上のKPI・推移・heatmap・Battle成績・集中度chipは通算のまま置く。

期間で画面全体を絞ると、既存の数字(平均コイン/配信・勝率・ライバー比率・Top1比率)が
別の意味になる。それらは「通算での姿」を答える指標として文言まで組まれているので、
分母だけを黙って差し替えない。表の直上に操作を置いて、どの表に効くのかを位置で名乗らせる。

## 期間の境界

暦どおり、**ローカル時刻**で切る。

| 粒度 | 境界 | keyの形 |
|---|---|---|
| 月 | 1日 00:00 〜 末日 24:00 | `2026-07` |
| 週 | 月曜 00:00 〜 日曜 24:00 | `2026-07-13`(その週の月曜) |
| 日 | 00:00 〜 24:00 | `2026-07-16` |

ローカル時刻なのは heatmap・cohort と同じ軸へ揃えるため。画面ごとに日の境目が違う状態を
作らない。深夜1時開始の配信は「前日の続き」ではなく暦どおり当日ぶんに入る。

境界の実装は**2か所**にあり、必ず一致させること。ずれると期間一覧のコイン合計と、その
期間を開いたときの合計が合わなくなる。

- SQL: `_PERIOD_SQL`（期間一覧の集計）
- Python: `_period_key` / `_period_bounds`（一覧の中身を切る）

`test_streamer_ranking.py::test_sql_and_python_agree_on_the_period_of_an_event` が
月末・週またぎ・深夜を並べて両者を突き合わせる。

## Battleは開始時刻の期間へ数える

Battleの貢献窓は次Battleの開始まで伸びうるので、日付を跨ぐことがある。**戦を2つの期間へ
割らない** — 割ると1戦の貢献が散って「誰の戦だったか」が読めなくなる。

その結果、月末23:30に始まった戦の翌月ぶんのGiftは、

- **Battle Gifter** … 前月(戦の始まった月)に入る
- **Gifter** … 暦どおり翌月に入る

と軸が違う。同じ配信者の2つの表でコインが一致しないのはこのためで、不整合ではない。

## 前期比

選んだ期間と**その1つ前の期間**を同じ規則で集計し、順位差を付ける。

- 前の期間の順位は、表示件数(100)で切る**前の全順位**から引く。上位N件だけを覚えると、
  圏外から上がってきた人が全員「初登場」に化ける
- 前の期間に居なかった人は `rank_delta = null`(画面は `new`)。0や大きな数で埋めると
  「急上昇」として描かれる
- 比べる前の期間が無い最初の期間は `prev_period = ""`(画面は `—`)。「差が0」ではなく
  「差が存在しない」

## 期間の一覧

**配信の在った範囲**から作り、間を1つも飛ばさない。Giftのあった期間だけを並べると、
「配信したが誰も投げなかった」期間が消え、**「その週は誰も投げていない」が「その週は
配信していない」に化ける**。間隔そのものが読めるよう、配信の無い期間も残す。

時刻の壊れた行1つで1970年からの日付が並ぶため上限(`_RANKING_PERIOD_MAX`)を置くが、
切ったときは件数を `dropped_periods` で返し、画面が「古い N 期間は省略」と名乗る。

## 性能

profileとは**別の口**にしてある。期間を変えるたびに通算集計(session全件・battle全件)を
引き直さないため。

`battles.data_json` は1戦あたりが大きく、実測で1配信者699戦=23MB。全戦をparseすると
それだけで440msかかる。窓の解決に要るのは時刻だけなので `json_extract` で引き、実体を
parseするのは**見ている期間の戦だけ**にしている(`annotate_result` は result と score に
しか触れないので、抜き出した時刻はannotate後の値と一致する)。

実測(110 session / 699戦の配信者、warm):

| 粒度 | 最適化前 | 現在 |
|---|---|---|
| 月 | 587ms | 557ms |
| 週 | 480ms | 316ms |
| 日 | 520ms | 183ms |

## 表示設定

粒度は残す(`tictok.streamers.gifterGranularity` / `.battleGifterGranularity`)が、
**選んだ期間は残さない**。絶対日付を復元すると、翌月に開いたときに先月が選ばれたまま
「今月は0」に見える。

2つの表の粒度は独立している。応答は両方の一覧を含むので、同じ期間を出しているときは
frontendが1回の応答を共有する(`rankingInflight`)。

# 人×期間の一覧（Gifter × 配信日／週／月）

期間別ランキングは**1つの期間の断面**しか出せない。誰が伸びて誰が落ちたのかを読むには
期間を切り替えて前の画面を記憶することになり、月と日は排他なので「月の山の中のどの日か」
は原理的に一度に見えなかった。その上へ、**期間を列・人を行**にした一覧を置く。

- 口: `GET /api/streamers/{unique_id}/matrix?granularity=day&since=&until=&columns=0`
- 実装: `streamer_gifter_matrix`（`tictok/store/streamers.py`）
- 画面: 「Gifter × 配信日」「Battle Gifter × 配信日」（既存の2表はそのまま残す）

1回の応答にGifterとBattle Gifterの両方が入る。列(`periods`)・行・升目(`cells`)が同じ応答で
揃うので、画面は縦(その列の中での上下)と横(その人の続き方)を**期間を選ばずに**描ける。

## 列は「Giftの在った期間」と「配信の在った期間」の合併

sessionの開始日だけで列を組むと、**日を跨いだ配信の深夜ぶんのGiftがどの列にも載らない**。
Giftの在った期間だけで組むと、配信したが誰も投げなかった期間が消える（期間の一覧と同じ
理由）。両方の合併を取り、新しい側から既定の列数を残す。

配信の無い期間は列にしない。暦の穴は日付ラベルの飛び（07/19 → 07/22）として読む。
上限で切った古い期間は `older_periods` で件数を返し、画面が「これより古い N 日は出して
いません」と名乗る。黙って切ると「これしか配信していない」と読める。

## 粒度と範囲

粒度は期間別ランキングと**同じ境界**（`_PERIOD_SQL` / `_period_key`）で切る。画面ごとに
日の境目が違う状態を作らないためで、`_battle_gifter_periods` も粒度をそのまま受ける。

`since` / `until` は**カレンダーで選んだ日付**（`YYYY-MM-DD`）で受け、`_date_to_period` が
**その日の属する期間**へ寄せる。月の1日・週の月曜だけを有効にすると、選べない日を
calendarが黙って弾くことになる（7/15を選べば「7月」「その週」を指したことにする）。

範囲の外は「選ばなかった」ぶんなので `older_periods` に数えない。数えるのは**範囲の中で
上限に当たって出せなかった**期間だけである。

粒度・日付・前後関係の壊れた指定は `ValueError`（口は400）で断る。黙って既定へ倒すと、
画面の名乗りと中身が食い違う。

範囲に1件も入らなかったときも `first_date` / `last_date`（在る記録の端）は返す。画面が
「記録が無い」と「選んだ範囲に無い」を描き分けられなくなるためである。

## 升目は投げた期間だけ持つ

`cells` は投げた期間のkeyしか持たない。0で埋めない — 画面が空欄として描けなくなり、
「0コイン投げた」と「投げていない」が同じ見た目になる。

Battle側は戦を割らない規則をそのまま引き継ぐので、**同じGiftでも2つの一覧で列が違う**
ことがある（窓が期間を跨いだとき）。上の「Battleは開始時刻の期間へ数える」と同じ話である。

## 並べ替えは見出しのclickだけ

並び順の専用buttonは置かない。表示範囲を絞る操作に見えるためで、実際に「直近3日」と
名乗るbuttonが14列出したまま並べ替えるだけ、という読み違いが起きた。

見出しを押すとその列で降順、もう一度押すと昇順。列の見出しはさらに、(1)行の先頭にその
期間の順位を付け、(2)その期間に投げていない人を薄くして下へ落とし、(3)**下の期間別
ランキングを同じ粒度＋その期間**へ送る。一覧で見つけた期間を、もう一度selectから選び
直させないためである。投げていない人の行を消さないのは、「今日は来なかった常連」が
読めなくなるため。昇順のときは順位を付けない（1が最下位になり、意味が反転する）。

## 濃さ

その列の量を `--ramp` の濃淡で出す（時間帯heatmapと同じ語彙。この画面に量の色を2種類
作らない）。窓の中の最小〜最大を**対数**で割る。0起点の線形だと、跳ねた1列のせいで
残りが全部同じ薄さへ寄る。

## 上限と性能

行 `_MATRIX_ROWS = 40`。列は粒度ごとに既定 `_MATRIX_COLUMNS`（日14 / 週12 / 月12）、
上限 `_MATRIX_COLUMNS_MAX`（日60 / 週26 / 月24）。上限が粒度ごとに違うのは、月の1列には
日の30倍の戦が入り、`_battle_gifter_periods`（Battle窓の解決）が同じ列数では持たないため。

2つの表は**窓を共有しない**（粒度も範囲もそれぞれ持つ）。同じ窓を見ているときだけ、
frontendが同じ応答を待つ（`matrixInflight`）。1回の応答に両方の一覧が入っているので、
別々に投げるとserver側で同じBattle窓の解決を2度走らせることになる。

取得するのは**配信者を選び直したとき**と**窓を変えたとき**だけで、収集中のlive更新
(`light`)では引き直さない。列の合計(`periods[].diamonds`)はその期間の全Gifter、行は上位
40人なので、人数が上限を超えた配信者では列の合計が見えている升目の合計を上回る
（画面は「上位 N 人を表示」と名乗る）。

## 表示設定

粒度は残す(`tictok.streamers.gifterMatrixGran` / `.battleMatrixGran`)が、
**カレンダーで選んだ日付は残さない**。期間別ランキングと同じ理由である。
