# 同時監視数を増やしたときに何が先に詰まるか

「監視数を増やしたらVPS 4GBで足りるか」への回答です。

> **前提の注意 (2026-09-01追記)**: 本文書の制約はすべて
> **「LIVE検出を自前のheadless Chromiumで公開pageに当てる」現在の実装**を前提にしています。
> 検出をvendor API(bulk live check / LIVE Alerts)へ移すと、
> **制約1(検出遅延)は丸ごと消え、監視数の上限もほぼ無くなります。**
> 先に [LIVE_DETECTION_VENDOR.md](LIVE_DETECTION_VENDOR.md) を読んでください。

**結論: RAMは足ります。先に詰まるのは(1)LIVE検出の遅れ、(2)diskです。**
どちらもRAMを増やしても解決しません。

## 1. 先に詰まる順

| 順 | 制約 | 監視数への依存 | RAMを増やして解決するか |
|---:|---|---|---|
| **1** | **LIVE検出の遅れ** | **線形に悪化** | ❌ しない(WAF対策の上限) |
| **2** | **disk(録画量)** | 同時録画数に線形 | ❌ しない |
| 3 | 画面を開いたときのWS message | 線形に増大 | △ 設定で減らせる |
| 4 | RAM | ほぼ増えない | — |

## 2. 制約1 — LIVE検出の遅れ（本命）

### 仕組み

`ProbeGate`(`tictok/collect/collector.py`)が**全監視のprobeを直列化**し、
間隔を次で決めます。

```python
spacing = max(LIVE_CHECK_MIN_PROBE_SPACING,   # 1.0秒
              60.0 / live_check_max_per_min,  # 既定 2.0 回/分 -> 30秒
              live_check_interval / count)    # 既定 60秒 / 監視数
```

**`live_check_max_per_min`(既定2.0)が全体の上限**です。監視数が2件を超えた時点で
この項が効き、**TikTokへのaccessは監視数に関わらず合計2回/分に固定**されます。
つまり1監視あたりの確認周期は監視数に比例して伸びます。

設定画面の説明にもそう書いてあります。

> 監視数が増えても合計がこの値を超えないよう確認間隔を自動で広げ、IP単位のブロックを
> 防ぎます。小さいほど安全ですが、個々の配信開始の検出は遅くなります。

### 実際の数値（既定値のまま）

| 監視数 | 1監視の確認周期 | **平均検出遅延** | 録り逃す長さ |
|---:|---:|---:|---|
| 4 | 2.0分 | **1.0分** | 冒頭1分 |
| 8 | 4.0分 | **2.0分** | 冒頭2分 |
| 10 | 5.0分 | **2.5分** | 冒頭2.5分 |
| 20 | 10.0分 | **5.0分** | 冒頭5分 |
| 30 | 15.0分 | **7.5分** | 冒頭7.5分 |
| 50 | 25.0分 | **12.5分** | 冒頭12.5分 |

**検出が遅れたぶんは録画の冒頭が丸ごと欠けます。**監視20件なら平均5分、
最悪10分ぶん録れません。短いLIVEは丸ごと取り逃します。

### 上限を上げてはいけません

`live_check_max_per_min` は最大30まで上げられますが、これは**IP単位のWAF対策**です。
`doc/LIVE_DETECTION.md` が記録するとおり、閾値を越えたIPはstub pageしか返されなくなり、
**全監視の検出が数分〜数時間止まります**(実測で229回連続失敗・5時間停止した事例あり)。

**datacenter IP(VPS)ではむしろ下げる方向の検討が要ります。**自宅の回線と違い、
IP帯そのもののevaluationが厳しいためです。ここは `doc/COST_ALTERNATIVES.md` の
go/no-go(WAF PoC)と同じ話で、**監視数を増やすほどWAFのriskも上がります**。

### 緩和策

| 手段 | 効果 |
|---|---|
| `live_check_schedule_enabled` を有効化 | 配信が始まりやすい時間帯へprobe予算を寄せる。**総量は変わらない** |
| 監視対象を絞る | 直接効く。probe予算は監視数で割られるため |
| IPを分ける(instanceを分割) | 効くが、単一instance lockとSQLiteの制約で**appは分割できない** |

`live_check_schedule_enabled` の既定がoffなのは、設定画面の説明どおり
「確認の総量が上限に達している状態では時間帯間に融通できる余剰が無く、実測で
検出の速さがほとんど変わらない」ためです。**既に上限に張り付いている場合は効きません。**

## 3. 制約2 — disk（¥1,000構成では即詰まる）

### 同時録画数に上限がありません

`auto_record` は on/off だけで、**同時録画数の上限設定もsemaphoreも存在しません**。
監視中の配信者が同時にLIVEになれば、その本数だけffmpegが起動します。

### 録画量

実測 0.92Mbps(318MB/46分)、現状は同時最大4本で **8.69GB/日**です。

| 監視数 | 録画量/日 | 40GB disk | 80GB disk | 160GB disk |
|---|---:|---:|---:|---:|
| 現状(同時4本) | 8.7 GB | 4.6日 | 9.2日 | 18.4日 |
| 1.5倍 | 13.0 GB | 3.1日 | 6.1日 | 12.3日 |
| **2倍** | **17.4 GB** | **2.3日** | **4.6日** | 9.2日 |
| 3倍 | 26.1 GB | 1.5日 | 3.1日 | 6.1日 |
| 5倍 | 43.4 GB | 0.9日 | 1.8日 | 3.7日 |

**¥1,000構成(disk 40〜80GB)では、監視を2倍にするとhot bufferが2〜5日になります。**
object storageへの送出が1日でも滞れば録画が落ちます。

`doc/CAPACITY_FORECAST.md` の `capacity_alert_days`(既定14)は、
この規模では**一度も鳴りません**。監視数に応じて1〜2日へ下げてください。

**storage費用も比例します。**保持38日 × 2倍 = ¥500 → 予算¥1,000の中では
保持期間を半分にするしかありません。

## 4. 制約3 — 画面を開いたときのWS message

`manager.snapshots()` は**全監視ぶん**のsnapshotを組み、`ws_recent_events`(既定200)件の
eventを載せます。`doc/EVENT_LOOP_BLOCKING.md` の実測では
**1接続あたり5,466,601 byte(1配信者ぶん、99.95%が `recent_events`)** でした。

1 event 約1.1KBなので、既定200件なら**1監視あたり約220KB**。監視20件で
**1接続あたり約4.4MB**になります。**11画面すべてがWSを張ります。**

現在は `asyncio.to_thread` へ逃がしてあるので event loop は止まりませんが、
組み立てとserializeのcostは監視数に比例します。監視数を増やすなら
**`ws_recent_events` を下げてください**(最小0)。画面が実際に使うのは末尾200件だけです。

## 5. RAM — 4GBで足ります

内訳です。**固定費が大半で、監視数に比例する部分はごく小さい**のが要点です。

| | 項目 | 目安 |
|---|---|---:|
| 固定 | OS + systemd | 200〜300 MB |
| 固定 | Python + libs(numpy / Pillow / fonttools / fugashi) | 250〜400 MB |
| **固定** | **SQLite page cache** — 書き込み接続 `cache_size=-131072`(128MB) + 読み取りpool 3本 × `-65536`(64MB) | **320 MB** |
| 固定 | `_user_cache` 上限(実測 875 byte × 40,000) | 33 MB |
| 固定 | headless Chromium 1本(resolverは**全監視で共有**) | 350〜700 MB |
| 変動 | **監視1件あたり**(`recent_events` 200件 + `timeline` 2,160件 + markers) | **1〜3 MB** |
| 変動 | 録画1本あたり(ffmpeg process) | 30〜60 MB |

### 見積り

```
監視20件 / 同時録画8本:
  固定 1.2〜1.8GB + 監視 20x2MB(40MB) + 録画 8x50MB(400MB) = 約1.7〜2.3GB
```

**4GBに収まります。**監視を50件にしても変動ぶんは +60MB 程度です。

**Chromiumが全監視で共有**なのが効いています(`BrowserLiveResolver` が常駐browserを
**1つ**持ち、contextを使い回してWAF通過状態を共有する設計)。監視ごとにbrowserが
立つ設計だったら、4GBは監視3〜4件で尽きていました。

### RAMより先に効く隠れた項目

`event_history` は最大5000まで上げられ、そのとき **1監視あたり約5.5MB**になります
(実測値からの換算)。**既定の200のまま運用してください。**監視50件で5000に
すると `recent_events` だけで約275MBです。

## 6. 結論

| 質問 | 答え |
|---|---|
| 4GBで監視数を増やせるか | **RAMは足ります**(監視50件でも変動は+60MB程度) |
| 何件まで実用的か | **検出遅延で決まります。**冒頭2分の欠けを許容するなら8件、5分なら20件 |
| ¥1,000構成で増やせるか | **diskが先に詰まります。**2倍でhot bufferが2〜5日。保持期間かdiskのどちらかを買い増す必要があります |
| RAMを増やせば解決するか | **しません。**上位2つの制約はどちらもRAMと無関係です |

### 増やすなら、順番はこうです

1. **`ws_recent_events` を下げる**(0〜50)。実装0行、即効
2. **`capacity_alert_days` を1〜2日へ**。diskが埋まる前に気づけるようにする
3. **object storageへの送出を確実にする**。hot bufferが薄いので、ここが唯一の生命線
4. **検出遅延の許容値を決める**。それが監視数の上限そのものになる
5. `live_check_max_per_min` は**上げない**。上げるならWAFで全停止するriskを引き受けることになる

# 付録: 「IPを分けて上限を取っ払う」案について

## 立場

**IP単位のrate limitを迂回するための分散は、この文書では扱いません。**
proxyの切り替え・fingerprintの回転を含めて、anti-abuse制御の回避にあたるためです。

ただし**やりたいこと(特定の配信者の検出を速くする)は、上限に触らずに達成できます。**
以下はその方法と、分散案が技術的にも割に合わない理由です。

## 1. そもそも今の実装は予算を配れていません

detectionには**2段の絞り**があります。

| 段 | 実装 | 効き方 |
|---|---|---|
| 個別 | `_live_check_sleep` = `live_check_interval × schedule_factor × backoff × jitter` | 監視ごとのsleep |
| **全体** | `ProbeGate.acquire()` = `max(1.0, 60/max_per_min, interval/count)` | **全監視を直列化** |

問題は **`ProbeGate` に優先度が無い**ことです。`acquire(priority)` の `priority` は
起動時・監視追加時の初回probe専用で、通常運用では**純粋なFIFO**です。

その結果:

* 監視が飽和すると、**全監視が一律 `監視数 × 30秒` 周期**へ収束します
* `schedule_factor` で「配信されにくい時間帯」を広げても、**空いた枠は全員に均等に散る**だけで、
  詰めたい監視へは行きません
* 逆に `schedule_factor` で間隔を詰めても、**gateの周期より速くはなりません**

`live_check_schedule_enabled` の既定がoffな理由(「上限に達している状態では融通できる
余剰が無く、実測で検出の速さがほとんど変わらない」)は、**機能の限界ではなくgateの
構造**によるものです。**配れる仕組みが無いので、配っても届かない**わけです。

## 2. 正しい対処 — gateを重み付きにする（総access量は不変）

`ProbeGate` の選択をFIFOから**重み付き**にすれば、**TikTokへのaccess総量を1回も
増やさずに**、重要な配信者の検出を数倍速くできます。

監視20件 / 予算2.0回/分のままでの比較:

| 配分 | 上位3件の平均検出遅延 | 残り17件 |
|---|---:|---:|
| 一様(現状) | 5.0分 | 5.0分 |
| **上位3件に50%** | **1.5分** | 8.5分 |
| 上位3件に70% | 1.1分 | 14.2分 |

**上位3件は現状の5分から1.5分へ、3.3倍速くなります。**
複数台に分けても、1台あたりの監視数が減るだけで**同じ効果**しか得られません。
**¥0で、IPも増やさずに達成できます。**

### 実装の規模

| 触る場所 | 内容 |
|---|---|
| `collect/collector.py` `ProbeGate` | `_next_allowed` の単一tokenを、重み付きの選択へ。待機中の監視から重み比で次を選ぶ |
| `core/settings.py` | 監視ごとの優先度(3段程度)。`SETTING_DEFS` ではなく監視対象の属性 |
| `store/settings_store.py` | `monitored_targets` へ priority 列 + migration |
| 画面 | 監視一覧で優先度を選べるように |

**小〜中規模(2〜4人日)** です。`ProbeGate` は約40行のclassで、
上限の計算(`_spacing`)はそのまま使えます。

### あわせて効くもの

**長期offline監視の自動減量。**現在の backoff は**失敗回数**にしか掛かりません
(`_live_check_sleep` の `2 ** failures`)。「3週間配信していない配信者」は
成功裏にofflineを返し続けるので、**満額の予算を消費し続けます**。
観測した配信頻度で重みを下げれば、その予算が実際に配信する人へ回ります。

重み付きgateがあれば、この減量が**そのまま活きます**(今の構造では、減らした
ぶんは全員に均等に散って消えます)。

## 3. 分散案が技術的に割に合わない理由

policy面を措いても、この app では成立しにくい構造です。

| 障害 | 内容 |
|---|---|
| **appを分割できない** | `core/process_lock.py` が単一instanceを強制。SQLiteは単一writer前提で `_lock -> _buf_lock` の契約の上に組まれている(`doc/STORAGE_SPLIT.md`) |
| **統合の仕組みが無い** | N台はN個のDBになる。`doc/HISTORY_MERGE.md` は**画面上のsession表示**の話で、instance間のdata統合ではない。fan台帳・ranking・全体解析はDBを跨げない |
| **費用が線形** | 案Z基準で2台¥2,000 / 3台¥3,000 / 5台¥5,000。**¥1,000の目標と正面から矛盾** |
| **IPは1つの信号にすぎない** | `doc/LIVE_DETECTION.md` の実測どおり、WAF通過後の `_waftokenid` は**TLS fingerprint等に紐づく**(移植すると403)。IPを変えれば通る、という構造ではない |
| **同一providerのIPは相関する** | datacenter帯はrange単位で扱われる。同じproviderで台数を増やしても独立にはならない |
| **失敗が静かに起きる** | shardが1つ塞がれても他は動くので気づけない。実測で**229回連続失敗・5時間停止**を誰も検知できなかった事例がある(`doc/LIVE_DETECTION.md`) |

とくに2番目が重い障害です。**この app の価値は横断集計(fan台帳・league・全体解析)に
あり、それはDBが1つであることに依存しています。**台数を増やすとその価値から先に失われます。

## 4. 結論

| やりたいこと | 手段 |
|---|---|
| 重要な配信者の検出を速くしたい | **`ProbeGate` の重み付け**(2〜4人日、access総量は不変、¥0) |
| 死んでいる監視に予算を食わせたくない | **配信頻度による重みの自動減量**(上とセット) |
| とにかく監視数を増やしたい | **検出遅延を受け入れる**。冒頭2分の欠けで8件、5分で20件 |
| それでも足りない | **監視対象を選び直す。**予算は監視数で割られるので、増やすほど全員が遅くなる |

**上限そのものは、上げるより「配り方を直す」方が実利があります。**
`live_check_max_per_min` を上げると全監視が数分〜数時間止まるriskを負いますが、
重み付けにはそのriskが1つもありません。
