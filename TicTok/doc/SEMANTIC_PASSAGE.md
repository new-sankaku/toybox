# 意味検索の1行は「文」ではなく「約25秒のpassage」

## 症状

シーン検索で意味検索の行を選ぶと、狙った台詞のかなり手前から再生が始まり、IN/OUTも広すぎる。

## 中身

意味検索は search_hits の行をそのまま埋め込まない。1文は短すぎて意味が乗らないので、
`semantic.build_passages` が **先頭から `TICTOK_SEMANTIC_PASSAGE_SECONDS`（既定25秒）以内 かつ
`TICTOK_SEMANTIC_PASSAGE_MAX_CHARS`（既定800文字）以内** で束ねてから埋め込む。返る行は
その束であって、当たった文ではない。

実データ（121,325 passage）の span は中央値 **24.5秒** / p90 28.8秒。狙った語がどこに居るかを
`お菓子` を含む passage で測ると:

| passage | span | 「お菓子」が出る位置 |
|---|---|---|
| rid=31 9319.9〜9345.2 | 25.2秒 / 7文 | 先頭から **+6.9秒** |
| rid=59 2332.8〜2357.9 | 25.1秒 / 8文 | **+18.5秒** |
| rid=74 706.4〜734.9 | 28.5秒 / 6文 | **+20.9秒** |
| rid=76 13759.1〜13788.9 | 29.8秒 / 10文 | **+17.7秒** |
| rid=148 3079.1〜3101.2 | 22.1秒 / 8文 | **+11.6秒** |

`openHit` は `hit.video_time`（passageの先頭行の秒）へ飛び、`hitCutRange` は
`[先頭行の秒, 末尾行の終わり]`＝passage全体をIN/OUTへ入れる。**時刻がずれているのではなく、
行が指す範囲が広い。** 語で一致（keyword）の hit は1行=1文なので、この症状は出ない。

## 手当て: 本文を1文ずつ押せるようにする

passageの本文は文を改行で繋いだもので、`hit_ids` と1対1に対応する（`_flush_passage` の
`"\n".join(bodies)` と `[r["id"] for r in group]`。実データ121,325件で食い違い0件）。この対応
だけを根拠に、`passageNode` が本文を `.vd-sent` へ割り、押された文の秒を
`/api/search/hits?ids=<id>` で **DBから引き直して** 開く。

- **秒をindexから読まない。** semantic index が持つのは vector・本文・hit_id だけで、時間軸の
  真実はDB側にしかない（文字起こしのやり直しで search_hits の秒だけが動く）。
- **行が消えていたら先頭へ飛ばさない。** 「indexが古い」と言って何もしない。落ちた文の代わりに
  passageの頭へ着地させると、直したはずのズレが別経路で戻る。
- 行数とid数が食い違う passage は文に割らない（割ると押した文と飛び先が別物になる）。

文単位で埋め込み直す案は採らない: 1 queryの埋め込みに実測32秒かかるため、表示中の passage の
文をその場で埋め込み直す形は画面の速度に乗らない。passageの粒度は検索の質のために要る。
