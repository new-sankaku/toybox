# 月額¥1,000で成立する構成 — AWS以外の選択肢

`doc/AWS_MIGRATION_COST.md` の続きです。AWSのminimum($33/月 = ¥4,900)を、
目標の**¥1,000**まで落とせるかを検討しました。

**結論から言うと、¥1,000は達成できます。ただしcloudではありません。**
自宅の常時稼働機を省電力機に置き換えるのが最安で、**月¥226**、
しかも**現状(¥2,489/月)より安くなります**。

## 1. なぜcloudでは¥1,000に届かないのか — 算術で決まります

AWSの内訳を分解すると、削れない項目が2つあります。

| 項目 | AWS Plan C | 性質 |
|---|---:|---|
| 常時compute | $24.00 | **24時間必要**。headless Chromium + collector + recorder |
| storage | $7.68 | **毎月264GBずつ増える** |
| request等 | $1.00 | 誤差 |

### storage は「最安のcloudでも」¥1,000に収まりません

録画は **8.69GB/日 = 264GB/月**で単調増加します(`doc/CAPACITY_FORECAST.md` 実測)。
1年目の平均保有量1.5TBを置くだけで:

| 置き場 | 単価 | 1年目平均(1.5TB) | 2年目平均(4.6TB) |
|---|---:|---:|---:|
| S3 Standard-IA | $0.0138/GB | ¥3,180 | ¥9,540 |
| **S3 Glacier IR** | $0.005/GB | **¥1,152** | ¥3,456 |
| B2級 ($6/TB) | $0.006/GB | ¥1,382 | ¥4,147 |
| 最安級 (€3.8/TB) | $0.0042/GB | ¥968 | ¥2,904 |

**業界最安の単価を使っても、1年目のstorageだけで予算をほぼ使い切ります。**
そして翌年には3倍になります。compute代($24 = ¥3,600)を足す余地はありません。

**cloudに録画を置く限り、¥1,000は算術的に不可能です。**

### 逆に言うと、録画さえcloudに置かなければ道はあります

eventのdataは録画とは3桁違います。`tictok.db` は実測506MBで、
264GB/月の録画に対して**桁が3つ違う**世界です。

**「録画をcloudに置くか」が唯一の分岐点**で、compute代の差はその後の話です。

## 2. 代替案の比較

| 案 | 構成 | 月額 | 録画の置き場 | 自宅障害への耐性 |
|---|---|---:|---|---|
| **A** ★推奨 | **自宅の常時機を省電力機へ** | **¥226** | 自宅(既存drive) | ✗ |
| B | A + 格安VPS(収集を冗長化) | ¥976 | 自宅(VPSから即転送) | ✅ |
| C | B のVPSを Oracle Always Free に | ¥226 | 同上 | ✅(ただしrisk有) |
| D | AWS Plan C | ¥4,900 | S3 Glacier IR | ✅ |
| E | 現状維持(主PC 24/7) | ¥2,489 | 自宅 | ✗ |

**A は D より21分の1、現状(E)より11分の1です。**

## 3. 案A — 常時稼働の役割を省電力機へ移す（月¥226）

### 考え方

現在は RTX 4070 Ti 搭載機が24時間動いています。しかし**24時間必要な処理にGPUは
1つも要りません**。

| 常時必要 | 必要な資源 |
|---|---|
| LIVE検出(headless Chromium) | CPU少・RAM 1GB |
| collector(TikTokLive WebSocket) | ほぼ無し |
| recorder(ffmpeg **stream copy**) | 実測 0.92Mbps×4本 = 3.7Mbps、書き込み0.1MB/s |
| FastAPI + 画面 | 利用者1人 |

| 間欠でよい | 必要な資源 |
|---|---|
| 焼き込み・超解像・文字起こし・BGM除去 | **GPU** |

**この非対称がそのまま答えです。**常時側を省電力機に移し、主PCはGPU作業のときだけ
起動します。

### 電気代（¥31/kWh で試算）

| | 消費電力 | 稼働 | 月間 | 月額 |
|---|---:|---:|---:|---:|
| 現状: 主PC 24時間 | 110W | 730h | 80.3kWh | **¥2,489** |
| 案A: 省電力機 24時間 | 10W | 730h | 7.3kWh | **¥226** |
| (参考) 主PCを1日4時間 | 200W | 122h | 24.4kWh | ¥756 |

消費電力はご自宅の実測値に差し替えてください。**式は上のとおりです。**

### 機材

**x86_64のmini PC(Intel N100級)を推奨します。**8〜16GB RAM、NVMe、idle 6〜10W、
実勢2〜2.5万円程度です。

Raspberry Pi 5 でも動きますが**arm64を推奨しません**。この projectは
`playwright` / `onnxruntime` / `fugashi` / `unidic-lite` に依存しており、
arm64 wheelの有無を1つずつ確認する手間が増えます。x86_64なら現在の環境がそのまま動きます。

既存のHDDはそのまま接続します。**録画dataの移動は不要です。**

### 回収期間

```
25,000円 ÷ (2,489円 - 226円) ≒ 11ヶ月
```

**1年で元が取れ、以降は月2,263円の黒字**です。cloudのどの案より安く、
しかも増え続けるstorage代がありません。

### 動くこと・動かないこと

| | 案Aの省電力機で |
|---|---|
| LIVE検出・collector・録画 | ✅ そのまま動く |
| 画面・検索・解析・切り出し候補 | ✅ 動く(集計readは遅くなる。下記) |
| `pack`(ts束ね) / `waveform` | ✅ stream copyとCPU処理なので動く |
| 焼き込み・超解像・文字起こし・BGM除去 | ❌ **GPUが要る** |
| `reprocess`(再mp4化) | △ AAC encode律速。46分の録画に47秒(12core実測)が数分になる。21.5h/日ぶんは厳しい |

**GPU機能は既定がすべて `0`(無効)なので、設定変更だけで済みます。**
`TICTOK_STT_ENABLED` / `TICTOK_UPSCALE_ENABLED` / `TICTOK_BGM_REMOVE_ENABLED` /
`TICTOK_SMILE_ENABLED` / `TICTOK_LAUGH_AUDIO_ENABLED` はすべて既定 `False` です。
**code修正は1行も要りません。**

### 集計readは遅くなります

現在の計測環境は12coreです。N100級(4core / SMTなし)では単thread性能が2〜3倍遅くなります。
実測の基準値:

| | 12core |
|---|---:|
| 934 battleのloop(ANALYZE後) | 154ms |
| events全scan | 59ms |
| 起動 | 1.65秒 |

N100では概ね2〜3倍と見込まれます(154ms → 300〜450ms程度)。
`GET /api/perf` と運用log画面の「API所要時間」で実測してから確定させてください。
`PRAGMA cache_size=-131072`(128MB)が効くので、RAMは**16GBを推奨**します。

### 外部から画面を見る場合

Cloudflare Tunnel か Tailscale を使えば、**port開放も固定IPも不要**で、
どちらも個人利用は無料です。自宅回線に穴を開けずに済みます。

### 唯一の未解決点 — GPU作業の受け渡し

省電力機がapp hostになると、GPU jobをどう主PCへ渡すかが問題になります。
`tictok/core/process_lock.py` が単一instanceを強制するので、
**2台で同時にappを起動することはできません**。

| 段階 | 内容 | 実装 |
|---|---|---|
| **A1** | GPU機能をOFFのまま省電力機へ移す | **0行** |
| A2 | GPU worker分離(主PCがjobを取りに来る) | 中〜大 |

**A1で始めるのが順当です。**現在の焼き込み完了率は1.8%、文字起こし完了率は58.2%
(`doc/CAPACITY_FORECAST.md`)なので、GPU作業はもともと間欠です。

なお **A2の実装はAWS案と同じ作業**です(`doc/AWS_MIGRATION_COST.md` §7-(2)
「移行で一番大きい実装」)。しかも自宅LANなら素材の受け渡しが**共有mountで済み**、
S3経由が要るAWS版より簡単です。**案Aを選ぶことで増える実装はありません。**

## 4. 案B — 案A + 格安VPS（月¥976）

案Aの弱点は、**自宅の回線・電源が落ちると収集も録画も止まる**ことです。
これを埋めるなら、収集だけをVPSへ出します。

```
[VPS 2〜4GB]  live検出 + collector + recorder
     |  録画は生成後すぐ自宅へ転送し、VPS側は数日ぶんのbufferだけ持つ
     v
[自宅 省電力機]  録画の保管 + 画面 + DB
     |  GPU作業のときだけ
     v
[主PC]
```

### なぜVPSならstorage代が乗らないのか

**AWSと料金体系が違うためです。**

| | AWS | 一般的なVPS |
|---|---|---|
| 転送量(外向き) | 100GB/月まで無料、以降 **$0.114/GB** | **月10〜20TB込み**、または無制限 |
| 264GB/月を自宅へ送る費用 | (264-100)×$0.114 = **$18.7/月** | **¥0** |

AWSで「録画を自宅へ落とす」構成が成立しないのは、この転送料のためです。
VPSでは264GB/月は無料枠のはるか内側で、**VPSのdiskは数日ぶんのbufferで足ります**
(40GBあれば4.6日ぶん)。

### 費用

| | 月額 |
|---|---:|
| VPS 2〜4GB級 | **¥750前後**(公表価格。要確認) |
| 自宅 省電力機の電気代 | ¥226 |
| **合計** | **¥976** |

VPSの価格は各社の公表値を確認してください。ここでは$5/月として計算しています。

## 5. 案C — Oracle Cloud Always Free（月¥226）

Oracleの Always Free には **Arm-based Ampere A1 Compute / Block Volume /
Object Storage / Archive Storage** が含まれ、30日の試用期間後も継続することを
公式pageで確認しました(`oracle.com/cloud/free/`)。

理論上、案BのVPS代が**0円**になります。ただし採用前に確かめる点が3つあります。

| 確認事項 | 内容 |
|---|---|
| capacity | Ampere A1 は人気regionで確保が難しいことが知られています。**取れるまで試す**性質のものです |
| 規約と停止 | Always Free枠のresourceが回収される条件を利用規約で確認してください |
| **arm64** | Ampere A1 は arm64 です。§3で述べた依存関係の確認が必要になります |

**「無料だが取れないかもしれない」ものを本番の常時収集に据えるかは、
判断が要ります。**案Bを本命に、案Cは試してみる位置づけが妥当です。

## 6. 全案に共通する go/no-go — TikTok WAF

`doc/AWS_MIGRATION_COST.md` §7-(1) と同じです。**cloudを使う案(B・C・D)には
全部かかります。**

`doc/LIVE_DETECTION.md` は「ゲートはIPではなくJS challengeを解けるbrowserかを見る」
と記録する一方、「VPN(特にdatacenter IP)では解決しない」とも書いており、
**datacenter IPでの挙動は実測されていません**。

**そして、安いproviderほどこのriskは高くなります。**格安VPS事業者のIP帯は
scraperに多用されており、evaluationはAWSより厳しい傾向があります。
一方、**国内VPS(さくら/ConoHa/Xserver等)は日本のIP帯で、
TikTok JPのCDNに対する経路も短い**ため、この用途では有利な可能性があります。

**案A(自宅)にはこのriskが一切ありません。**今と同じ自宅IPのままで、
すでに動いている実績があります。**これは案Aの隠れた最大の利点です。**

## 7. 推奨

```
案A1 (月¥226 / 実装0行 / risk無し)  ← まずここ
   ↓ 自宅の回線・電源障害が実際に問題になったら
案B  (月¥976 / VPS追加)             ← WAFのPoCを通してから
   ↓ GPU作業を自動化したくなったら
案A2 (GPU worker分離)               ← AWS案でも同じ作業。自宅なら共有mountで済む
```

**案A1は、code修正0行・cloud契約0件・月¥226で、現状より¥2,263安くなります。**
初期費用2.5万円は11ヶ月で回収されます。

目標の¥1,000は、cloudを使わないことで達成できます。
**cloudに払う¥4,900は、可用性を買う費用であって、安さの選択肢ではありません。**

## 8. この検討で採らなかった案

| 案 | 理由 |
|---|---|
| 録画をcloudのarchiveへ置く | 最安単価でも1年目¥968/月、2年目¥2,904/月。単調増加するので予算が固定できない |
| AWSで録画して自宅へ落とす | 転送料 $18.7/月。AWSの料金体系では成立しない |
| 録画の保持期間を短くして容量を抑える | `doc/RETENTION.md` の通り `.ts` は再取得不能な原本。容量のために原本を消すのは順序が逆 |
| 解像度・bitrateを落として録画量を減らす | 録画は `-c copy` のstream copy。落とすには再encodeが要り、CPU/GPUを常時使うことになる。本末転倒 |
| Raspberry Pi 5 (arm64) | 動くが、`playwright` / `onnxruntime` / `fugashi` のarm64確認が要る。x86 mini PCなら現行環境がそのまま動く |
