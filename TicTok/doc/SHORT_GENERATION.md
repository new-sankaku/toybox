# short（縦の短尺動画）の自動生成

盛り上がり検出が返す**時刻**を、投稿できる**成果物**まで通す経路。既存の候補・文字起こし・章立て・
焼き込み・高画質化はそのまま使い、この機能が足したのは「範囲を決める」「間を詰める」
「検品する」「metadataを付ける」の4つである。

配信そのものが9:16縦なので、世間のshort制作で最も重いauto-reframe（顔追従crop）は要らない。

**画面の口は無い。** 配信者動画の再生画面に置いていた「short（縦の短尺動画）」の節は、
同画面の情報量を落とすために外した。下見・投入はAPI(`short-plan` / `short`)を直接叩く。
型の作成は設定画面の「shortの型」に残っている。

## 段の並び

```
候補(core.spike)                       … 既存
  ↓  api/candidates.compute_clip_candidates
範囲の確定(media/clip_range)            … 新規
  ↓  発話・無音へ吸着 / 章で挟む / 尺で捨てる / 重なりを畳む
切り出し(media/clipper precise)          … 既存 + codec指定を追加
  ↓  焼く要素があれば range焼き込み(record/video_overlay)
間の詰め(media/tighten)                 … 新規
  ↓  無音の真ん中を落として繋ぐ
高画質化(record/upscale)                … 既存
  ↓
検品(media/clip_gate)                   … 新規
  ↓
metadata(ai/ai_analysis clip_meta)      … 新規
```

実体は `tictok/media/short.py` の `make_short()`、jobは
`tictok/api/media_jobs.py` の `_run_short_job()`（kind=`short`）。

## 型(clip_presets)

「どの尺でどう仕上げるか」の組を1行で持つ表。設定表(settings)ではないのは、**同時に複数
成立する値**だからである — settingsは1 keyに1値しか持てず、15〜60秒の型と30〜90秒の型を
併存させた時点で表現できない。key名に番号を埋めて増やす形は、型の数をcode側で固定する。

列と値域は `tictok/store/clip_presets.py` の `PRESET_FIELDS` が唯一の出所で、API・画面・
seedがそこを見る。表が空のときだけ初期の2型を入れる（全部消した状態は尊重する）。

## 範囲の確定

候補は移動窓を畳んだ区間なので、その中心を山とみなす。確定は4段:

1. **山を置く** — `peak_position`（既定0.65）の位置へ据える。中央に置かないのは、shortが
   「何が起きるか」を見せてから山へ入る必要があるため。
2. **章で挟む** — 山を含む章の外へ出さない。どの章にも入らない候補は挟まない（章立ては
   録画全体を覆う保証を持たない）。
3. **端を吸着** — 発話segmentの `start`/`end` と、無音spanの明け/始まりへ寄せる。
   `snap_max_shift_seconds` より遠い吸着先しか無い端は**動かさない**。
4. **尺で判定** — 下限に届かない／上限を超える範囲は**捨てる**。縮めて通すと、話の途中で
   切れた物が「成功した成果物」として出る。

捨てた候補は理由つきで返す（`REJECT_LABELS`）。数だけが減ると、検出が弱いのか範囲確定で
落ちているのかを切り分ける手段が無くなる。

下見は `GET /api/recordings/{id}/short-plan`。作らずに範囲だけを出す。

## 間の詰め

対象は**成果物**であって原本ではない。原本の時刻軸で計画して切り出し後へ写す形を採らないのは、
切り出しにkeyframeの前置きが付き、焼き込みも独自にCFRへ畳むためで、実物を測れば座標の
写し替えが1つも要らない。

無音spanは丸ごと落とさず `tighten_keep_seconds` を残す。残す位置は**両端**、落とすのは
真ん中 — 無音の端には発話の減衰と立ち上がりが乗っており、そこを落とすと語頭・語尾が欠けて
聞こえる。落とせる量が `MIN_REMOVAL_SECONDS` 未満の無音は詰めない（接合を1つ増やす代償に
見合わない）。

**呼ぶ順は焼き込みの後**。先に詰めると、焼き込みが参照する文字起こしの秒と実物の秒がずれる。

## 検品

`rc=0` は成果物が正しいことを意味しない。見るのは成果物そのもので、生成過程の申告は使わない。

| 判定 | 根拠 |
|---|---|
| 映像/音声trackの有無 | ffprobeのstream単位 |
| 片側trackの尾切れ | video/audioの尺差（container尺は長い側を名乗る — `OVERLAY_OUTPUT_INTEGRITY.md`） |
| 尺が型の範囲内か | 下限/上限 |
| ほぼ全編が無音 | silencedetectの合計 ÷ 尺 |
| 映像がほぼ真っ黒 | blackdetectの合計 ÷ 尺 |
| 字幕ありなのに発話0件 | 焼く材料の件数（画素からは数えられない） |

**落ちても成果物は消さない。** 消すと、なぜ落ちたのかを確かめる手段がその場で失われる。
呼び出し側は「合格していない」と名乗るだけで、理由はsidecar(json)にも書く。
測れなかった項目はNoneのまま残す（0で埋めると「無音0秒だった」という観測の捏造になる）。

## metadata

題名・説明・hashtag・表紙位置を局所LLMに作らせる（`analyze_clip_meta`）。章立てと同じ約束で、
**秒はmodelに書かせない** — 表紙の位置はmodelが選んだ行番号から、こちら側がsegmentの
`start` を引いて決める。範囲外の行番号は近い行へ寄せずに落とし、表紙なしで返す。

表紙は成果物ではなく**原本**の該当時刻から撮る。成果物から撮ると間の詰めで動いた分を写し
直す必要があり、写し損ねると別の瞬間の表紙が黙って出る。

cacheは `ai_analysis` 表（`kind=clip_meta` / `target_type=clip`）。1つの録画に複数のshortが
在るので、`target_id` は `<recording_id>:<start>-<end>` の文字列（milli秒まで持つ — 吸着で
範囲は数百ms動くため、秒で丸めると別の範囲が同じ行を指す）。

## 出力

```
<一時保存先>/<配信者>/_clips/
  <stem>_<開始>-<終了>[_題名].short.mp4     成果物
  <stem>_<開始>-<終了>[_題名].short.json    題名・説明・hashtag・検品結果
<一時保存先>/<配信者>/_screenshots/
  <stem>_shot<位置>[_題名].cover.png        表紙
```

置き場と名前の規約は切り出し・範囲焼き込みと同じ（`CLIP_OUTPUT.md`）。表紙だけが別のdirに
出るのは、静止画の置き場が動画と分かれているためで、決め方（一時保存先固定・配信者folderの下）
は同じである。sidecarをDBではなくfileにするのは、成果物と一緒に動かせるようにするため —
「最終保存先へ移動」で録画に随伴するとき、rootからの同じ相対位置へ一緒に移る。

作った範囲は見どころ(`bookmarks`、`origin='auto'`)へ1行残し、書き出し済みとして印を付ける。
次に同じ録画で走らせた
ときに同じ場面をもう一度出さないための唯一の手掛かりである（成果物のfileはDBに行を持たない）。

## codec

投稿へ回る出力なので、保存用の正規化(既定AV1)ではなく `TICTOK_SHORT_CODEC`（既定h264）を
使う。保存用がAV1で良いのは、その出力が再生されるのがこのPCの中だけだからで、shortは
機械の外へ出る。

## 実装中に見つかった既存の欠陥（修正済み）

どちらも実録画・実成果物で再現し、この機能を通すまで誰も踏んでいなかった。

### D1: smart cutがGPU環境で常に失敗する

`_head_args` が原本の `level_idc` をそのまま `-level` へ渡していた。ところがこの録画の源側は
**自分の宣言を満たしていない**: 432x864の配信が level 3.0(=30) を名乗るが、その解像度は
1,458 macroblock/frame で、30fpsなら 43,740 MB/s と level 3.0 の上限 40,500 を超える。

| encoder | level 30 | level 31 |
|---|---|---|
| libx264 | 通る（誤った宣言のまま書く） | 通る |
| h264_nvenc | **InitializeEncoder失敗（Invalid Level）** | 通る |

GPUのある環境ではこの配信者の録画のsmart cutが全て失敗していた。修正は `-level` を渡さず
encoderに選ばせること（実際の解像度・fpsを満たす最小のlevel＝実測31）。headは連結の先頭
なのでmp4のavcCはheadの値になり、常に原本以上になる。低い方へ倒れる経路が無いので、
head/tailの照合からは `level` を外した（`check_compatible(ignore=("level",))`）。

### D2: smart cutの音声が壊れる

源側の音声は **HE-AAC(SBR)**。smart cutは先頭1 GOPだけをAAC-LCへ焼き、残りは原本のpacketを
そのまま繋ぐので、1つのtrackにLCの構成情報とHEのframeが同居する。

実測（30秒の切り出し）:

| 経路 | 音声の復号error |
|---|---|
| copy（既定） | 0件 |
| **smart cut** | **error率77%**（`Number of bands (68) exceeds limit (45)`） |
| precise（全編再encode） | 0件 |

映像は正常なので、再生して音を聞くまで気付けない。shortは `precise` を使うことでこれを
踏まない（15〜90秒なら全編再encodeでも数秒で、原本のpacketを保つ価値＝素材出しはここには
無い）。**smart cut自体はまだこの欠陥を持つ** — 素材出し用途で使う場合は音声を確認すること。
