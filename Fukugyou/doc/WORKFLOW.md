## 0. 総工数と、週7時間で何週かかるか

| 段階 | 工数 | 週 |
|---|---|---|
| 段階0 棚卸し・逆算・販路・規約確認 | 7.0h | 週0〜1 |
| 段階1 困りごと集めと相手探し | 14.0h | 週1〜4 |

**工数と暦がずれる理由は、段階4 が薄いからです。** 26.0時間を8週に配ると週3.25時間で、**残りは2回目の入金を待っているだけ**です。ここは工数を増やしても縮みません。

> **第2版の3つの数字（110.9h / 114.3h / 118.3h）は、どれも採用しません。** 同一文書内に3つの総計が併存していたうえ、**自動化 道具6本の実装工数がどの総計にも入っていませんでした**（見積もり33〜88時間）。削減効果は22.7時間と称していましたが、§1 から積み上げ直すと17.35時間しか出ず、差額5.35時間は出所不明です。

> **したがって自動化は前提から外しました。** 削減17.35時間に対して実装33〜88時間なら、**回収には2.1〜5.6周が必要**です。本手順書は1周の設計なので、正味で赤字になります。「16週は自動化を前提にして初めて成立する」は逆で、**自動化すると21〜29週になります。**

> **上表は全部、手作業の数値です。** `AUTOMATION.md` の 道具は、2周目以降に回すか、または `AUTOMATION.md` §2 の制約を守れる範囲で1本だけ作る、という扱いに降格しました。**`AUTOMATION.md` §2 は「前回 道具を作って judgment が歪んだ」という失敗を自分で記録しています。** その再演を避ける意味でも、既定は手作業です。

## 1. この工程の制約は「依存」ではなく「資源」

- **週7時間の予算が壁です。** 依存関係を解いても総工数は縮みません。**並行作業で工数は縮みません。**
- 縮むのは**待ち時間**だけです。3種類あり、そこだけが並行化の効きどころです。

| 待ち時間 | 長さ | 自分の作業量 |
|---|---|---|
| 話を聞く相手の日程調整（連絡→返信→実施） | 1〜2週 | ほぼゼロ |
| **課金の周期（2回目の入金を待つ）** | **8週** | 有償提供の工数のみ（週3.25h） |
| 紹介ページの検索登録、税理士の回答、決済の審査 | 2〜4週 | 着火の30分だけ |

**設計目標は1つです: 待ち時間の長いものを、できるだけ早く着火する。**

## 2. 3本の track

| track | 中身 | 性質 |
|---|---|---|
| **A: 顧客接点** | 相手への連絡、聞き取り、有償提供、先行販売 | **待ち時間が長い。常に最優先で着火する。** 詰まると全体が止まる |
| **B: 机上調査** | 混み具合調べ、競合の価格の年表、撤退競合の探索、判定式の適用 | **いつでも詰められる。** A が待ちに入った週の穴埋め |
| **C: 外部依存の着火** | 税理士への問い合わせ、決済の申込、紹介ページの設置 | **着火だけして放置する。** 結果は数週後に返る |

**A が止まったら B を進める。B しか進んでいない週が2週続いたら、それは調査ではなく現実逃避です。**

## 4. 並行化の実際

### 常時並行する3つ

1. **連絡（A）と机上（B）** — 週1〜4 の全週。連絡は送って待つだけなので、返信を待つ間に机上を進めます。**連絡を後回しにして机上から始めると、聞き取りが丸ごと後ろにずれます。**
2. **紹介ページ（C）と段階4** — 週9〜10 に立てて放置します。**先行販売で使うページを先に作り、検索登録の待ち時間を先に消費しておく**のが目的です。**検索での表示数は関門ではありません**（既定値が流入ゼロなので、表示ゼロは需要の不在ではなく登録状態を測っているだけ。`MARKET_RESEARCH.md` §3 段階5）。
3. **税理士・決済（C）と全段階** — 週1で質問を送り、放置します。**有償提供で実際に請求する時点までに答えが要る**ので、逆算すると週1が期限です。ここが未確認だと段階4で8週止まります。

### 排他にすべき2つ

1. **混み具合調べは、段階0〜1 の後にしか置けません。** 先に調べると、棄却の道具が発見の道具に化けます。
2. **関門の判定と次の段階の作業を、同じ週に置きません。**

## 5. 最長経路と、前倒しできる唯一の場所

```
週1 連絡開始 →（1〜2週の返信待ち）→ 週4 聞き取り開始
  → 週8 関門3 → 週9 有償提供1人目の初回課金
  → 8週（2回の課金周期）→ 週16 2回目の入金 → 週17 着手判断
```

**後半8週は課金の周期であって工数ではありません。** 縮める方法は1つ、**最初の課金を早く始めること**です。

### 早期着火の規定（週6前後で判断）

聞き取りの途中で「**今すぐ人手でやってくれるなら金を払う**」と明言した人が現れた場合、**関門3を待たず、有償提供を1名だけ開始してよい**ものとします。

- **1名まで。** きっかけが未確定のまま3名を抱えると、外れた場合に8週を失います。
- 最大で **2週前倒し**（着手判断が週17→週15）。
- **使うか否かを週0の時点で決めて `hypothesis.md` に書いてください。** 走りながら「せっかくだから」で始めるのは関門の緩和と同じです。

### 短縮できない場所

- **2回目の入金は待つ以外にありません。** 初回だけで判断するのは、継続収入型で最も高くつく誤りです。
- **聞き取り12件を5週未満に詰めるのは、質を落とすだけです。** 1件2.0時間（聞き取り30分＋日程調整・移動・記録）で、週7時間の予算では週2〜3件が上限です。

## 7. 週次 routine

| 枠 | 時間 | 内容 |
|---|---|---|
| 平日夜 A | 1h | A（聞き取り1件＋記録、または肩代わり） |
| 平日夜 B | 1h | A（連絡・日程調整） |
| 平日夜 C | 1h | B（観察・机上） |
| 週末 | 4h | A の主作業 2h ＋ **整理と判断 1h** ＋ B/C 1h |

**週末の「整理と判断」1時間を絶対に削らないでください。** 無作為化試験が示した効果は 数値を取ることではなく、**取った 数値で判断を更新すること**から来ています。

この1時間で必ずやること:

1. `hypothesis.md` の仮説を、今週の事実に照らして更新（**上書きせず履歴として残す**）
2. `counter.md` に**仮説に不利な事実**を1つ書く（無ければ「今週は探したが無かった」と明記）
3. 判定基準表に今週の実績値を記入

## 9. 中断と再開

週によっては0時間になります。**失敗は、遅れを取り戻すために基準を緩めることです。**

| 状況 | 規定 |
|---|---|
| 1週 0時間 | 翌週へ。schedule を1週後ろへずらす |
| 2週連続で 0時間 | **判定基準を緩めず**、残作業を再見積もりして `hypothesis.md` に記録 |
| 段階4の途中で中断 | **顧客に必ず連絡する。** 対価を取っている以上、放置は事業判断以前の問題です。停止するなら返金するか、終了を明示的に伝える |
| 3か月以上の中断 | 段階1からやり直し。`observation.md` と `scan-*.md` は古くなっています |

## 10. この workflow 自体の限界

- **一度も実地で回されていません。** 1周したら実績時間を各段階に書き戻してください。見積もりが外れた箇所が次の改訂点です。
- **判定基準表の数値は本人が決めます。** 目標月収と獲得能力は本人の事情です。空欄のまま開始しないでください。
