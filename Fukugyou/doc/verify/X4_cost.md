## 1. 114時間の機会費用

### 1.1 外部の実測値は発見できませんでした（未確認）

「個人開発者が最小の道具を作って公開するまでの実工数」について、**測定された公開値を発見できませんでした。**

- WebSearch は本session の上限（200件）に到達済みで、追加検索を実行できませんでした。
- 代表例として参照される levels.io の『12 startups in 12 months』を実際に取得して確認しましたが、**製品ごとの構築時間（時間数・日数）の記載は一切ありません。** 記載があるのは「1か月に1本公開する」という枠と、収益到達の速さのみです。

したがって「114時間で何周作れるか」という問いには、**外部の証拠では答えられません。**

加えて、仮に事例が見つかっても**本手順書の設計原則に照らして証拠として使えません**。`MARKET_RESEARCH.md` §1 第5条は「成功者の因果説明は証拠にしない」と定め、Denrell (2003) と Golder & Tellis (1993) を根拠にしています。「あの人は2週間で作って当てた」は、まさにこの条項が禁じた生存者のみの標本です。**「すぐ作れ」派の主張も、手順書と同じかそれ以下の証拠水準しか持っていません。** ここは公平に記録しておきます。

### 1.2 では何で判定するか — 棄却1件あたりの工数

外部証拠が無い以上、**手順書の内部だけで機会費用を評価します。** 手順書自身が目的関数を「何個を、どれだけ安く、確信を持って捨てられたか」（§1 第4条）と定義しているので、評価軸は**関門ごとの「棄却1件あたりの工数」**です。

| 関門 | 限界工数 | 棄却率 | 棄却1件あたり | 棄却率の出所 |
|---|---|---|---|---|
| 関門0 販路・逆算 | 4.8h | 50%（仮置き） | 9.6h | **数値の記載なし。**「ここで多くの企画が死ぬ」という文のみ |
| 関門1 困りごと5人・候補15名 | 8.8h | 30%（仮置き） | 29.3h | **記載なし** |
| **関門2 混み具合 2/4** | **3.6h** | **64%（実測）** | **5.6h** | `G_thresholds.md`: 業務系22語中8語が通過 |
| 関門3 聞き取り 7/12 | 19.0h | 50% | 38.0h | 本文が「真の集中度50%の候補を81%落とす」と明記 |
| **関門4 3名全員が2回目も支払う** | **53.0h** | **14%** | **378.6h** | 手順書自身の月次解約4.9%から算出（下記1.3） |
| 関門5 先行販売 | 7.5h | 30%（仮置き） | 25.0h | 本文は「0/30でも判定保留」と明記 |

**結論: 最も安く最も多く殺すのは関門2（3.6時間、実測棄却率64%、自動化後は0.1時間）です。最も高く最も殺さないのは関門4（53.0時間、棄却率14%）で、そこに全工数の46%が置かれています。**

棄却1件あたりの工数で見ると、関門2と関門4の間には**68倍**の開きがあります。「外れを安く殺す」を目的関数に掲げた文書が、最も高い殺し方に最大の予算を配っています。

### 1.3 関門4の棄却率14%はどこから来るか（重い指摘その1）

手順書は月次解約率 **4.9〜5%** を「唯一 data に基づく前提」として扱い（§6.4／§6.5.1／§6.5.5）、必要到達人数の計算 `M = c·B ÷ (1 − e^(−c·T))` の全てにこの値を入れています。

同じ値を関門4に適用します。

```
1名が2回目も支払う確率 = 1 − 0.049 = 95.1%
3名全員が支払う確率   = 0.951^3 = 86.0%
→ 関門4の棄却率 = 14.0%
```

| 月次解約 | 3名全員が継続 | 関門4の棄却率 |
|---|---|---|
| 4.9%（手順書の前提） | 86.0% | **14.0%** |
| 10% | 72.9% | 27.1% |
| 20% | 51.2% | 48.8% |
| 21%以上 | 49.3%以下 | 50%超 |

**関門4が「半分を落とす関門」であるためには、月次解約が21%以上でなければなりません。** つまり次の2つは同時に成立しません。

- (a) 月次解約4.9%が妥当 → §6.5.1の到達計算は成立するが、**関門4は53時間かけて14%しか殺さない検査**になる
- (b) 肩代わりの2か月目継続はもっと落ちる（解約20%超） → **関門4は棄却装置として機能するが、§6.5.1の到達計算・必要到達人数・「週7hで成立する最低単価64,000円」の全てが前提を失う**

**どちらを採るにせよ、手順書のどこかを書き換える必要があります。** 現状は(a)を計算に使い、(b)を暗黙に信じて工数を配っている状態です。

（補足: 4.9%は PMF 到達済みの有償 SaaS 顧客集団で測った値で、人手提供の試行の2か月目継続とは母集団が違います。私は(b)が実態に近いと考えます。**しかしそれを認めるなら §6.5.1 の全表に「前提の外挿である」という但し書きが要ります。**）

### 1.4 証拠の階層と工数配分の対応

| 証拠階層 | 該当段階 | 工数 | 比率 |
|---|---|---|---|
| 1段目（自分が受け取った金） | 段階4＋段階5 | 60.5h | 53% |
| 2段目（platform の実測値） | 段階2 | 3.6h | 3% |

## 2. 段階4（53.0時間）を疑う

### 2.1 判定条件の定式化

**「手作業の肩代わりが最小実装より安い条件」を定式化します。**

記号:

| 記号 | 意味 |
|---|---|
| `Hc` | 肩代わりの実工数（現行 53.0h） |
| `Hi` | 同じ3名に出せる最小実装の工数 |
| `p` | この企画が外れる（棄却される）確率 |
| `σ` | 実装が外れた時に他企画へ再利用できる割合 |
| `w` | 週あたり可処分時間（7h） |

期待工数:

```
肩代わり先行 : Hc + (1 − p)·Hi     ← 当たれば結局 Hi は払う。肩代わりは純粋な追加
実装先行     : Hi − p·σ·Hi
```

**肩代わりが安い条件:**

```
Hc  <  p · Hi · (1 + σ)

σ = 0（再利用ゼロ）のとき:   Hc < p · Hi
```

**言葉にすると「肩代わりの工数が、棄却確率 × 実装工数 を下回るときだけ、肩代わりは安い」です。**

現行の `Hc = 53.0h` を代入します。

| 棄却確率 p | 肩代わりが正当化される最小実装工数 | 週7hでの実装期間 |
|---|---|---|
| 90% | `Hi` > 58.9h | 8.4週 |
| 80% | `Hi` > 66.2h | 9.5週 |
| 70% | `Hi` > 75.7h | 10.8週 |
| 60% | `Hi` > 88.3h | 12.6週 |
| 50% | `Hi` > 106.0h | 15.1週 |

再利用 σ = 0.3 を認めても、p = 0.7 で `Hi` > 58.2h です。

**つまり段階4を53.0時間かけて行うことは、「同じ3名に出せる最小実装が76時間以上（週7hで11週）かかる」場合にのみ正当化されます。**

### 2.2 76時間かかる実装とは何か

手順書が対象とする領域を考えると、この条件は**多くの場合に満たされません。**

満たされにくい理由が、手順書の内部に3つあります。

1. **段階0の関門2が「その作業を内側から知っていること」を要求している。** 当事者1名の承認まで取ります。**要件が既に分かっている人にとって、要件発見のための肩代わりの価値は小さくなります。** 段階0の関門を厳しくするほど、段階4の情報価値は下がるという逆相関があります。
2. **段階3の関門が「12件中7件が同じきっかけ」＝同質性の確認を要求している。** 同質と確認された相手に対して、なお8週間ひとりずつ手で対応するのは、**直前に確認した同質性を使っていません。** 同質なら1本の script が3名を賄えます。
3. **肩代わりの作業内容そのものが script 化対象である。** 成果物 `log/automation.md`（自動化候補の特定）が段階4の完了物に含まれている時点で、この作業が実装可能であることを手順書自身が前提にしています。

**条件が満たされる場合（＝段階4が正しい場合）も明示しておきます。**

| 肩代わりが実装より安くなる条件 | 判定の目安 |
|---|---|
| 要件が本人にも言語化できていない（毎回判断が違う） | 3名の作業手順を書き出して、分岐が10を超えるか |
| 実装が外部条件に阻まれる（相手側 system への接続許可、認証、data 提供の交渉） | 接続の交渉に要する暦が4週を超えるか |
| 成果物が「判断」であって「処理」ではない（人が読んで決める部分が本体） | 自動化しても人の確認が要る比率が5割を超えるか |
| 3名の作業が実は同質でない | 段階3の関門（7/12）を通っていれば、この条件は原理的に成立しにくい |

**上4つのどれにも該当しないなら、段階4は自己目的化しています。**

### 2.3 暦（判定日）は肩代わりを擁護するか

擁護します。ただし限定つきです。

8週間の課金周期は**肩代わりでも実装でも等しく乗ります**。差は「実装に要する暦だけ、初回課金が後ろにずれる」ことです。

| 最小実装 `Hi` | 初回課金の遅れ | 判定到達 |
|---|---|---|
| 20h | 2.9週 | 週18.9 |
| 40h | 5.7週 | 週21.7 |
| 60h | 8.6週 | 週24.6 |
| 120h | 17.1週 | 週33.1 |

肩代わり先行なら判定は週16です。**したがって「実装が40時間を超えるなら、肩代わりのほうが判定に5週以上早く着く」というのは正しい主張です。**

**しかしこれは「3名・8週・53時間」を正当化しません。** 早く課金を始めることが目的なら、必要なのは**1名に、1回、請求すること**であって、3名に8週間張り付くことではありません。前倒しの効果は最初の1名で取り切れます（§4.3）。

### 2.4 時間単価から見た段階4

| 想定単価 | 8週間の売上（3名×2か月） | 53.0時間あたり |
|---|---|---|
| 月4,500円 | 27,000円 | 509円/h |
| 月15,000円 | 90,000円 | 1,698円/h |
| 月50,000円 | 300,000円 | 5,660円/h |
| 月64,000円 | 384,000円 | 7,245円/h |
| 月150,000円 | 900,000円 | 16,981円/h |

**手順書自身の §6.5.1 が「目標50万円・週7時間で成立する最低単価は約64,000円/月」と結論しているので、生き残る単価帯では段階4の時間単価は7,000円以上あり、労働としては赤字ではありません。** ここは段階4への最も強い擁護です。

**ただし同じ §6.5.1 が、その単価帯で別の問題を作ります。** 単価150,000円なら目標契約数は5件です。

```
5件 × 1.5時間/週（手作業提供） = 7.5時間/週  >  可処分 7.0時間/週
```

**目標を達成した瞬間に、人手提供では可処分時間を超えます。** つまり高単価路線では肩代わりは検証ではなく事業そのものであり、**遅かれ早かれ実装しなければ目標に到達できません。** そして低単価路線は §6.5.1 の到達計算で既に死んでいます。

**結論: どの単価帯を選んでも実装は必要です。問われているのは「実装するか否か」ではなく「実装の前に53時間を人手に使うか」だけです。そして §2.1 の条件式は、その53時間を8.4時間程度まで縮めるべきだと言っています**（最小実装12時間・棄却確率70%を仮定した場合の上限）。

## 3. 各段階の見積もりの根拠

### 3.1 根拠は書かれていません（重い指摘その2）

**31項目の積み上げも、1項目ごとの算出根拠も、どの文書にも存在しません。**

- `WORKFLOW.md` §0 は「全31項目を積み直した実数です（内訳は `AUTOMATION.md` §1）」と書いていますが、`AUTOMATION.md` §1 は**12行の可否 map** であって31項目ではなく、しかも工数の総和を出していません。
- 137.0時間を再構成しようと試みた結果、最も近い組み合わせで **138.0時間**にしかならず、1.0時間の差を埋める項目を特定できませんでした。
- 「1時間」「1.5時間」「2.2時間」といった値に、**何件を何分で処理する前提かの記述が1つもありません。**

`CLAUDE.md` の「曖昧＝裏取りが無い」および `MARKET_RESEARCH.md` §1 第7条（標本・期間・分母を必ず書く）に照らすと、**この文書は自分の工数見積もりに対してだけ第7条を適用していません。**

```
段階3の未計上 4.5h を戻すと 7.03h/週  →  予算比 100%（余裕ゼロ）
```

**「週7時間の予算が壁です」と書いた文書が、16週のうち8週で自分の壁を破っています。** しかも本文は「週8〜15が最も重く（7.7時間）」と書くだけで、それが予算超過であることに触れていません。

### 3.6 候補15名では聞き取り12件は成立しません（重い指摘その3）

**手順書が内在的に仮定している歩留まりは 12/15 = 80.0% です。**

段階1の完了条件は「接触可能な候補者15名」、段階3の完了条件は「12件」。両者の間に他の供給源はありません（段階3の紹介依頼は、その段階3が始まってからしか効きません）。

歩留まりを「接触→返信 r／返信→承諾 a／承諾→実施 s」に分解して必要接触数を出します。

| 経路 | r | a | s | 歩留まり | 12件に必要な接触 |
|---|---|---|---|---|---|
| 経路1 現職・前職（強い縁） | 0.60 | 0.70 | 0.90 | 37.8% | **32名** |
| 経路1 現職・前職（並） | 0.40 | 0.60 | 0.85 | 20.4% | **59名** |
| 経路2 紹介 | 0.70 | 0.70 | 0.90 | 44.1% | **28名** |
| 経路3 制作報告の書き手 | 0.15 | 0.50 | 0.80 | 6.0% | **200名** |
| 見知らぬ相手（本文§3.3が引く英語圏cold email 4.1%） | 0.041 | 0.50 | 0.80 | 1.6% | **732名** |

**歩留まり80%を成立させるには返信率が 0.80 ÷ (0.7×0.9) = 127% でなければならず、数学的に不可能です。**

現実的な混成（実名30名を経路1で使い切り、残りを制作報告の書き手で埋める）:

```
実名30名 × 歩留まり20.4% = 6.1件
残り 5.9件を歩留まり6%の経路で埋めるには 99名の接触が必要
合計 129名  →  手順書の15名の 8.6倍
```

**時間のほうは足りています。** 週割りの連絡・日程調整は合計8.3時間で、`MARKET_RESEARCH.md` §6.5.1 が使う「1接触0.25時間」なら33名、10分なら50名に届きます。

**したがって欠陥は工数ではなく「15名」という数字です。** そして手順書はこの数字が使えないことを自分で書いています。

- §6.5.2:「反応率を±10ポイントの精度で測るには**93名**（真の率が20%前後と分かっていれば60名）が必要です」
- §6.5.2:「**15名しか使えないなら経路を1つに絞って**測ってください——2経路に分けると各7〜8名になり、どちらの数字も意味を持ちません」
- 段階1の完了条件:「**経路別の**連絡数と返信数を記録した」← 4経路に分けると1経路3.75名

**「経路を1つに絞れ」と書いた3節あとで「経路別に記録せよ」を関門にしています。** 15名では両立しません。

## 4. 中断・撤退の設計

### 4.1 最も早く「駄目だ」と分かるのは何週目か

**週0です。** そしてそれは正しい設計です。

- 関門0の中核である §6.5.1 の逆算（必要到達人数）は週割りで**0.6時間**しか要らず、それだけで「目標50万円・週7時間なら単価64,000円未満は全て不可」という結論が出ます。単価4,500円の企画は**36分の算数で死にます。**
- 手順書はこれを最初に置いています。**「最も安く最も多くを殺す検査を最初に置く」という原則に、関門0は完全に適合しています。**

**逆に言えば、残り113.7時間の限界情報量は、最初の0.6時間よりはるかに小さいということです。** これが機会費用の答えの中核です。114時間全体の是非ではなく、**最初の1時間が突出して効率的で、そのあと急速に逓減する**という形をしています。

### 4.2 並び替えるべき箇所

| # | 現行 | 提案 | 理由 |
|---|---|---|---|
| 1 | 混み具合調べ（実測棄却率64%・自動化後0.1h）を**週3**に置く | **週1末**へ前倒し | 必要な入口語彙は週1の観察1.6hで揃う。**週2の連絡5.5時間を、64%の確率で無駄になる企画に使わずに済む。** 手順書は「段階0〜1の後にしか置けない」と書いているが、必要なのは段階1の**観察**であって**接触**ではない。前倒し費用はゼロ |
| 2 | 紹介ページ 3.0h を**週3**に置く | **週12**へ後送 | 目的は「検索登録の待ち時間を先に消費する」だが、手順書自身が「検索での表示数は関門ではない」「既定値は流入ゼロ」と明記している。**待ち時間を消費しても関門が1つも早まらない。** 週3に置く実害は、判定に効かない成果物を早期に作ることで生じる sunk cost と anchoring |
| 3 | 最初に金が動くのが**週8**（段階4の1人目） | **週3に「有償probe」を新設**（+3.0h） | 下記4.3 |
| 4 | 早期着火を「関門3を待たず1名」と規定（週6前後） | 規定は残すが、**判定の主対象を有償probeへ移す** | 現行の早期着火は「相手が自発的に言い出した場合」という受動条件で、こちらから殺しに行く検査になっていない |

### 4.3 週3の「有償probe」— 最も安く1段目の証拠を取る

**証拠階層の1段目（自分が受け取った金）に到達する最小の実験は、3名に8週ではなく、1名に1回です。**

| | 現行の段階4 | 提案する有償probe |
|---|---|---|
| 内容 | 3名に8週間、人手で提供 | **1名に1回だけ**人手で提供し、実際に請求して入金を確認する |
| 工数 | 53.0h | **3.0h** |
| 初回入金 | 週8 | **週3** |
| 得られる証拠 | 継続決済（2か月目） | 初回決済（継続は分からない） |
| 殺せるもの | 「継続しない」 | **「そもそも誰も金を出さない」** |

**「そもそも1円も動かない」という最も多い外れ方を、3.0時間・週3で殺せます。** 現行はこれを週8まで、53時間の入口まで持ち越しています。

この probe は手順書の原則と衝突しません。証拠階層の1段目（自分が受け取った金）そのものであり、§6.3 の「決定は段階4〜5の実価格で行う」とも整合します。**むしろ現行の設計のほうが、1段目の証拠を最も遅く・最も高く取りに行っています。**

### 4.4 撤退の規定そのものは良好

以下は本検証で崩れませんでした。維持を推奨します。

- 段階3の中間関門（6件時点で投資済み2件以下なら中止）— futility 停止として正しい形
- 「候補15名が集まらない場合の縮退規定を段階0で決めておく」— 走行中の緩和を封じる正しい設計
- 「段階4の途中で中断したら顧客に必ず連絡する」— 対価を取っている以上、当然の規定
- 「関門の判定と次の段階の作業を同じ週に置かない」

## 8. 最も重い指摘 3件

1. **関門4（53.0時間・全工数の46%）は、手順書自身の解約率前提では棄却率14%しかない。** 月次解約4.9%を §6.5.1 の全計算で使いながら、同じ値を関門4に入れると `0.951³ = 86%` が通過する。棄却率を50%超にするには解約21%以上が必要で、その場合 §6.5.1 の到達計算・必要到達人数・「最低単価64,000円」が全て前提を失う。**どちらかを書き換えなければならない。**

2. **自動化は正味で赤字であり、その実装工数はどの総計にも計上されていない。** 削減22.7時間（§1から積み上げると17.35時間しか出ず、5.35時間は出所不明）に対し、script 6本の実装は33〜88時間。「16週は自動化を前提にして初めて成立します」は逆で、**自動化すると21.0〜28.9週になる。** 回収には2.1〜5.6周が必要だが手順書は1周設計。加えてこれは `AUTOMATION.md` §2 が自ら警告した前回の失敗（tool を作って judgment が歪んだ）の再演の形をしている。

3. **候補15名で聞き取り12件は成立しない（必要返信率127%）。** 歩留まりを分解すると必要接触は経路1で32〜59名、混成で129名。**そして手順書は §6.5.2 で「15名では何も判定できない」「経路を1つに絞れ」と書いた3節あとで、段階1の関門に「経路別の連絡数と返信数」を置いている**（4経路で1経路3.75名）。時間は足りている（連絡8.3hで33〜50名に届く）ので、欠陥は工数ではなく**15という数字**にある。

**併せて記録**: 段階0〜2は週割り表と完全一致するが、工数の7割を占める段階3〜5は12.9時間ぶん一致しない。総計は同一文書内に 110.9h／114.3h／118.3h の3つが併存。週8〜15は表記7.7h/週で、**自ら壁と呼んだ週7時間の予算を10%超過している**（未計上分を戻すと121%）。
