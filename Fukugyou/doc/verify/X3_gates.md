## 1. 百分位数で閾値を置くことは何を見ていないか

### 1.1 結論

**段階2 の gate は、絶対的に成立するかを一度も見ていません。** これは推測ではなく、条件式の定義から出ます。

`thresholds.yaml` の4条件はすべて「同じ標本の中での順位」です。

| 条件 | 式 | 参照先 |
|---|---|---|
| C1 | `hits ≤ p25(hits)` | 同じ22語の分布 |
| C2 | `installs ≥ p75(installs)` かつ `rating ≤ p25(rating)` | 同じ176件の分布 |
| C3 | `kw_median_months ≥ p75(...)` | 同じ22語の分布 |
| C4 | `kw_median_complaint_ratio ≥ p75(...)` | 同じ22語の分布 |

**参照先が同じ標本なので、この4条件は標本を平行移動しても同じ答えを返します。** 22語すべてが儲からない領域でも、必ず p25 と p75 は存在し、必ず約25%が「該当」します。**通過語が出ることは、通過語が儲かることの証拠を1 bit も含みません。** G 自身が §8 で「合格率が 10〜36% から大きく外れたら閾値ではなく keyword 集合を疑え」と書いており、gate が**標本の形にしか反応しない**ことを設計者も認識しています。

### 1.2 では絶対条件はどこに在るか

在ります。3か所です。

| 場所 | 絶対条件 | 性質 |
|---|---|---|
| §6.4 / §6.5.1（段階0） | 必要月次純増契約数、必要到達人数、必要時間/月 ≤ 30.3時間 | **自分側**の絶対条件。市場側は見ていない |
| §3 段階4 | 3名全員が2か月目も支払った | 金。最も強い |
| §3 段階5 | 先行販売 成約件数 / 提示人数 | 金 |

つまり手順書は絶対条件を持っています。**問題は「持っていない」ことではなく、段階2 の相対 gate と段階0 の絶対条件が一度も接続されていないことです。**

### 1.3 接続の欠落を数値で示す

§6.5.1 の式 `M = c·B ÷ (1 − e^(−c·T))` を再実装し（doc の表を再現できることを確認: 単価15,000円・目標50万円で M=4.01件/月・必要到達736人・184時間 = doc の値と一致）、**「週7時間で成立する最低単価」**を目標別に解きました。

| 目標粗利/月 | 副業月収分布での位置 | 成立する最低単価 | 年額換算 | USD |
|---|---|---|---|---|
| 50,000円 | **中央値** | **6,523円/月** | 78,272円/年 | **$522/年** |
| 92,445円 | 平均 | 12,060円/月 | 144,718円/年 | $965/年 |
| 200,000円 | 中央値の4倍 | 26,091円/月 | 313,090円/年 | $2,087/年 |
| 500,000円 | 中央値の10倍 | 65,227円/月 | 782,724円/年 | $5,218/年 |

（§6.5.1 の設定値をそのまま使用: 利益率70%・解約 月5%・18か月到達・知人60名は成約率10%・以降 0.5%・1接触0.25時間・可処分30.3時間/月。doc の「約64,000円」に対し本計算は65,227円で一致）

**副業月収の中央値を狙うだけでも、顧客1件あたり年額 $522 が下限です。**

ここに §7.2（platform の経済条件）を重ねます。**手順書自身の表です。**

| 生態系 | 決済の仕組み | §7.2 の記述 |
|---|---|---|
| WordPress.org | **なし** | 「有料配布そのものが不可。全 code が GPL 互換必須」 |
| VS Code Marketplace | **なし** | 「有料 extension 非対応」 |
| Chrome Web Store | **なし** | 「2021-02-01 に課金停止済み。自前 決済の仕組み が必須」 |
| Atlassian Marketplace | あり | 「有料 app が当然の生態系。導入者は決裁の通った企業」 |

**閾値を実測した4生態系のうち3つは、その生態系の中で金を受け取れません。** C2 の `installs ≥ 52,500` は**無料 install の件数**であり、C1/C3/C4 も金に触れません。段階2 は「無料配布の生態系で、無料採用の順位」を測っている一方、段階0 は「年 $522 以上で売れなければ成立しない」と言っています。**この2つが同じ手順書の中で一度も突き合わされていません。**

WordPress の freemium（pro 版を外部配布）や VS Code の外部 license は可能ですが、**その場合 C1〜C4 が測っている install/rating は有料版の指標ではありません。** つまり gate は、判定したい対象（金を払う顧客が居るか）とは別の量（無料版の順位）を測っています。

**Atlassian だけが例外です。** 決済の仕組みがあり、導入者が決裁済み法人で、`installs` の p75 が982件と3桁——年 $522 × 数百件は現実的な帯です。**4生態系のうち、段階0 の絶対条件と整合するのは Atlassian 1つだけ**というのが本検証の読みです。

### 1.4 §2（情報源の採否）との関係

§2.1 の evidence hierarchy は正しい順序です（1. 自分が受け取った金 → 2. platform 実測値 → …）。**段階2 の data は hierarchy の 2 位に置かれていますが、gate としては 1 位（金）の代理になっていません。** hierarchy は「情報の強さ」の順序であって「何を測っているか」の一致を保証しません。install 数は実数（推定でない）ですが、**実数であることと、意思決定に必要な量であることは別です。** §2.4 の「分母は何か」という問いを段階2 に適用すると、C2 の分母は「無料で入れた人」です。

## 2. 通過率の実測と、偽陽性/偽陰性の非対称性

### 2.1 実測通過率（要求された数値）

G の語別判定表から再計算しました。**22件の検証 keyword のうち 8件（36.4%）が通ります。**

| 生態系 | 評価可能な条件数 | 各条件の成立数 | ≥1条件 | **≥2条件（現行 gate）** | ≥3条件 |
|---|---|---|---|---|---|
| WordPress | 4 | C1 6 / C2 11 / C3 6 / C4 6（n=22） | 95.5%（21語） | **36.4%（8語）** | 0.0%（0語） |
| Atlassian | 3 | 6 / 9 / 6（n=22） | 68.2% | **22.7%（5語）** | 4.5%（1語） |
| VS Code 開発系 | 3 | 5 / 8 / 5（n=20） | 70.0% | **20.0%（4語）** | 0.0% |
| Chrome | 2 | 6 / 3（n=10） | 80.0% | **10.0%（1語）** | — |

### 2.2 この通過率は「4条件を組んだ」ことで生じているか — **生じていません**

各条件の成立率をそのままにして、**どの語が該当するかを無作為に振り直した**場合の通過率を計算しました。

- 解析解（独立 Bernoulli, p = 0.273 / 0.500 / 0.273 / 0.273）: **P(≥2 of 4) = 0.3989 → 期待 8.78語**
- 列ごとの permutation 検定（B=200,000）: 平均 8.77語、sd 1.20、**観測値 8語は null 分布の 27.4 percentile**

**実測 8語は、条件の中身を壊した null の期待値 8.78語と区別がつきません。** 「4つの条件を測って2つ以上を要求する」という構造が、通過率に対して何もしていません。通過率 36% は、条件の設計ではなく **p25/p75 という切り方が周辺成立率を約25%に固定していること**だけから出ています。

さらに、通過率は**その生態系の API がたまたま公開している field 数**で決まります。周辺成立率を 0.273 に揃えて計算すると:

| 評価可能な条件数 | P(≥2) |
|---|---|
| 2 | 0.074 |
| 3 | 0.183 |
| 4 | 0.301 |
| 5 | 0.415 |

実測（Chrome 0.10 / VS Code 0.20 / Atlassian 0.23 / WordPress 0.36）はこの列とよく一致します。**同じ候補でも、Chrome で評価すれば 10%、WordPress なら 36% ——3.6倍の差が、市場ではなく「その marketplace が support_threads を返すかどうか」で決まります。**

### 2.3 4条件は同じものを測っていない（負の相関）

gate が意味を持つには、4条件が「この入口は成立する」という共通の潜在量を測っている必要があります。測っているなら条件どうしは**正に**相関するはずです。

| 対 | n11 | n10 | n01 | n00 | phi | Fisher p |
|---|---|---|---|---|---|---|
| C1×C2 | 1 | 5 | 10 | 6 | **−0.408** | 0.149 |
| C1×C3 | 2 | 4 | 4 | 12 | +0.083 | 1.000 |
| C1×C4 | 0 | 6 | 6 | 10 | **−0.375** | 0.133 |
| C2×C3 | 2 | 9 | 4 | 7 | −0.204 | 0.635 |
| C2×C4 | 2 | 9 | 4 | 7 | −0.204 | 0.635 |
| C3×C4 | 1 | 5 | 5 | 11 | −0.146 | 0.634 |

**6対の平均 phi = −0.209。** 列 permutation による null は平均 −0.0001・sd 0.0895・90%範囲 [−0.141, +0.152] で、**片側 p = 0.0035**。個々の対は有意ではありませんが、6対そろって負に振れる確率は小さい値です。

1因子 model（4条件がいずれも共通潜在量 Z に正の負荷 ρ_i で載る）では、対の相関は ρ_i·ρ_j となり**必ず非負**です。**観測は逆符号なので、1因子 model は棄却されます。**

負になる機構は明らかです。hit 数と上位8件 install 中央値の Spearman 相関は **+0.568（p=0.006）**で、「検索結果が薄い（C1）」と「巨大な既存者が居る（C2）」は**同じ軸の反対側**です。薄い語には大手が居ません。C1 と C2 は構造的に排他に近い。

**ここから出る帰結が重要です。** 4条件が排他的な別経路（どれか1つ成立すれば良い）なら、正しい集約は **1-of-4（OR）** です。しかし 1-of-4 の通過率は **95.5%（21/22）**で、gate として何も落としません。逆に共通潜在量を測っているなら 2-of-4 に意味がありますが、その model は data に棄却されています。**2-of-4 を正当化する構造が、どちらの読みでも存在しません。**

### 2.4 偽陽性/偽陰性の非対称性 — 尤度比で評価する

真偽の正解 label が無いので偽陽性率そのものは推定できません。代わりに、**gate が事前確率をどれだけ動かすか（尤度比 LR）**を1因子 model で計算しました。ρ は各条件が真の潜在量に載る強さです。

| ρ | P(通過 \| 良い候補 = +1sd) | P(通過 \| 悪い候補 = −1sd) | **LR** | 含意される対の相関 ρ² |
|---|---|---|---|---|
| 0.0 | 0.399 | 0.399 | **1.00** | 0.000 |
| 0.1 | 0.463 | 0.335 | 1.38 | 0.010 |
| 0.2 | 0.527 | 0.274 | 1.92 | 0.040 |
| 0.3 | 0.590 | 0.211 | 2.80 | 0.090 |
| 0.5 | 0.722 | 0.098 | 7.38 | 0.250 |

**観測された対の相関は負（平均 −0.209）です。** 好意的に「真の ρ² は 0 以上だが小標本の揺らぎで負に見えた」と読んでも、90%上限 +0.152 から **ρ ≤ 0.39 → LR ≤ 約3**、点推定に従えば **LR ≈ 1.0（＝情報ゼロ）**です。

### 2.5 適正な通過率はいくつか — 労力の期待値から解く

**通過率を単独で「高すぎる/低すぎる」と論じることはできません。** 適正値は gate の識別力（LR）と、候補を作り直す cost で決まります。手順書の時間見積りを使って解きました。

- 候補を1つ作り直す cost = 段階0（4.8h）+ 段階1（8.8h）= **13.6h**
- gate 自身 = 段階2 **3.6h**
- gate の下流 = 段階3（19.0h）+ 段階4（53.0h）+ 段階5（7.5h）= **79.5h**
- 目的関数: **成立する入口1つに到達するまでの期待労力**

π（段階1 を通った候補が本当に成立する事前確率）= 0.2 として:

| LR | 最適な通過率 q | 期待労力 | gate 無しとの比 |
|---|---|---|---|
| 1.0 | 1.00（＝gate を使わない） | 484h | 1.04x（**gate は損**） |
| 1.6 | **0.70** | 364h | 0.78x |
| 3.0 | 0.47 | 271h | 0.58x |
| 8.0 | 0.30 | 205h | 0.44x |
| （gate 無し） | — | 465h | 1.00x |

**現行の q = 0.36 は LR ≈ 5〜6 の gate に対する最適設定です。** data が支持する LR（1.0〜1.6）に対する最適値は **q ≈ 0.70〜1.00**。つまり現行 gate は、示せている識別力の**約2倍厳しく**設定されています。

そして gate を走らせること自体の損益分岐点:

| π | q=0.36 で gate が労力を節約するのに必要な LR |
|---|---|
| 0.10 | **1.43** 以上 |
| 0.20 | **1.51** 以上 |
| 0.30 | **1.62** 以上 |
| 0.50 | **2.16** 以上 |

（候補の作り直し cost を 13.6h でなく 30h / 60h / 120h と重く見積もると、必要 LR は 1.85 / 2.32 / 2.94 に上がります。**現実には「その作業を内側から知っている領域」は替えが利かないので、13.6h は下限です**——§1 第2条は斯業経験を最強の予測変数（2.4倍）としており、それを捨てる cost は時間では測れません）

**必要 LR 約1.5 に対し、示せている LR は 1.0〜1.6。gate が労力を節約するかどうかは、data からは決着していません。**

### 2.6 決定的な点: gate は 22語ではなく 1〜3 候補に当たる

§3 段階2 は「**段階0〜1 で出た入口にのみ適用**」と明記しています。22語の list に当てるのではなく、斯業経験から出た **1〜3個**の候補に当てます。

| 通過率 | 候補が全滅する確率 k=1 | k=2 | k=3 |
|---|---|---|---|
| 0.36（WordPress） | **64.0%** | 41.0% | 26.2% |
| 0.23（Atlassian） | 77.0% | 59.3% | 45.7% |
| 0.20（VS Code） | 80.0% | 64.0% | 51.2% |
| 0.10（Chrome） | 90.0% | 81.0% | 72.9% |

**候補が1つなら、識別力の示せていない gate が 64〜90% の確率でそれを殺します。** 手順書が最も強い予測変数と認定している資産（§1 第2条）を、LR ≈ 1 の判定で捨てることになります。

V5 §3.5 は AND funnel の感度低下（5段で 0.33）を「意図した trade-off」と評価し、手順書もそれを継承しています。**その評価は「各段に識別力がある」ことを前提にしています。** 識別力が示せていない段については、感度低下は trade-off ではなく**ただの損失**です。

### 2.7 判定

**gate として機能していません。** 通過率 36.4% は妥当な水準に見えますが、(a) その水準は条件の中身と無関係に p25/p75 の切り方から出ており（null と区別不能）、(b) 4条件は共通潜在量を測っておらず（対の相関が負）、(c) 通過率は市場でなく API の field 数で 3.6倍動き、(d) 現行の厳しさは示せている識別力の約2倍です。

**ただし段階2 が無価値だとは言っていません。** G_thresholds.md が発見した事実——「WordPress の上位8件は半数が1か月以内に更新される」「生態系ごとに install が3桁違う」「Atlassian の `lastModified` は使えない」——は、その生態系に参入する前に知っておくべき**記述的な情報**として明確に有用です。**問題は、それを「通す/落とす」の判定に変換したことです。**

## 3. rule of three の適用は正しいか

### 3.1 前提

§3 段階5 は「接触30名から0件なら conversion は約10〜12%未満（片側9.5% / 両側11.6%）」としています。この計算は **30試行が独立同分布**であることを前提にします。片側上限は `1 − 0.05^(1/n)`（n=30 で 9.50%）です。

### 3.2 30件は独立か — **独立ではありません**

手順書の設計上、30件は次を共有します。

- **同一経路**（§6.5.2 の経路1: 現職・前職の関係者。§3.2 の名簿）
- **同一時期**（段階5 は週14〜16 の3週間）
- **同一の話し方**（同じ landing page・同じ提示文）
- **同一の価格・同一の価値提案**（判定対象そのものが1つ）

これは cluster 標本です。同じ職場・同じ業界・同じ時期の相手は、成約するかどうかが相関します。

### 3.3 計算: cluster 相関を入れたときの上限

beta-binomial（cluster 内 ICC = ρ）で `P(0件) = 0.05` を解き、片側95%上限を求めました。

**n=30・0件のときの片側95%上限**

| ICC | 3経路×10名 | 5経路×6名 | 10経路×3名 | 単一経路30名 |
|---|---|---|---|---|
| 0.00 | 9.50% | 9.50% | 9.50% | 9.50% |
| 0.05 | 11.57% | 10.68% | 9.99% | **15.5%** |
| 0.10 | 13.55% | 11.86% | 10.48% | **20.7%** |
| 0.20 | **17.49%** | 14.26% | 11.54% | **30.7%** |
| 0.30 | **21.62%** | 16.80% | 12.69% | **40.9%** |

**実効試行数**（同じ上限を与える独立試行数）:

| ICC | 3経路×10名 | 単一経路30名 |
|---|---|---|
| 0.05 | 24.4 | 17.8 |
| 0.10 | 20.6 | 12.9 |
| 0.20 | 15.6 | 8.2 |
| 0.30 | 12.3 | 5.7 |

**同じ上限 9.5% を回復するのに必要な接触数**（1経路10名の場合）:

| ICC | 必要な経路数 | 必要な総接触数 |
|---|---|---|
| 0.05 | 4 | **40名** |
| 0.10 | 5 | **50名** |
| 0.20 | 6 | **60名** |
| 0.30 | 8 | **80名** |

### 3.4 ICC はどれくらいか

**本検証では実測していません（未確認）。** 社会 network を通じた勧誘の ICC についての公表値を、本環境からは確認できていません。ただし判断には十分です。**ICC = 0 は「同じ職場の同僚10名の反応が、無関係な10名の反応と同じだけばらつく」という主張**で、これは擁護できません。0.1〜0.3 の範囲を作業仮説に置くのが妥当で、その範囲での上限は **10.5%〜21.6%**、単一経路なら **20.7%〜40.9%** です。

### 3.5 もう1つの独立性違反 — 「同じ提示」は試行を1回にする

より深い問題があります。30名すべてに**同じ価格・同じ文面**で提示した場合、失敗の原因が「需要が無い」ではなく「文面が悪い」「価格が1桁ずれている」であれば、**30件は独立な30試行ではなく、1つの提示設計に対する1回の試行**です。ICC → 1 の極限で上限は事実上「不明」に発散します。

**rule of three が言えるのは「この提示・この価格・この経路での conversion の上限」であって、「この価値提案の conversion の上限」ではありません。** 手順書 §3 段階5 の「30名接触で1件も出ない事業は、副業の時間では立ち上がらない」は、**「この提示では立ち上がらない」**までしか言えません。

### 3.6 同じ問題は 段階3 の 7/12 にもあります

聞き取り12件も同一経路（§3.2 の名簿）から集まります。cluster 相関を入れると 7-of-12 gate の性能が変わります。

| 真の集中度 | ICC=0 | ICC=0.1 | ICC=0.2 | ICC=0.3 |
|---|---|---|---|---|
| 0.4（落としたい） | 0.158 | 0.251 | 0.298 | **0.327** |
| 0.6（通したい） | 0.664 | 0.620 | 0.603 | 0.594 |

**偽陽性が 15.8% → 32.7% に倍増し、検出力はほぼ変わりません。** 同じ経路から12名を集めると、「同じ きっかけ」は経路の共通性から生じます。**手順書は「同一 きっかけ」を需要の signal として読みますが、cluster 標本ではそれは経路の signal です。**

### 3.7 判定

**rule of three の数式は正しく、適用の前提が成立していません。** 上限 9.5% は最良の場合の値で、現実的な cluster 構造では **10.5%〜30.7%** に緩みます。「conversion は10%未満」という結論は、**接触経路が3つ以上に分かれている場合にのみ**成立します。

**それでも否定側の推論が肯定側より強いという §1 第4条の非対称性は維持されます。** 30名0件は「上限30%」であっても、目標が「20人接触で4.8契約（成約率24%）」（§6.5.1.1 の中央値行）なら反証として十分機能します。**壊れているのは結論の向きではなく、数字の精度です。**

## 4. 勝者の呪い（winner's curse）

### 4.1 手順書の現状

§3 段階2 の末尾に一行あります。

> 実務上の意味は「funnel を通った候補の見込みは、通過時点の推定より必ず低い」ということです。

**言及はあります。補正はありません。** 何%低いのか、通過後にどの数字をどれだけ割り引くのか、という手続きが無く、§4 の判定基準表にも該当行がありません。G_thresholds.md §5 も「通過時点の見込みは推定より必ず低い」と書くだけです。

### 4.2 計算: gate 通過後の期待値

1因子 model で、通過した候補の真の潜在量 Z の条件付き期待値を計算しました（q は 2-of-4 の通過率）。

| ρ | P(通過) | E[Z\|通過] | E[Z\|不通過] | 分離幅（sd） |
|---|---|---|---|---|
| 0.0 | 0.399 | **−0.001** | +0.001 | **0.00** |
| 0.1 | 0.399 | +0.159 | −0.104 | 0.26 |
| 0.2 | 0.399 | +0.308 | −0.203 | 0.51 |
| 0.3 | 0.399 | +0.441 | −0.293 | 0.73 |
| 0.5 | 0.396 | +0.667 | −0.439 | 1.11 |

**ここに本検証で最も皮肉な結論があります。** 勝者の呪いは「選抜が強いほど楽観に偏る」現象です。#2 で示したとおり本 gate の ρ は 0 に近いので、**楽観への偏りも 0 です。通過しても期待値が上がらないので、上振れを選ぶこともできません。**

**つまり手順書が持っていない補正は、この gate に関しては必要ありません。必要なのは「通過しても何も分かっていない」という記述です。**

### 4.3 補正が本当に要る場所

勝者の呪いが実際に効くのは、**選抜後に観測値を事業計画の前提に使う**場所です。V5 §4.2 は 8/12 gate で計算していますが、手順書は 7/12 に緩めたので**現行の閾値で計算し直しました**。

| 真の集中度 p | P(通過) | E[X/12 \| 通過] | 上方 bias |
|---|---|---|---|
| 0.4 | 0.158 | **0.623** | +0.223 |
| 0.5 | 0.387 | **0.646** | +0.146 |
| 0.6 | 0.665 | 0.680 | +0.080 |
| 0.7 | 0.882 | 0.731 | +0.031 |

**真の集中度が 40% の候補でも、7/12 gate を通れば「62%」と観測されます。** 閾値を 8/12 から 7/12 に緩めたことで bias 自体は小さくなりましたが（p=0.5 で +0.208 → +0.146）、消えてはいません。

**手順書はこの補正を持っていません。** §3 段階3 は「7件以上が同一 きっかけ なら 段階4 へ」とだけ書き、通過後にその件数比を「顧客の6割はこの きっかけ を持つ」と読んではいけない、という注記がありません（V5 §4.7 の修正案5が未反映）。§6.5.1 の必要到達人数はこの種の率を入力に取るので、上振れした率をそのまま入れると必要人数が過小になります。**成約率の弾力性は 1.000（§6.5.1）——率が上振れした分だけ、必要人数が同じ倍率で過小に出ます。**

### 4.4 判定

**深刻度は中。** gate に選択力が無いため段階2 由来の楽観偏りは生じませんが、**段階3 の 7/12 通過後に観測された集中度を段階4/5 の前提に持ち込む経路が塞がれていません。** V5 の指摘（修正案5）が手順書に反映されていないことを確認しました。

## 5. 「段階0 で全部埋めて以後変更禁止」は正しいか

### 5.1 まず事実確認 — 手順書は自分でこの規律を破っています

§4 の見出しは「**判定基準（段階0 で全部埋める・以後変更禁止）**」です。しかし同じ手順書が3か所で更新を指示しています。

| 箇所 | 記述 |
|---|---|
| §3 段階1 の関門 | 「**実測値が 段階0 の想定を大きく下回る場合、必要到達人数を計算し直す**」 |
| §6.5.1 | 「（成約率2%は）仮置き。**段階1 と 段階5 の実測で置き換える対象です**」 |
| §6.5.2 | 段階0/1/5 の各段で獲得能力を測り直す表 |

**「以後変更禁止」と「実測で置き換える」が同一文書内で両立していません。** これは規律の問題以前に、読者がどちらに従えばよいか判断できない矛盾です（深刻度: 高）。

### 5.2 仮説検定の作法を、検定でないものに持ち込むのは誤りか

**部分的に誤りです。** 分けて評価します。

**誤っている部分——事前登録の統計的な根拠は、ここには存在しません。**
事前登録が守るのは type I error rate です。それは「同じ手続きを反復したとき偽陽性が α を超えない」という**反復可能性に基づく保証**で、n=1 の個人事業には反復がありません。あなたは分布の中の1点ではなく、その1点そのものです。**「p-hacking を防ぐ」という言い方で §4 を正当化するなら、それは誤りです。**

**正しい部分——手順書は統計的な根拠で正当化していません。**
§4 の理由書きはこうです。

> 特に 段階4・5 の金額は、第8週の sunk cost を負った状態で宣言すると必ず甘くなります。

**これは統計の話ではなく、時間非整合な選好に対する commitment device の話です。** 将来の自分（sunk cost を負い、8週間を無駄にしたくない自分）が、現在の自分と違う基準を使うことを見越して、現在の自分が選択肢を縛る。Ulysses 契約です。**この論拠は n=1 でも有効で、統計的検定である必要がありません。** 手順書の理由付けは正しく、**誤解の余地があるのは「変更禁止」という表現の広さだけです。**

### 5.3 情報を捨てているか — 捨てている量を分けて評価する

Bayes 的に見れば「事前に決めた基準を動かさない」は、途中で得た情報を判断に反映しないことです。ただし**何を凍結するかで、捨てる情報の量が全く違います。**

| 凍結の対象 | 途中の情報で更新すべきか | 理由 |
|---|---|---|
| **目標**（目標粗利/月、可処分時間） | **凍結すべき** | 外部 data で更新される量ではありません。動くなら sunk cost が動かしています |
| **判定 rule の形**（何を見て何を決めるか、閾値の水準） | **凍結すべき** | ここが緩むと関門が消えます。手順書の懸念そのもの |
| **分類体系**（きっかけ の label） | **凍結すべき** | V5 §4.4 のとおり、label 粒度で判定が400倍動きます |
| **入力の推定値**（成約率、解約率、反応率） | **更新すべき** | 段階0 時点は仮置き。実測が入るのに使わないのは情報の破棄 |
| **入力から結論への計算**（必要到達人数、必要時間） | **再計算すべき** | 入力が変われば従属的に動く量。凍結すると内部矛盾を起こします |

**手順書が実際に運用しているのは既にこの区別です**（§3 段階1 で必要到達人数を再計算させ、§6.5.1 で成約率を実測に置き換えさせる）。**足りないのは、区別を明文化していないことだけです。**

### 5.4 それでも残る本質的な問題 — 最も無知な時点で閾値を決めている

§4 は段階0（週0・4.8時間）で全部を埋めさせます。**この時点で最も不確かな量は成約率で、§6.5.1 の弾力性表によれば必要人数への弾力性は 1.000——最大です。** 最も効く変数が最も分からない時点で、それに依存する閾値を確定させています。

段階1 で経路別の反応率を実測する設計になっているので、**成約率に依存する数値（必要到達人数、必要時間/月、必要月次純増契約数）は段階1 終了時に確定させるほうが、情報の使い方として正しい**です。段階0 で凍結すべきは目標と判定 rule の形であって、その2つは段階1 の実測では動きません。

### 5.5 判定

**「commitment device としては正しい。統計的な事前登録の作法として説明するなら誤り。そして凍結対象の区別が明文化されていないため、手順書は自分の規則を破っている。」**

規律そのものは維持すべきです。**危険なのは「変更禁止」が広すぎて、(a) 実測が入っても更新されない量を生むか、(b) 逆に「どうせ守れない規則だ」として全体が緩むかの、どちらかに倒れることです。**
