# 自動化の設計

作成 2026-08-11 / 対応: `doc/MARKET_RESEARCH.md`（方針）、`doc/WORKFLOW.md`（工程）

---

## 0. 方針と方法の切り分け

| 区分 | 内容 | 自動化 |
|---|---|---|
| **方針** | 何を測るか（既に金か時間を払っているか）／目的は棄却／判定点は2か月目の継続決済 | **対象外。** 人が決め、変えない |
| **方法** | 6段階の工程と、各段階の合格条件 | **原理的には段階0〜2と観測系が自動化できる。ただし1周目は手作業（§1の末尾）。段階3〜5は自動化できない** |
| **規律** | 出典・取得日・分母・閾値の事前確定 | **機械に守らせる**（人間が最も破りやすい部分） |

## 1. 自動化の可否マップ

工程を「機械がやる／人がやる」に分解します。**混在する工程は、境界を明示します。**

| 工程 | 機械 | 人 | 削減効果 |
|---|---|---|---|
| **0. 棚卸し・逆算・販路** | 自作道具の候補の列挙／逆算と維持上限・必要導入数の計算 | **その作業を知っていることの言語化、当事者への確認、領域と目標の決定** | 6.0h → 4.5h |
| **1a. 観察（収集）** | `MARKET_RESEARCH.md` §3.1 の検索先と 検索語（**英語圏4種＋日本語圏4種: Reddit / Hacker News / Stack Overflow / GitHub、Qiita / Zenn / note / X**）を掃引して重複排除、発言を出所URL・投稿日つきで一覧化 | — | 2h/週 → 20分/週 |
| **1b. 観察（読解）** | — | **語彙の採取、困りごとの同定、検索語の書き換え** | 削減しない |
| **1c. 候補者 一覧化・接触** | 接触状態の管理と催促日の算出 | **誰に、どう繋がるかの判断と、文面** | わずか |
| **2. 混み具合調べ** | **全部**（API 取得・判定式の適用・採点表の出力） | 閾値の決定（段階0 で1回）と、結果の解釈 | 3h → 5分 |
| **3. 聞き取り** | 記録 雛形 の生成、きっかけ 名前 の集計 | **実施そのもの** | 削減しない |
| **4. 有償提供** | 作業 記録の集計、自動化候補の抽出 | **提供そのもの、請求、継続確認** | 削減しない |
| **5. 先行販売** | GSC / 決済の日次取得と分母の追跡 | 提示、価格の決定 | わずか |
| **競合の外形測定** | 価格の時系列、公開の間隔、review 増加、求人、撤退検出 | 撤退理由の読解、低評価の分類 | 4.5h → 1.5h |
| **週次の記録・整理・判断** | 実績値の集計、判定基準表への転記、関門到達の警告 | **判断そのもの（週1時間。削らない）** | 27.0h → 19.8h（1.5h/週 → 1.1h/週） |

**削減効果は上表を積み上げて17.35時間です。** 残りは人でしか進みません。これは設計の失敗ではなく、**証拠の強さが人の接触に偏っているという結論の裏返し**です。機械が出せるのは階層の2段目（配布元の実測値）までで、1段目（自分が受け取った金）は自動化できません。

> **重要: 1周目では自動化しないでください。正味で赤字です。**
>
> | | 時間 |
> |---|---|
> | 削減効果（上表の積み上げ） | **17.35時間** |
> | §3 の 道具6本の実装（見積もり） | **33〜88時間** |
> | 回収に必要な周回数 | **2.1〜5.6周** |
>
> **本手順書は1周の設計です。** したがって1周目に 道具を書くと、総工数は 112時間から 145〜200時間（21〜29週）へ増えます。
>
> **第2版はこの実装工数をどの総計にも計上せず、「16週は自動化を前提にして初めて成立する」と書いていました。逆でした。** 検証記録は `doc/verify/X4_cost.md` §5。
>
> **なお実装工数の 33〜88時間は見積もりであり、実測ではありません（未確認）。** §3 の仕様からの積み上げです。ただし第2版は工数を「小／中」という記号でしか持っておらず、**数字での反証ができない状態**でした。反証可能にするために数字を置いています。
>
> **例外として、1本だけ作る価値があるものがあります。** §3.2 の `scan_questions.py` 相当（混み具合調べの API 取得）は、削減が3時間→5分と最も大きく、実装も最小です。**それでも「作らずに手で3時間かける」ほうが1周目は安い**ことは変わりません。
>
> **2周目以降は逆転します。** 領域を変えて再度回すなら、混み具合調べと競合の外形測定は再利用が効きます。**その時点で書いてください。**
>
> **そして §2 が警告している失敗の型が、まさにこれです。** 「人に聞く代わりに 道具を作る」。1周目に 道具を書くことは、その再演の最も自然な入口です。

## 2. 自動化してよい境界（最重要）

**この節が本書で一番大事です。** 先行して同型の 道具を作って失敗しているため、同じ設計に戻らないための制約を先に置きます。

### 守る規律

| # | 制約 | 理由 |
|---|---|---|
| 1 | **道具は候補を生成しない。** 入力は必ず「人が 段階0〜1 で出した入口の一覧」 | 候補生成に使った瞬間、棄却の道具が発見の道具に化ける（目的反転）。前回の失敗はここ |
| 2 | **全走査を禁止する。** 1回の実行で扱う入口は上限20件、`--limit` を必須引数にする | 35,995件の全走査は「ジャンルの平均」を測る行為に戻る。測りたいのは入口1件ごとの値 |
| 3 | **閾値を 道具の中に埋めない。** `log/hypothesis.md` または `config/thresholds.yaml` から読む | 走りながら閾値を触れる状態にすると 関門 が緩む。設定 file を git 管理し、変更を履歴に残す |
| 4 | **取得日を必ず出力に刻む。** file 名にも本文にも | `info.results` は日々変動する（実測: `booking calendar` 719→720）。日付の無い scan 結果は判定に使えない |
| 5 | **生 応答 を保存する。** `log/raw/<情報源>/<date>/` に JSON のまま | 再解析を可能にするため。指標を変えて測り直す必要が出た時、取り直しは効かない |
| 6 | **API 失敗時は fallback せず、失敗として落とす。** 欠損は欠損のまま出力に残す | 代替値で埋めると「取れなかった」と「値が小さい」が区別できなくなる。判定を誤る |
| 7 | **平均を出力しない。** 集約が要る場合は分布（中央値・上位k件・到達率）を出す | 平均は分布差に鈍い。前回の失敗の直接原因 |
| 8 | **判定は出すが、決定はしない。** 出力は「4条件中N件該当」までで、採否は人が書く | 機械が採否まで出すと、判定基準表が形骸化する |

### 保存形式

**DB を作らないでください。** 出力は日付つきの markdown と JSON のみ。前回 `数値/demand.sqlite3` を作った結果、「貯めた 数値 を活かす」動機が judgment を歪めました。**捨てられる形で持つのが正しい設計です。**

## 3. 道具一式の仕様

`Fukugyou/tools/` に配置。**venv 前提、Windows / Linux 両対応**。各 道具は単独で動き、相互に依存しません。

### 3.1 `scan_marketplace.py` — 段階2の中核

| | |
|---|---|
| **入力** | `--entries entries.txt`（人が書いた入口の一覧）／`--ecosystem wordpress\|atlassian\|vsコード`／`--limit 20` |
| **API** | WordPress `api.wordpress.org/plugins/info/1.2/`（認証不要・`-g` 相当の URL encode 必須）／Atlassian `marketplace.atlassian.com/rest/2/addons/{key}/distribution`（認証不要）／VS Code `_apis/public/gallery/extensionquery`（POST・`Accept: application/json;api-version=7.2-preview.1`） |
| **出力** | `log/scan-YYYYMMDD.md`（判定表）＋ `log/raw/…`（生 JSON） |
| **判定** | `config/thresholds.yaml` の4条件を適用し、**該当数を出すだけ**。合否は書かない |
| **実装上の注意** | `active_installs` は有効数字1桁に丸められる（`downloaded` は厳密）／VS Code の `install` と `downloadCount` は70倍違う別物で、**使うのは `install`**／Atlassian の `totalUsers: -1` は 特殊値 なので合計に混ぜない、`bundled: true` は自発的導入ではないので除外 |

### 3.2 `scan_questions.py` — 未解決問題の量

| | |
|---|---|
| **入力** | tag の一覧、`--limit` |
| **API** | Stack Exchange 2.3 `?filter=total`（1回の呼び出しで件数のみ） |
| **出力** | tag 別の「質問総数 / 未回答数 / 差」 |
| **注意** | 利用上限 は3状態（key/token 無し **300/日**・key あり 10,000/日・token あり user·追加機能 ごと 10,000/日）。**`backoff` field の遵守が必須**、同一 IP 30 req/秒 超で drop、同一の呼び出しは1分に1回。**2023年以降 LLM で投稿が減少しているため、時系列比較を禁止し同時点の tag 間比較のみ出力する** |

### 3.3 `track_competitors.py` — 競合の外形測定（削減効果が最大）

| | |
|---|---|
| **入力** | 競合の 競合の URL・repository・配布元での識別子の一覧 |
| **取得** | Wayback CDX API で pricing ページの snapshot 一覧 → **変化した日付だけ**抽出／GitHub releases の間隔／review 件数の推移／求人掲載 |
| **出力** | `log/competitors.md`（**日付の時系列表**。金額の推定はしない） |
| **撤退検出** | 直近12か月 snapshot が消えた・404 化・GitHub archive・pricing ページが消滅 → **「撤退候補」として別掲**。生存者だけ測るのを防ぐ |
| **注意** | 訪問者数 は推定しない（個人規模では相関0.50〜0.79で使えない）。**取るのは離散 event の日付だけ** |

### 3.4 `sweep_community.py` — 段階1a の収集

| | |
|---|---|
| **入力** | 検索語 一覧（人が書く。例: `"is there a 道具 that"` `"how do I automate"` `"spreadsheet nightmare"` + 領域語） |
| **対象** | 英語圏: Hacker News（Algolia。Firebase 版は公式に rate limit 無しと明記）／Stack Exchange／GitHub issues。**日本語圏: Qiita / Zenn / note / X**（`MARKET_RESEARCH.md` §3.1。日本語圏では困りごとが「作ってみた」記事の形で現れるため必須）。**Reddit は API 条件が2023年に変わっているため、規約を確認してから追加** |
| **出力** | 発言の抜粋＋**出所 URL＋投稿日**の一覧（重複排除のみ。要約も分類もしない） |
| **境界** | **読解は人がやる。** 道具は集めて並べるところで止める |

### 3.5 `weekly_digest.py` — 規律の強制

| | |
|---|---|
| **動作** | `log/` を走査し、今週の実績値を判定基準表の形に集計 |
| **警告** | ①`log/counter.md`（反証記録）に今週の追記が無い → **警告** ②Track B の作業しか記録が無い週が2週続いた → **警告** ③関門 の判定日を過ぎているのに判定の記録が無い → **警告** ④**顧客と話した時間より コードを触った時間が長い週が2週続いた → 警告**（段階4 で最小実装を認めたことへの歯止め。手で数えてもよい） |
| **理由** | 反証を書く・顧客接点を止めない・関門 を先送りしない、の3つは人間が最も破りやすく、機械が最も検出しやすい |

### 3.6 `economics.py` — 逆算 **（実装済み）**

| | |
|---|---|
| **入力** | 目標月次利益、想定単価、利益率、月次 解約率、**目標までの月数 T**、**経路別の母数・成約率・1人あたりの時間時間** |
| **出力** | 必要 年間の継続収入 / 必要契約数 / 維持に必要な月次獲得 / **目標到達に必要な月次獲得 `M = c·B ÷ (1 − e^(−c·T))`** / **必要な集客数（経路別）** / **必要時間/月** |
| **注意** | 為替と 利益倍率（Acquire.com 中央値 3.9x、**標本件数は原典に記載なし**）は `config` に置き、hard-コード しない。**集客の手段を引数で受け取り、個別の声かけなら維持上限（可処分時間÷1人あたりの時間×成約率÷解約率）、掲載・記事なら必要導入数を出す**（`MARKET_RESEARCH.md` §6.5.1）。**「必要時間 = 必要到達 × 1人あたりの時間」という単一の式は実装しないこと。** 掲載・記事を表現できず、企画を誤って殺します |

### 3.7 `scan_stock_params.py` — 掲載・記事の到達量 **（実装済み）**

| | |
|---|---|
| **入力** | `--keywords config/keywords_business.txt`（人が書いた語）／`--top 8`／`--limit`（既定30） |
| **API** | WordPress `api.wordpress.org/plugins/info/1.2/`。`added`（登録日）と `active_installs` を取る |
| **出力** | `log/stock-params-YYYYMMDD.json`（分布と関門の条件A）＋ `log/raw/wordpress/YYYYMMDD/`（生 JSON） |
| **測る量** | `active_installs ÷ 登録からの経過月数` の分布（p25 / 中央値 / p75）を参入時期の 参入年次 別に |
| **注意** | **`downloaded` は使わないこと。** 自動更新の配信を含むため到達量になりません（導入30万件の 追加機能 は月15.6万DL）。`active_installs` は有効数字1桁に丸められるので、小さい値ほど相対誤差が大きい |
| **限界** | 上位N件しか取れないため、**参入したが上位に入れなかった掲載を分母に含みません**（強い生き残りだけを見る偏り） |

## 4. 実装の順序

効果 ÷ 実装 費用 の順です。**上位4つで削減の63%が取れます。**

| 順 | 道具 | 削減 | 実装 |
|---|---|---|---|
| — | **`economics.py`** | 逆算そのもの | **実装済み**（2026-08-12）。段階0 の前に要る唯一の道具。表計算でも足りますが、**手書きの表を2回間違えた**ので コード にしました |
| — | **`scan_stock_params.py`** | 掲載・記事の到達量の実測 | **実装済み**（2026-08-12）。`doc/research/H_stock_params.md` の再現用。**削減ではなく、無かった測定を足すもの**です |
| 1 | `weekly_digest.py` | 6.4h（最大） | 小 |
| 2 | `scan_marketplace.py` | 3h → 5分 | 中（生態系ごとに分岐） |
| 3 | `track_competitors.py` | 2.5h | 中（Wayback CDX の扱いが要点） |
| 4 | `scan_questions.py` | 1h → 2分 | 小 |
| 5 | `economics.py` | 30分 → 即時 | 小 |
| 6 | `sweep_community.py` | 2h/週 → 20分/週 | 中（情報源 ごとの API 差） |

削減の内訳は 週次集計7.2h / 観察の収集2.5h / 混み具合調べ2.9h / 競合の外形測定3.0h の4項目で、**合計15.6時間＝削減17.35時間の90%**です。

> **ただし §1 の末尾のとおり、1周目はどれも作りません。** この順序は2周目以降のためのものです。
>
> **1周目に唯一やる価値があるのは `economics.py` の計算そのもの**ですが、これは 道具 でなく**表計算1枚**で足ります（入力6つ、出力4つ）。**逆算に30分かける価値はあり、逆算のための 道具 に3時間かける価値はありません。**

## 5. 自動化しないと決めたもの

| 対象 | 理由 |
|---|---|
| **聞き取り の実施と要約** | 発言の要約を機械にさせると、きっかけ の 名前 が事後に動く。名前 は 段階3 開始前に人が確定させ、以後追加しない規律と衝突する |
| **困りごとの分類・scoring** | 「不満の強さ」を機械が採点すると、★の低さを不満の proxy にするのと同じ誤りに戻る（評価の甘さ により、非公開で「二度と雇わない」と答えた発注者の28.4%が公開では4★以上） |
| **候補 狭い領域 の生成・ranking** | §2 の制約1・2。前回の失敗の再演になる |
| **価格の決定** | 意向と行動は乖離する。決定は 有償提供 の実請求と 先行販売 の実価格でのみ行う |
| **採否の判定** | 機械が合否を出すと判定基準表が形骸化する。出すのは「4条件中N件該当」まで |
| **LLM による記事要約を証拠にすること** | 証拠階層の最下段（出典なき記事）に落ちる。一次情報 の URL と取得日が残らない要約は使わない |
