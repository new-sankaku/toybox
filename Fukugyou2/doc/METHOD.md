# 題材の決め方

作成 2026-08-24 / 対応: `doc/PIPELINE.md`（工程）、`doc/SOURCES.md`（情報源）

---

## 0. 何を決めるのか

**1人で運用でき、継続課金で積み上がり、提供の中核を機械が回せる事業の題材を1つ選ぶ。** これだけです。

ここで決めないもの: 作る機能の詳細、価格、名前、技術の選定。**題材が決まる前にこれらを考えると、決めた気分になって題材の検証が止まります。**

進め方は「発明」ではなく「移植」です。**既に金が払われている型を見つけ、日本市場と別業界に移せるかを調べます。**

---

## 1. 選ぶ型の定義

| | 入れる型 | 外す型 |
|---|---|---|
| **収益** | 同じ相手から翌月も自動で入金される（継続課金） | 買い切り、受託、広告、時間売り |
| **提供** | 毎回発生する作業を機械が回す | 毎回 人が読む・打つ・電話する |
| **運用** | 1人で回る | 24時間の有人対応、現物在庫、有資格者の常駐 |
| **客** | 法人（業務の費用として払う） | 個人の趣味支出 |

**「AIで自動化できる」の定義を狭く取ります。** 提供の中核（客が金を払っている作業そのもの）が機械で回ることを指します。**開発を AI で速くすることは、ここでは自動化に数えません。** それは誰でも同じだけ速くなるので、差になりません。

**法人を選ぶ理由は、解約率です。** 個人向けは月額が低く解約が速いため、1人の運用では積み上がりません。業務に埋め込まれた法人向けは、金額が上がり解約が遅くなります。

---

## 2. なぜ「既に製品化されたもの」から始めるのか

新規の発明は、**需要があるか**と**作れるか**の2つに同時に賭けます。既存製品を出発点にすると、賭けは1つに減ります。**「日本で、あるいは別の業界で、同じ型が成り立つか」だけ**です。

ただし、そのまま真似ると価格と販路で先行者に負けます。**だから §3 の失敗事例と §4 の転用を必ず通します。** 一覧を作って終わりにしないでください。

---

## 3. なぜ失敗事例も集めるのか（撤退理由の型）

成功例だけを見ると「やれば当たる」に見えます。これは生存者だけを数えた結果であり、実態ではありません。**撤退の理由は、参入してはいけない領域の地図になります。**

読んだ失敗事例は、次の型のどれかに分類してください。**型は事後に増やしません。** どうしても足りない場合は、日付を書いて追記します。

| # | 型 | 現れ方 |
|---|---|---|
| 1 | 客がいなかった | 使われず、問い合わせも来ない |
| 2 | 客はいたが金を払わなかった | 無料や既存の代用品で足りていた |
| 3 | 単価が低すぎた | 客はいるが、維持費を割った |
| 4 | 解約が速かった | 使う理由が1回で終わる（引っ越し・移行・年1回の作業） |
| 5 | 販路がなかった | 作れたが、届ける経路が無い |
| 6 | 大手が標準機能にした | 同じ機能が本体に載って消えた |
| 7 | 規制・審査で詰まった | 決済審査、業法、個人情報の扱い |
| 8 | 作る側が尽きた | 時間・関心が続かなかった |

**型4と型6は、個人の副業にとって最も致命的です。** 題材を選ぶ段階で、この2つに当たらないかを先に確かめてください。

## 4. 判定の4軸と、証拠の強さ

`config/screen.yaml` の4軸です。**記号は一覧表で使います。**

| 記号 | 軸 | 何を見るか |
|---|---|---|
| **S** | Stock性 | 継続課金の表示が実在するか（宣伝文ではなく価格表） |
| **A** | AI自動化性 | 中核の作業が、機械で回る動詞で書かれているか |
| **P** | 証拠性 | 金額・規模の数字が、出所つきで存在するか |
| **B** | 法人が払うか | 業務の対象（請求・契約・勤怠・監査など）を名指ししているか |

### 証拠の強さ

| 段 | 証拠 | 取り方 |
|---|---|---|
| **1（最強）** | 自分が受け取った金 | 人が売るまで出ません。**機械では絶対に出ません** |
| 2 | 公開された価格表 | `tools/fetch_pricing.py` が取れる上限 |
| 3 | 出所つきの実数（利用者数・収益） | 本文中の数字。誇張が混じります |
| 4 | 本人の主張（宣伝文） | 反証に使えません |
| **5（最弱）** | 出典の無い記事・要約 | **使いません** |

**機械が取れるのは2段目までです。** 一覧の上位に来た事例は「2段目の証拠がある候補」であって、当たりではありません。

## 5. 規律

この8項目は program 側で強制しています。**緩める場合は、緩めた日と理由を書いてください。**

| # | 規律 | 理由 |
|---|---|---|
| 1 | **program は検索語を生成してよい。ただし採用は実測の歩留まりで決める。** 人が書くのは「何を positive と呼ぶか」の定義（`screen.yaml` の条件、`discovery.yaml` の失敗事例の定義）であって、検索語ではありません | 語を人が書くと、探索の幅がその人の語彙で止まります。かといって生成した語をそのまま使えば創作です。**生成は自由、採用は実測**で分けます（§5A） |
| 2 | **全走査を禁止する。** `--limit` を超える入力は落とす | 全部を数えると「業界の平均」を見ることになります。見たいのは事例1件ごとの値です |
| 3 | **失敗を代替値で埋めない。** 欠損は欠損のまま出力に残す | 「取れなかった」と「値が小さい」を混ぜると、判定を誤ります |
| 4 | **取得日を record と file 名の両方に刻む** | 件数は日々動きます。日付の無い数字は比較に使えません |
| 5 | **生 response を保存する** | 指標を変えて測り直すとき、取り直しは効きません |
| 6 | **閾値と条件を code に埋めない。** `config/*.yaml` に置き、git で履歴を残す | 走りながら閾値を触れる状態にすると、条件が後から緩みます |
| 7 | **平均を出力しない。** 分布（p25 / 中央値 / p75）で出す | 平均は分布差に鈍く、少数の外れ値で動きます |
| 8 | **判定は出すが、決定はしない。** 出力は「4軸中N軸該当」まで | 機械が採否を出すと、判定表が形骸化します |

## 5A. 検索語の発見 algorithm

**人は検索語を書きません。** `tools/discover_queries.py` が data から作り、実測で選びます。

| 段 | やること | 選定の理由 |
|---|---|---|
| 1 | **母集団の取得**。query 無しで引ける構造 tag（Hacker News の `show_hn`）と、比較用の一般 story を、期間で層化 sampling します | query を使わずに母集団が取れるため、**開始時点で人の語が1つも要りません**。期間で層化するのは、直近の話題（現在なら AI 開発道具）に偏らせないためです |
| 2 | **標識づけ**。製品化事例は `screen.yaml` の軸、失敗事例は `discovery.yaml` の定義で positive / negative に分けます | 定義と検索語を分離します。人が触るのは定義だけです |
| 3 | **keyness**。positive と negative を分ける語を Dunning の対数尤度比 G² で選びます | corpus 比較の標準的な指標です。**低頻度語に強い**点で、頻度差や TF-IDF より適します（TF-IDF は文書内の重要度であって、集団間の差ではありません） |
| 4 | **掛け合わせ**。効いた語 × 新しい語 の AND query も候補にします | 1語の query は該当が広すぎて適合率が落ちます。擬似適合性 feedback（pseudo-relevance feedback）と同じ要領で絞ります |
| 5 | **歩留まりの実測**。候補で実際に検索し、該当件数・適合率・新規獲得数を測ります | **生成した語をそのまま使いません。** 実測が閾値を満たした語だけを採用します |
| 6 | **飽和まで反復**。採用語の結果を positive に足して 3 に戻ります | 新規 positive が増えない round が続いたら止めます。件数の目標ではなく、**増えなくなったこと**を終了条件にします |

### 採否に使う指標を、標識の作り方で変える

| 種別 | 標識 | 採否の指標 | 理由 |
|---|---|---|---|
| **製品化事例** | `screen.yaml` の条件（語と独立した4軸） | **適合率**（取得のうち positive の割合） | 標識が query の語と独立しているため、適合率が意味を持ちます |
| **失敗事例** | 「畳んだ」と書いてあるかどうか（語そのもの） | **新規獲得数**（新しく取れた positive の件数） | 標識が語なので、その語を含む query の適合率は必ず高く出ます。**適合率で測ると自分で自分を証明します**。測るべきは網羅です |

### 循環を切る仕掛け

**標識づけに使った語は、候補から除外します**（`exclude_condition_terms`）。除外しないと「条件に書いた語が、条件に合う事例を連れてくる」だけになり、発見が起きません。除外した結果、discovery が出すのは**条件に書いていない語**になります。

### 新規率を採否に使わない理由

新規率（既知でない事例の割合）は記録しますが、**採否には使いません**。同じ語でも、手元に何件持っているかで値が変わるためです。**それは検索語の性質ではなく、実行した時点の性質です。** 飽和の判定と並び替えにだけ使います。

## 6. この方法で言えないこと（限界）

**先に書いておきます。後から言い訳にしないためです。**

- **言及の件数は需要ではありません。** 代理指標です。困っている人の数とも、金を払う人の数とも違います。
- **Qiita / Zenn は技術者に偏ります。** 建設・介護・運送といった非 IT 業界の困りごとは、そもそもこの2つに書かれません。**日本側の数字が小さいことは、需要が無いことの証明にはなりません。**
- **Hacker News の点数は人気であり、金ではありません。** 点数の高い事例が儲かっている事例ではありません。
- **価格表の一致は「継続課金の表示がある」ことだけを意味します。** 客が実在するか、黒字かは分かりません。
- **上位N件しか見ていません。** 参入したが上位に入れなかった事例を数えていないため、生き残りだけを見る偏りが残ります。
- **画面を JavaScript で描く site の価格は取れません。** 取れなかったものは「未取得」として残します。「証拠なし」とは別物です。
- **母集団は Hacker News に偏ります。** 英語圏の技術者が投稿した事例だけです。日本の非 IT 業界で売れている製品は、ここに1件も現れません。
- **発見した語は、母集団の語彙より外へは出ません。** `show_hn` に「介護記録」の話が無ければ、その語は永遠に出てきません。**情報源を足すことでしか広がりません。**
- **日本語の語の発見は Qiita の tag に依存します。** tag は技術名に偏るため、業務の語（例: 実地指導、B/L、施工体制台帳）はほとんど出ません。**日本語側は現時点で最も弱い部分です。**

**この6つの限界は、最後は人が会って聞くことでしか埋まりません。** 機械は候補を絞るところまでです。

## 7. 人がやること（自動化しないもの）

| 対象 | 理由 |
|---|---|
| positive の定義を決める（`screen.yaml` の条件、失敗事例の定義） | 何を探しているかの定義です。ここだけは人が決めます。検索語はここから機械が導きます |
| 失敗事例の本文を読み、§3 の型に分類する | 撤退理由は行間にあります。要約させると理由が変わります |
| 転用 worksheet を埋める | 業界の商習慣は、書かれていない部分が本体です |
| 採否の決定 | §5 規律8 |
| 価格の決定 | 意向と行動は乖離します。実際に請求するまで分かりません |
| 客に会って聞く | 証拠の1段目は、これでしか手に入りません |
