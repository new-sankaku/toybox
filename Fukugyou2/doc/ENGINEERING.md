# 道具としての現在地

作成 2026-08-24 / 「これは実務で使える道具か」への自己評価です。**都合の良い評価を書きません。**

---

## 0. 結論

**「調査を再現できる道具」としては実用段階です。「製品」としては未達です。**

決定的に足りないのは2つ、**情報源が1本しかないこと**と、**取り逃しの量を測っていないこと**です。
この2つが埋まるまで、出てくる一覧は「Hacker News に投稿された範囲での話」に留まります。

---

## 1. 備わっているもの

| 項目 | 実装 |
|---|---|
| **設定と code の分離** | 閾値・条件・分類・業界・LLM の provider/model は `config/*.yaml`。code に定数がありません |
| **検索語の自動生成** | `discover_queries.py`。人が書くのは positive の定義だけです（`doc/METHOD.md` §5A） |
| **生成した語の検証** | 実測（該当件数・適合率・新規獲得数）を満たした語だけ採用。理由が `log/discovery-*.json` に残ります |
| **代替値で埋めない** | 取得失敗は欠損のまま出力に残り、件数が報告されます |
| **再現性の記録** | 実行ごとに `log/runs/*.json`（git commit・引数・件数・失敗・host 別 request 数） |
| **一時失敗の再送** | 429 / 5xx / 通信断のみ指数 backoff、`Retry-After` 尊重。恒久的な失敗は即座に落とします |
| **request の上限** | host ごとに `config/discovery.yaml` の `budget` で頭打ち。超えたら止まります |
| **robots.txt の尊重** | RFC 9309 の status 解釈（401/403 は全面禁止、その他 4xx は許可、取得不能は不明として取りに行かない） |
| **自動 test** | 28件。純関数・設定の整合・robots の解釈・条件照合・発見の候補生成 |
| **可搬性** | Windows / Linux、標準 library ＋ PyYAML のみ |

### test の走らせ方

```bash
python -m venv .venv
.venv/bin/pip install -r requirements-dev.txt   # Windows: .venv\Scripts\pip
.venv/bin/python -m pytest tests -q
```

## 2. 足りないもの

| # | 項目 | 現状 | 影響 | 優先 |
|---|---|---|---|---|
| 1 | **情報源が1本** | Hacker News だけ | 母集団の偏りが全工程に乗ります。日本の非 IT 業界の製品は1件も出ません | **高** |
| 2 | **取り逃しの量が不明** | 網羅率を測っていません | 「これで全部か」に答えられません | **高** |
| 3 | **日本語側が弱い** | Qiita の tag 依存 | 業務の語（実地指導・施工体制台帳など）が出ません | **高** |
| 4 | 日をまたぐ蓄積がない | 事例 file が日単位 | 昨日集めた事例と今日の重複が残ります | 中 |
| 5 | record の schema 版がない | 列を足すと過去 file と混在 | 古い出力の再解析で崩れます | 中 |
| 6 | JavaScript 描画の価格が取れない | HTML 取得のみ | Stock性の証拠が取れる site が限られます | 中 |
| 7 | CI がない | 手元で test を回すだけ | 壊れたまま commit できます | 中 |
| 8 | 撤退理由の分類が人手 | 型は定義済み、分類は人 | 失敗事例が増えると読みきれません | 中 |
| 9 | package 化していない | `python tools/xxx.py` 直呼び | 他の環境へ持ち出しにくいです | 低 |
| 10 | 費用・所要時間の見積もりが出ない | request 数のみ記録 | 「1周いくらか」が言えません | 低 |

## 3. 次にやる順（効果 ÷ 手間）

### Phase 1 — 母集団を広げ、取り逃しを測る

1. **情報源の追加**（#1）。Product Hunt（OAuth token）、Reddit（規約の再確認）、GitHub の repository 検索。
   `config/sources.yaml` に定義を足し、`collect_cases.py` に adapter を1つ足す形にします。
2. **網羅率の測定**（#2）。**capture-recapture（標識再捕獲法）** を使います。
   独立な2つの検索語群 A・B で集め、|A∩B| から母集団を推定します（Lincoln-Petersen 推定量
   `N ≈ |A|·|B| / |A∩B|`）。**生態調査で使われる標準的な手法で、追加の取得はほとんど要りません。**
   これで初めて「何割を見たか」が言えます。
3. **日をまたぐ store**（#4）。`log/cases.jsonl` を通し file にし、日単位 file は差分にします。

### Phase 2 — 壊れないようにする

4. **CI**（#7）。push で `pytest` と、config の regex 検証を回します。
5. **schema 版**（#5）。record に `schema_version` を持たせ、読み込み時に検査します。
6. **価格取得の強化**（#6）。headless browser は費用と可搬性を落とすため、
   まず「価格が JSON-LD や `<meta>` に入っている場合の抽出」で取れる範囲を広げます。

### Phase 3 — 読む量を減らす

7. **撤退理由の自動分類**（#8）。`doc/METHOD.md` §3 の8型への分類を、
   弱い標識（本文の語）＋人手 100件の正解で評価してから入れます。**評価せずに入れません。**

## 4. 「プロの道具」と呼べる条件（自己判定）

| 条件 | 判定 |
|---|---|
| 同じ入力から同じ出力が出る（再現性の記録がある） | **満たす** |
| 失敗が黙って結果に混ざらない | **満たす** |
| すべての数字に出所と取得日がある | **満たす** |
| 閾値と条件が code の外にあり、履歴が残る | **満たす** |
| 人の語彙に探索が縛られない | **満たす**（工程0） |
| **網羅の程度を数字で言える** | **未達**（Phase 1-2） |
| **情報源が1本でない** | **未達**（Phase 1-1） |
| 誰が回しても同じ結論に近づく | **未検証**（2周目以降で確認） |

**8項目中5つです。** 未達の3つは、いずれも「出てくる一覧をどこまで信じてよいか」に直結します。
現時点の一覧は**候補の生成には使えますが、「他に無い」という主張には使えません。**
